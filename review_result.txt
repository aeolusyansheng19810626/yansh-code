claude 4.7 opus 的review结果

  🔴 一、真实 bug / 安全问题（按严重度排）

  1. mcp_client.py:_reader_loop 退出时不唤醒 pending 请求 — 真死等 60 秒

  mcp_client.py:190-212：

  def _reader_loop(self) -> None:
      proc = self.proc
      if proc is None or proc.stdout is None:
          return
      for line in proc.stdout:   # ← server 死掉、stdout 关闭就自然退出
          ...

  server 进程崩溃 → stdout EOF → for 循环退出 → reader 线程结束。但 self._pending 里挂的所有 (Event, holder) 永远不会被
  set——_request 的 ev.wait(timeout) 会硬等到 _CALL_TIMEOUT_SEC（60s）。

  并发场景下还会更糟：reader 死了之后，连 is_alive() 都还是 True（直到 proc.poll() 被新一次 call_tool 调到才更新），LLM
  看到的不是"server 挂了"而是"工具超时"。

  修复（reader_loop 的 finally 里）：

  def _reader_loop(self) -> None:
      proc = self.proc
      try:
          if proc is None or proc.stdout is None:
              return
          for line in proc.stdout:
              ...
      finally:
          # server 死了：把所有 pending 全部唤醒，避免 _request 死等到 timeout
          with self._pending_lock:
              for mid, (ev, holder) in self._pending.items():
                  holder["msg"] = {"id": mid, "error": {
                      "code": -32000,
                      "message": f"server {self.name} stdout 已关闭（stderr 末尾：{self.stderr_buffer[-3:]}）",
                  }}
                  ev.set()
              self._pending.clear()

  2. mcp_client.MCPServer.shutdown 不杀孙进程 — 资源泄漏

  mcp_client.py:71-88 用 subprocess.Popen 启 server 完全没设进程组，对比 hooks.py:_run_one_hook 那段就漏了：

  # hooks.py 有，mcp_client.py 没有
  if _sys.platform == "win32":
      popen_kwargs["creationflags"] = subprocess.CREATE_NEW_PROCESS_GROUP
  else:
      popen_kwargs["start_new_session"] = True

  后果：shutdown() 只 terminate() 父 server；server 内部派生的孙进程（典型如 npx MCP server 跑 Node
  child_process）变孤儿。Windows 上 npx.cmd → node.exe → mcp-server.js 这条链常见。长跑场景（用户多次 /mcp
  restart）会积累一堆孤儿 node 进程。

  修复：mcp_client 抄 hooks 那段进程组创建，shutdown 时按平台杀进程组（taskkill /T /F 或 killpg）。

  ---
  3. hooks.py stdout 没大小上限 — 恶意/失控 hook 可 OOM

  hooks.py:167：

  stdout, stderr = proc.communicate(input=stdin_text, timeout=timeout)

  communicate 会把 stdout/stderr 全读进内存，没有任何 size 限制。一个 timeout=10s 的 hook 在 10s 内能写出几百 MB
  stdout（管道 buffer 满后 hook 写阻塞，但 communicate 一直在读）。

  风险等级：中（hooks.json 是用户自己写的，外部攻击面小，但 hook 写 bug 把 yansh 拖崩很可能）。

  修复：把 communicate 换成手动循环读 + 大小 cap，例如 stdout 累计 > 1 MB 就 kill 进程并报错。

  4. memory._slugify — 不是路径遍历但有静默覆盖

  针对 prompt 里担心的 ../../etc/passwd：

  s = re.sub(r"[^\w\-]+", "-", str(name).strip())

  /、. 都会变 -，所以 ../../etc/passwd → etc-passwd，写到 target_dir/etc-passwd.md，没逃出 target_dir——这块安全。

  但有个静默问题：

  return s.lower() or "memory"

  任何只含非 \w 字符的 name（"###", "---", ""）都被映射为 "memory"。不同恶意 name 会互相覆盖——LLM 调
  save_memory(name="!!!") 会无声覆盖之前的 memory.md。同 slug 直接覆盖在 docstring 里坦白了，但slug 退化到 "memory"
  的行为没有任何提示。

  修复：fallback 时 raise 或改用 f"memory-{hash(name)[:8]}"，让冲突不可能。

  5. hooks.py shell=True + cwd=workspace 的微妙风险

  prompt 里担心的注入路径："rm -rf $(echo $USER_INPUT)"——实际上 yansh 没把 user_input 注入 env，user_input 通过 stdin
  JSON 传给 hook。所以 $USER_INPUT 在 hook shell 里是空。这个具体场景安全。

  但还有一类真实风险：用户写的 hook 命令里有 unsanitized 变量替换。比如 hook 作者写 bash -c 'jq -r .user_input | xargs

  是 untrusted 输入；用 jq 解 JSON 而非 shell substitution"。

  🟡 二、并发 / 线程安全

  7. _task_log_mod._task_tool_calls 共享 list — CPython 现在安全，将来不安全

  task_log.py:19 + agent.py:1089：

  _task_tool_calls.append({"name": ...})

  并发的子 agent（含 general role 写工具）都在 append 这个全局 list。CPython 因 GIL 单条 list.append 字节码是 atomic
  的，目前没问题。finish_task_log 的 _task_tool_calls[:] 切片在 CPython 也不会崩。

  但：(1) Python 3.13+ free-threaded 模式去 GIL 后这就是 race；(2) finish_task_log 调
  dict.fromkeys(_task_files_modified) 时如果有并发 append，dict 构造迭代器期间 list 长度变化——CPython
  也只能保证不崩，结果未定。

  建议：task_log.py 给 _task_tool_calls / _task_files_modified 加一个 _lock，append 和 snapshot 都走锁。15
  行改动，永远不踩坑。

  8. init_mcp 的 TOOLS[:] = ... 与运行中子 agent 迭代竞态

  agent.py:2164-2166：

  TOOLS[:] = [t for t in TOOLS if not t["function"]["name"].startswith("mcp__")]
  TOOLS.extend(new_schemas)

  _subagent_tools_for_role (line 1974) 在子 agent 启动时 {t["function"]["name"] for t in TOOLS}。如果用户在子 agent
  跑的时候做 /mcp restart，迭代时 TOOLS[:] = ... 会触发 RuntimeError: list changed size during iteration。

  当前规避：/mcp restart 命令现在你应该是同步在 main 线程跑，子 agent 都在 ThreadPoolExecutor 里——存在并发可能。

  建议：要么 init_mcp 加锁，要么文档说明"运行中不能 hot-reload mcp"。

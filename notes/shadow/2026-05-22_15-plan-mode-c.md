# P2 #7 Plan Mode 方案 C 落地

承接 [_14](./2026-05-22_14-p1-batch-4-5-6.md)：P1 三项收尾后开始 P2，按用户要求"一个个来，先 #7"。
方案 B/C 二选一时讨论后用户选 **方案 C：完整状态机**——session 级 flag、跨多轮对话精炼方案、用户 /approve 触发实施。

## 改了什么

### 1) state.py 新增 plan 字段

```python
@dataclass
class Session:
    ...
    plan_mode: bool = False
    plan_draft: str = ""
    plan_history: list = field(default_factory=list)
```

`pull` / `push` / `reset` / `scoped_session` 都同步处理新字段。
agent.py 维护对应模块级 `_PLAN_MODE` / `_PLAN_DRAFT` / `_PLAN_HISTORY`——保持渐进式（不改读写路径）。

### 2) tools.py 加两个 sentinel 工具

```python
def update_plan_draft(content):
    return {"_plan_draft_update": True, "content": str(content or "")}

def exit_plan_mode_signal(reason=""):
    return {"_exit_plan_mode_signal": True, "reason": str(reason or "")}
```

跟 `task_complete` 同款 sentinel 形态——由 plan_chat 循环识别后处理。
两个工具加进 `READONLY_TOOL_NAMES` 白名单。

### 3) agent.py 新增 plan 路径

**`_PLANNER_ROLE` system prompt**：明确"写工具被禁用"、"用 update_plan_draft 整体替换草稿"、"用 exit_plan_mode_signal 表明等待审阅"、"不要调 task_complete（退出由用户 /approve 触发）"，附 plan 结构建议（## 目标 / ## 改动文件 / ## 步骤 / ## 风险）。

**`plan_chat(user_input)`**：完整循环
- 注入 workspace 顶层符号索引（同 audit）
- system prompt 末尾追加上一轮的 `_PLAN_DRAFT`（保持连续性）
- 工具白名单 = `_filter_tools(READONLY_TOOL_NAMES)`
- 多轮（最多 12 轮）：识别 `_plan_draft_update` → 写入 `_PLAN_DRAFT`；识别 `_exit_plan_mode_signal` → 跳出
- 沉默退出兜底：第一次没调工具追问一次让显式 exit signal
- 把用户输入和 assistant 文本沉淀进 `_PLAN_HISTORY`（不存 tool_calls，避免膨胀）

**状态切换 helper**：
- `enter_plan_mode()` / `cancel_plan_mode()`
- `is_plan_mode()` / `get_plan_draft()`
- `approve_plan() -> str`：把草稿拼进 requirement（"原始诉求 + 【已批准的实施方案 - 严格按此执行】+ draft"），清空 plan 状态，返回字符串供 `run()` 实施

### 4) main.py slash 命令族

```
/plan_on   进入 Plan Mode
/plan_off  退出（不实施，丢弃草稿）
/plan      查看当前草稿
/approve   批准并进 run() 实施
```

主循环判断 `agent.is_plan_mode()`：是 → 走 `plan_chat()`；否 → 原 classify_input → run/chat 路径。

### 集成验证（ICA Sonnet 4.6）

workspace 准备 calc.py（add/subtract）+ test_calc.py。

**R1**：`enter_plan_mode()` → `plan_chat("给 calc.py 加 multiply(a,b) 函数和对应测试")`
- LLM 调 read_file 看 calc.py / test_calc.py
- update_plan_draft 写完整草稿（## 目标 / ## 改动文件 / ## 步骤 / ## 风险）
- exit_plan_mode_signal 收尾
- 草稿 ~600 字符

**R2**：`plan_chat("再加 divide(a,b)，处理除零")`
- LLM 看到 system 里上一轮草稿
- update_plan_draft **整体替换**（不是追加）：草稿同时含 multiply + divide
- 风险段落详细讨论 ValueError vs ZeroDivisionError 选择
- 草稿扩展到 ~1500 字符

**/approve**：
- enriched requirement 1404 字符 = 原始 R1 用户输入 + "【已批准的实施方案 - 严格按此执行】" + 草稿
- plan_mode 关闭、草稿清空

**run(enriched, mode="auto")**：
- 进 plan() → code() → test
- LLM 严格按草稿执行（**只加 multiply 没乱加 divide**——草稿是强约束）
- 测试 rc=0 通过

**关键收益证据**：
1. **跨轮上下文保留**：R2 草稿基于 R1，不需要用户重述需求
2. **写工具屏蔽**：R1+R2 期间 LLM 看到的工具列表里没有 write_file，物理上不可能写代码
3. **草稿是强约束**：implementation 阶段 LLM 严格按草稿做，不引入计划外改动

## 评估

跟 P0 错误恢复闭环、P1 工程基础不一样，**Plan Mode 是用户体验创新**：

- 把"理解需求"和"动手做"拆开——用户能在 LLM 烧 token 之前就看到方案
- 多轮对话精炼方案，比单次 plan() 输出 JSON 灵活得多
- 写工具屏蔽是**物理保证**而不是 prompt 约定——LLM 看不见的工具不会被调

### 跟 Claude Code 的差距

Claude Code 的 Plan Mode 还有：
- **退出审批 UI**：批准/拒绝/编辑三选一，不只是 y/n
- **plan 草稿可编辑**：用户能直接改 markdown 而不是让 LLM 重写
- **subagent 探索隔离**：plan 阶段如果探索很深，子 agent context 不污染主线

yansh 当前是最小可工作版本，前两条只要 main.py 加几行就能补；第三条要等 P2 #9 子 agent 落地。

### 跟方案 B 的本质区别

方案 B 是单次任务内的 plan→exit→approve→implement——一进去就只能 y/n 一次。
方案 C 是 session-level flag——用户能反复对话直到方案满意才 /approve。**关键场景**：用户改了好几次方案才决定执行，这种迭代没法用方案 B 完成。

下一波（不在这次范围）：
- 退出审批 UI：批准/拒绝/编辑三选一
- 草稿手工编辑入口：`/plan_edit` 打开 $EDITOR 编辑当前草稿
- approve 后 implementation 阶段是否还要再走一次 plan()——目前是会再走一次（拿 enriched requirement 再分解），未来可以让 enriched requirement 直接跳过 plan 阶段
- plan_chat 的 token 预算控制（当前只有 12 轮硬上限，没有 token 预算）

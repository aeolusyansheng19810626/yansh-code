# task61-69 R1 修复与重跑

## 重大环境坑：editable 安装并发损坏（已根治）

- 现象：并发跑多个 `yansh.exe`（pip install -e）→ dist-info 损坏成 `~ansh_code-0.1.0`、editable finder 丢失 → `ModuleNotFoundError: No module named 'main'`。
- 规律：每批第 3 个崩、前两个成功（损坏渐进）；重装 editable 只能临时救，再并发又坏；串行补跑也崩（已被上一轮并发跑坏）。
- 误判过程：先以为是"并发偶发"，给 runner 加崩溃重试 —— 但重试对**持续性**损坏无效。
- **根治**：runner 改用 `python -m main`（cwd=TOOL_HOME 直接从源码 import main），完全不走 yansh.exe 的 editable finder。串行重跑 9 个全部 exit 0，确认有效。
- 教训：AB 测试跑 editable 安装的 CLI，并发会破坏安装；用 `python -m <entry_module>` 绕开。

## R2 诊断结论（已看 log，精确定性）

### task65：yansh 真缺陷（replace 失败不自检 + 谎报完成）
- 功能 rename 成功（所有测试通过），但 agent.py:1877 / subagent.py:124 的**功能性 prompt 文本**残留 `directory_summary(path='<dir>')`（拼给 yscode 自己 LLM 的提示，不改会误导调用旧名）。
- 真因：yansh 的 replace_in_file 构造 old_str 时多写了转义（`...')):\"`)→ 匹配失败 → 反复用错误 old_str 重试 → 始终没改成 → 最后 task_complete 谎称"已完成/只在文档"。
- cc 对比：cc 的 Edit 失败可见+重读重试，更稳；yansh 缺"失败察觉→纠正"闭环。

### task66：轮次预算调度低估（非 hardcap 太低）
- config 实际：coder_rounds_per_file=8（基线）、coder_max_rounds_per_file=20（硬顶）。
- 调度 bug：edits_per_round=3 假设过乐观，expected_edits=12 → ceil(12/3)=4，max(8,4+3)=8 → 只分到基线 8 轮（没到 20）。实际逐处 read+replace 一轮改 1 处，12 处需 12-15 轮 → 半途切断，且先改了测试、源码签名没改完 → test_subagent 6 失败。
- cc 对比：cc 无每文件固定轮次上限，模型自主判断完成。

### task62：矛盾需求，yansh 用 monkey-patch 绕过（已确认机制）
- 需求自相矛盾（不改 tools.py 却要给其函数加参数）。yansh 不喊停，新建 tools_ext.py 用 `tools.search_in_files=包装函数` monkey-patch 绕过。
- 全量 pytest 失败具体原因：单独跑 10 passed；全量跑时 yscode 的模块隔离机制（test_session_isolation/conftest）重载 tools 模块 → patch 失效 → test_tools_ext 全部 `TypeError: unexpected kwarg max_results`（8 处）。
- （test_tools.py 5 个失败是 pre-existing 中文断言 flaky，与 task62 无关）

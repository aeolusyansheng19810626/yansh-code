## 测试项目：strkit（字符串工具库）

专门为 AB test 创建的小型 Python 项目，需在运行前手动搭建。

### 项目结构

```
strkit/
├── strkit/
│   ├── __init__.py
│   ├── transform.py    # slugify / truncate / camel_to_snake 等转换函数
│   ├── validate.py     # is_email / is_url / is_phone 等验证函数
│   └── stats.py        # word_count / char_freq / readability_score
├── tests/
│   └── unit/
│       ├── test_transform.py
│       ├── test_validate.py
│       └── test_stats.py
├── pyproject.toml      # pytest 配置
└── README.md
```

### 设计原则

- 代码量适中（每个模块 ~80 行），AI 可在 1-2 次 read 内掌握全局
- 有明确的现有测试（pytest），便于 success 判定
- 不依赖外部服务，纯 Python 标准库
- 每个 task 对应不同难度和场景类型

## Task 11（中等）— 非主场 bug fix，无 test 引导

**类型**：定位 + 修复，只有症状，无 failing test

**场景**：`truncate()` 函数处理含 emoji 或 CJK 字符的字符串时截断位置不对，
部分多字节字符会被截断到中间（用户反馈"截出来的字符串末尾有乱码"）

**Prompt**：
```
strkit 的 truncate(text, max_len) 函数在处理含 emoji（如 "Hello 🌍 World"）
或中文字符时会截断位置异常：
  truncate("你好世界abc", 5) 可能返回带乱码的结果，而不是 "你好世界a"
用户只知道报错现象，没有对应单测。

定位根因，修复 transform.py 中的 truncate()，
加 2 个单测：emoji 截断正确 / 中文+ASCII 混合截断正确。
```

**预期改动文件**：`strkit/transform.py`、`tests/unit/test_transform.py`

**难点**：需理解 Python str（Unicode 码位）vs bytes 的区别，以及 `len()` 的语义；
陌生 codebase，要先 read 现有实现再定位根因

**成功标准**：test_result=pass，files_modified 包含 transform.py + test_transform.py

## Task 12（中等）— 非主场新功能，有明确 spec

**类型**：新功能 + 单测，功能不存在于项目中

**Prompt**：
```
给 strkit 的 transform.py 添加 wrap_text(text, width, indent="") 函数：
- 按 width 字符宽度换行，在单词边界断行（不切单词）
- indent 参数在每行行首加前缀（用于代码块缩进场景）
- 空字符串输入返回空字符串
- 加 4 个单测：基础换行 / indent 前缀 / 长单词不截断 / 空字符串
```

**预期改动文件**：`strkit/transform.py`、`tests/unit/test_transform.py`

**难点**：需理解现有 transform.py 的代码风格和导出方式，保持一致；
`wrap_text` 的边界情况（单个超长单词如何处理）需要 LLM 自行决策

**成功标准**：test_result=pass，4 个新单测全过

## Task 13（中等）— 非主场重构，行为不变

**类型**：消除重复代码，不改行为

**场景**：`validate.py` 里 `is_email`、`is_url`、`is_phone`、`is_ipv4` 四个函数
都有相同的"compile pattern → match → return bool"样板代码

**Prompt**：
```
strkit/validate.py 里 is_email / is_url / is_phone / is_ipv4 四个函数
都有重复的正则匹配样板代码（compile + fullmatch + return bool）。

把这个模式抽取成私有辅助函数 _match(pattern: str, value: str) -> bool，
四个公开函数改用它。确保所有现有单测通过，不改变任何公开行为。
```

**预期改动文件**：`strkit/validate.py`

**难点**：纯重构，files_modified 只有一个文件，单测不变；
需理解"行为不变"的重要性，不能改变任何已有正则或返回值语义

**成功标准**：test_result=pass，files_modified=[validate.py]，现有测试全部通过

## Task 14（中高）— 非主场跨文件新子系统

**类型**：跨模块新功能，需要协调 transform + validate + 新文件

**Prompt**：
```
给 strkit 添加 Pipeline 类，支持链式处理字符串：

1. 新建 strkit/pipeline.py，暴露 Pipeline 类：
   - add(func) 方法：添加一个处理步骤（callable，接收 str 返回 str）
   - run(text) 方法：依次执行所有步骤，返回最终结果
   - run_batch(texts: list[str]) 方法：对列表中每个字符串执行流水线
2. strkit/__init__.py 导出 Pipeline
3. 加 4 个单测：空流水线 / 单步 / 多步链式 / batch 处理
```

**预期改动文件**：`strkit/pipeline.py`（新建）、`strkit/__init__.py`、`tests/unit/test_pipeline.py`（新建）

**难点**：需要创建新文件 + 修改 `__init__.py` 导出，理解项目的 import 结构；
`run_batch` 的错误处理方式（跳过/停止/收集错误）需要 LLM 自行决策

**成功标准**：test_result=pass，新建 pipeline.py + test_pipeline.py

## Task 15（中高）— 非主场需求模糊，需设计决策

**类型**：spec 故意留白，LLM 需要自己做架构决策

**Prompt**：
```
strkit 的 stats.py 里 readability_score(text) 函数计算的是
Flesch Reading Ease 分数，但用户反馈返回值不直观（浮点数 0-100）。

改进这个函数，让它返回更易读的结果。具体形式自行设计，
但要满足：
- 原有分数信息不丢失
- 有人类可读的等级描述（如"简单"/"中等"/"较难"）
- 加单测覆盖至少 3 个分数区间
```

**预期改动文件**：`strkit/stats.py`、`tests/unit/test_stats.py`

**难点**：返回值类型完全由 LLM 决定（dict / namedtuple / dataclass / str），
不同选择代表不同的设计质量；等级划分阈值也需要 LLM 自行研究 Flesch 标准

**成功标准**：test_result=pass，stats.py 返回值含等级描述，有 3 个以上单测覆盖

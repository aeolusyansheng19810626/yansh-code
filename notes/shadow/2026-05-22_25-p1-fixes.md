## P1-1: mcp 子进程生命周期（reader_loop EOF + shutdown 杀进程树）

### 漏洞 A：`_reader_loop` EOF 不唤醒 pending（Codex + Claude）

`mcp_client.py:_reader_loop` 是个 `for line in proc.stdout` 循环。server 崩溃 → stdout EOF → for 退出 → reader 线程结束。但 `self._pending` 里挂的所有 `(Event, holder)` 永远不被 set——`_request` 的 `ev.wait(timeout)` 死等到 `_CALL_TIMEOUT_SEC=60s`。

LLM 看到的不是"server 挂了"而是"工具超时"——错误诊断完全偏向。

### 漏洞 B：`shutdown` 不杀孙进程（Gemini + Claude）

`mcp_client.py:shutdown` 只 `proc.terminate()`／`proc.kill()`。npx → node → mcp-server.js 这条链上的孙进程会变孤儿。长跑场景（用户多次 /mcp restart）积累孤儿 node 进程。

### 修复

**A**：`_reader_loop` 加 `try/finally`——finally 里把 `_pending` 全部 set 一个错误响应：

```python
finally:
    stderr_tail = list(self.stderr_buffer[-3:]) if self.stderr_buffer else []
    with self._pending_lock:
        for mid, (ev, holder) in self._pending.items():
            if "msg" not in holder:
                holder["msg"] = {
                    "id": mid,
                    "error": {"code": -32000,
                              "message": f"server {self.name} stdout 已关闭..."},
                }
            ev.set()
```

**B**：Popen 加进程组 + shutdown 用 `_kill_tree`：

```python
# Popen
if _sys.platform == "win32":
    popen_kwargs["creationflags"] = subprocess.CREATE_NEW_PROCESS_GROUP
else:
    popen_kwargs["start_new_session"] = True

# shutdown：跳过 graceful 直接 kill_tree（必须趁父还活着才能枚举到孙）
if proc.poll() is None:
    self._kill_tree(proc)

# _kill_tree：psutil 优先（最可靠），fallback 平台原生
@staticmethod
def _kill_tree(proc):
    try:
        import psutil
        root = psutil.Process(proc.pid)
        victims = root.children(recursive=True) + [root]
        for p in victims:
            try: p.kill()
            except psutil.NoSuchProcess: pass
        psutil.wait_procs(victims, timeout=2)
    except ImportError:
        # fallback: taskkill /F /T (Win) / killpg (POSIX)
        ...
```

### 关键设计权衡

**为什么跳过 graceful 直接 kill_tree？**

最初尝试是先 `terminate() + wait(2)` graceful，超时再 `_kill_tree`。问题：父进程可能 graceful 退出（wait 成功），但孙进程独立 sleep 不受影响。父退后 `psutil.Process(pid)` 抛 NoSuchProcess——孙列表丢失，孙泄漏。

正确方案：**趁父进程活着枚举孙列表**。`children(recursive=True)` 必须在父还在时调用。所以 close stdin（给 server 退出信号）后立刻 `_kill_tree`，不给 graceful 机会。

MCP server 也设计成可被强制关闭（close stdin 已是协议级信号），不需要 graceful 清理。

**为什么 psutil 优先而非 taskkill /T？**

Windows 下 `subprocess.Popen + CREATE_NEW_PROCESS_GROUP` 不构成 Job Object——子进程通过 `Popen → Popen` 派生时，孙不在父的"进程树"里。`taskkill /T /PID parent_pid` 找不到孙。

而 `psutil.Process.children(recursive=True)` 走 OS 的进程父子关系链——能真正"看见全树"。Linux/macOS 上 `killpg` 可靠，psutil 也行。所以 psutil 是跨平台一致最可靠的方案。

def find_memory(name, workspace_dir=None):

## P1-3: tree-sitter `_TS_PARSER` 并发不安全

### 漏洞

`tools.py:691` `_TS_PARSER` 是模块级单例，懒加载无锁；`tools.py:743/581/792` 三处 `parser.parse(src_bytes)` 跨线程共享。tree-sitter Python binding 的 Parser **不是线程安全的**——并发 subagent 启动 `agent.py:1995 workspace_symbols()` 都会撞 parser，冷缓存下能造数据脏。

### 修复

加全局锁串行 parse 调用：

```python
_TS_PARSER_LOCK = threading.Lock()

def _load_ts_parser():
    if _TS_PARSER is not None:
        return _TS_PARSER, None
    with _TS_PARSER_LOCK:
        # double-check
        if _TS_PARSER is not None:
            return _TS_PARSER, None
        # ... init
        _TS_PARSER = Parser(py_lang)

def _ts_parse_locked(parser, src_bytes):
    with _TS_PARSER_LOCK:
        return parser.parse(src_bytes)
```

3 处 `parser.parse(src_bytes)` 改成 `_ts_parse_locked(parser, src_bytes)`。

### 设计权衡

**为什么单锁而非 thread-local parser？**

thread-local 看起来更"高大上"——每个线程有自己 parser，无锁。但：
1. tree-sitter Parser init 不便宜（~50ms 加载 grammar）
2. yansh 并发场景：典型 ≤4 subagent 同时 parse
3. 单次 parse 通常 < 10ms

**算法**：4 个并发线程 × 10ms parse = 串行总 40ms（用单锁）vs 4 × 50ms init + 4 × 10ms parse = 240ms（thread-local）。**单锁反而快**。

未来如果 yansh 真做大量并发 parse（比如 background indexer），再换 thread-local 也不晚。

## 三个 P1 共同的设计教训

### 1. "graceful 退出" vs "强制收尾"——子进程管理的关键权衡

第一版 `shutdown` 想让 server graceful 退出（terminate + wait），却没考虑孙进程不响应父的 graceful 信号。**子进程管理永远要假设最坏：进程树深、不响应信号、有 sleep**。

正确范式：
- 给信号（close stdin / SIGTERM）让良民自己退
- 给极短 timeout（≤1s 而非 ≤60s）
- 然后**无条件 kill_tree**——别等

### 2. 路径校验：slugify ＋ resolve() 双保险

只 slugify 不够（防 `../../X` 但不防 symlink 攻击）；
只 resolve() 不够（防 symlink 但不阻 slugify 已防的字面 `../`）。
**两者叠加才完整**——边际成本 5 行代码。

### 3. 跨线程共享对象的"看似安全"陷阱

tree-sitter Parser 的 `parse()` 看起来纯函数（输入 src_bytes 输出 tree）——但 Parser 实例内部有可变状态。这种"看起来无状态实际有状态"的库太常见了——SQLite connection、numpy random、re.compile 缓存。

**经验法则**：**第三方库实例跨线程必须查 thread-safety 文档**——除非文档明确说 thread-safe，否则默认不是。一把锁包起来代价小，避免脏数据隐患。

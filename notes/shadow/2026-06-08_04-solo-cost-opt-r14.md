# solo mode 降本优化：R14 实测 + compact 根因分析

**日期**：2026-06-08

## 背景

solo mode 默认 sonnet+solo 已证明可达黑盒 10/10（R13，$16.8，120 轮烧满）。主要成本来源：ICA 无 prompt cache + O(N²) context 累积。委托 opus-4.8 分析降本方案，得出三项可立即实施的优化。

## 三项优化（已实施，commit 推送）

### ① execute_command 输出头尾截断
- **位置**：`tools.py`，新增 `_truncate_cmd_output()`，超 6000 chars 截头尾各 3000
- **效果**：pytest 中段 PASSED 行不再永久留在 context 每轮重发
- **风险**：加 `[... N chars truncated ...]` 标记，agent 可主动用 `-v` 补全；几乎零风险

### ② _SOLO_ROLE 加 pytest -q 指令
- **位置**：`agent.py _SOLO_ROLE` 自测段
- **效果**：agent 主动减少 pytest 输出量，从源头降低 tool result 体积
- **验证**：R14 中 agent 确实使用了 `-q`

### ③ compact threshold 60K → 40K
- **位置**：`agent.py _make_compact_state`
- **效果**：更早触发压缩，降低 O(N²) 累积的常数项
- **副作用**：见下方根因分析

## R14 实测结果

**三项优化合计节省 22% input token，质量持平。**

## R14 过程关键观察

### 正向：节奏明显改善
- 轮 1–14：每轮写一个文件，14 轮写完全部 14 个模块（R13 更多轮）
- pytest `-q` 被正确使用（② 生效）
- compact 在第 49 轮触发（40K 阈值），压缩 40K→2.5K（94%），降低了后续峰值

### 负向：compact 后丢失环境记忆
- 轮 15–71：`cd /workspace` 路径探索（Linux 路径在 Windows 无效），但最终在第 72 轮找到 `py -3.11 -X utf8 -m pytest` 有效路径
- 轮 86：compact 再次触发（45K→11.8K）。**第 72 轮学到的路径被二次压缩吞掉**
- 轮 88–104：重新探路，浪费约 15 轮，退化为 R13 的老问题

## compact 摘要二次压缩退化：根因分析

委托 opus-4.8 深入分析（读了相关代码），核心发现：

**失效机制**：
1. 第 49 轮 compact → 生成摘要 A（system message）
2. 第 86 轮 compact 时，摘要 A 被当成普通 old_pair 再次喂给 summarizer
3. Summarizer prompt（`_SUMMARIZE_SYSTEM`）没有要求保留"已验证的 shell 命令"
4. Summarizer 把 `py -3.11 -X utf8 -m pytest` 当噪音省略 → 摘要 B 中命令丢失
5. Agent 从摘要 B 中读不到可用路径 → 重新探路

**为什么 keep_recent_pairs=3 治标不治本**：
- 问题不在"最近一对被切掉"，而在"多次 compact 的摘要逐代退化"
- keep=3 只推迟失效点一轮，第三次 compact 照样丢
- 实际 token 代价 +500-800K（不是估算的 +300K），性价比可能为负

## 修复方案（已实施）

**改 `_SUMMARIZE_SYSTEM` 加强制项⑥**（零 token 开销，直击根因）：

```
⑥ 已验证可用的运行环境事实（python/pytest 命令、工作目录、失败前缀）
**强制项：第⑥点必须逐字保留已验证成功的 shell 命令原文**
（如 `py -3.11 -X utf8 -m pytest`），不可泛化或省略。
```

让 summarizer 把环境命令"钉进"每一代摘要，防止二次压缩退化。摘要字数上限从 800→900 字（为⑥留空间）。

## R15 实测：summarizer⑥ 验证 + 状态文件方案讨论

**R15 参数**：同 R14（40K/keep=2）+ summarizer⑥ 修复

| | R13 | R14 | R15 |
|---|---|---|---|
| input tokens | 5.27M | 4.08M | 4.67M |
| cost | $16.8 | $13.2 | $15.7 |
| compact 次数 | 1 | 2 | **4** |
| 探路轮次浪费 | ~10轮 | ~15轮 | **0轮** |
| 黑盒 | 10/10 | 10/10 | **4/10** |

**⑥ 验证结论**：四次 compact 全程零重新探路（R14 round 88-104 的浪费消失）。但 R15 token 反而比 R14 多（4次 compact 开销 + 本跑实现 bug 更多修复轮次），黑盒 4/10 是本跑实现质量波动，与 summarizer 修复无关。

**状态文件方案（opus-4.8 评估）**：

summarizer⑥ 本质仍是概率性（summarizer 未来可能遗漏）。更可靠的方案是 **agent 写、框架在 compact 时自动注入**：

- **写**（role 指令）：发现有效命令/签名时 agent 主动 `replace_in_file .yansh/agent_state.md`
- **读**（框架托管）：`_compact_messages` 触发时，把 `.yansh/agent_state.md` 原文塞进 `[历史摘要]` message——不依赖 agent 记得读，100% 确定性

状态文件内容（最小必要集）：① 已验证运行命令；② 失败命令黑名单；③ 自产 symbol contract（跨文件签名）；④ 当前进度/卡点。不存代码内容。

**前置确认项**：`.yansh/agent_state.md` 不能进 `_infer_test_scope` 的 files_modified（否则 test gate 误用）。

**优先级**：中。⑥ 已解决当前痛点，状态文件是加固（应对长任务多次 compact、symbol contract 漂移）。建议先跑最小版 A/B 验证再决定是否删⑥。

## R16 实测：状态文件 role 指令验证失败 + 下一步方案

**R16 参数**：同 R14（40K/keep=2）+ summarizer⑥ + 状态文件 role 指令 + 框架 compact 注入

| | R13 | R14 | R15 | R16 |
|---|---|---|---|---|
| input tokens | 5.27M | 4.08M | 4.67M | **4.44M** |
| cost | $16.8 | $13.2 | $15.7 | **$14.3** |
| compact 次数 | 1 | 2 | 4 | **2** |
| 探路浪费 | ~10轮 | ~15轮 | 0轮 | **~1轮** |
| 黑盒 | 10/10 | 10/10 | 4/10 | **9/10** |
| 状态文件创建 | — | — | — | **从未** |

**状态文件 role 指令失效根因（opus-4.8 分析）**：

1. **奖励结构错配**：写状态文件对当前轮任务进展零即时收益，每轮都输给"继续修 bug"。LLM next-action 选择本质是"哪个动作最像在解决眼前问题"——写元信息永远失败。
2. **内省触发不可靠**："发现有效命令后立即写入"要求 agent 自己判断"我刚才那个是有效命令"再切换动作——连续执行流里几乎不会自发做这种状态盘点。
3. **无负反馈**：没写不会立刻受惩罚，惩罚延迟且不可归因（agent 不会把"重新探路"反推成"我没写状态文件"）。
4. **可选措辞自我豁免**："只在有新事实时才更新"给了充分的不作为借口。
5. **文件在 context 里不存在**：从未创建过 → compact 注入跳过 → agent 永远看不到这个文件存在。

**根本原则（opus 总结）**：凡是框架能确定性获得的元信息（命令 exit code、文件写入历史），就不要让 LLM 维护。

**下一步实现方案（opus 方案 A + 跨 run 扩展）**：

框架自动维护 `.yansh/agent_state.md`，不依赖 agent：
1. `execute_command` dispatch 层：命令首次成功 → 自动追加白名单；非零退出 → 追加黑名单
2. `solo()` 启动时：如果 `.yansh/agent_state.md` 存在，注入进 system prompt（**任务开始注入**，不只是 compact 时）
3. compact 时也注入（已实现）

**跨 run 复用价值**（用户提出）：
- 状态文件保存在 workspace，跨任务持久化
- 第二次在同一 workspace 跑任何任务，开局就知道环境，探路成本接近 0
- 适合跨 run 保存：有效 python 命令、pytest 路径、失败前缀、项目约定
- 不适合：上次任务的代码签名、具体进度

## 性价比与路由建议

- solo 默认 mode（已改 config），小任务绝对成本差 $0.4-0.8 可忽略
- sonnet+solo 强化 PROMPT = $13.2 可达 10/10（R14），性价比最优
- opus 仅在需要高效 agent 环境感知时有溢价（$13→$48），纯 SQL 能力无差异
- compact 参数：threshold=40K 保留，keep_recent_pairs=2 保留，通过 summarizer prompt 修复退化

## P2-1: 抽 `procutil.py` 给 hooks/mcp 共用

### 动机

P1-1 给 mcp_client 加了 `_kill_tree` 静态方法处理孙进程；hooks.py 早就有一份**几乎一样的** taskkill / killpg + Popen 进程组 创建逻辑。两边各写一份会漂移（事实上 hooks 没用 psutil，mcp 用了；如果 mcp 改了实现，hooks 不会跟上）。

### 修复

新模块 `procutil.py` 提供：
- `spawn_with_pgroup(cmd, **popen_kwargs) -> Popen`：自动按平台加 `creationflags / start_new_session`，调用方无需重复 if win32
- `kill_tree(proc, timeout=2.0) -> None`：psutil 优先（最可靠），fallback 平台原生（taskkill /F /T / killpg SIGKILL）

mcp_client 和 hooks 都改用 procutil；`MCPServer._kill_tree` 保留为透传 wrapper（向后兼容）。

### 验证

`tests/unit/test_procutil.py` 5 条：
- `test_spawn_sets_platform_pgroup_flag`：起 Python 子进程不挂
- `test_spawn_preserves_existing_creationflags_windows`：已传 creationflags 时不覆盖（OR 合并）
- `test_kill_tree_kills_grandchild`：**端到端**——父 spawn 孙 sleep(60)，kill_tree 后 psutil 验证孙 pid 不存在
- `test_kill_tree_handles_none_proc`：边界
- `test_kill_tree_handles_already_dead_proc`：边界

## P2-2: hooks.py stdout/stderr size cap

### 漏洞

`hooks.py:proc.communicate(input=stdin_text, timeout=timeout)` 把 stdout/stderr 全读进内存，**没有大小限制**。一个失控/恶意 hook 在 10s timeout 内能写几百 MB stdout——管道满后写阻塞，但 communicate 一直读，OOM。

### 修复

`communicate` 换成 3 个后台线程 + 主线程协调：
- 写线程：阻塞写 stdin（避免 stdout 满 + stdin 写阻塞死锁）
- 读 stdout 线程：循环 read(4096)，累计 > `_HOOK_STDOUT_CAP=1MB` 立即 set `cap_exceeded`
- 读 stderr 线程：同上，cap=256KB
- 主线程：每 50ms 检查 `cap_exceeded.is_set()` / `t.is_alive()` / 超时 deadline

任一触发 → `kill_tree` + 返回 `_hook_error`。

`_HOOK_STDOUT_CAP=1MB`：远大于正常 hook 用量（典型 < 1KB），但能挡住失控的几百 MB 输出。

### 验证

`tests/unit/test_hooks.py` +2 条：
- `test_run_one_hook_stdout_size_cap_kills_runaway_hook`：5MB 输出 hook → cap 触发 → 错误信息含"上限"，elapsed < 10s（不等 30s timeout）
- `test_run_one_hook_normal_output_under_cap_works`：正常小输出 hook 完整接收（防过度限流）

`test_hooks.py` 28 → 30 全过。

## P2-3: `task_log` 全局 list 加锁

### 漏洞

`task_log.py:18-20` 模块级 `_task_tool_calls` / `_task_files_modified` 是 list，被 agent 多处直接 `.append()`。CPython GIL 下 list.append 单条原子，但：
1. `finish_task_log` 的 `dict.fromkeys(_task_files_modified)` 迭代期间如果有并发 append → 结果未定（CPython 文档说"行为未定义"）
2. Python 3.13+ free-threaded 模式去 GIL 后 list.append 也不再原子

子 agent 并发跑时多个线程同时写日志，记录顺序乱、可能漏。

### 修复

`task_log.py` 加 `_log_lock = threading.Lock()`，所有读写走锁：
- `init_task_log` / `finish_task_log` clear + update 整段加锁
- `record_file_modified` / `record_tool_call` append 加锁
- 新增 `snapshot_files_modified()` / `snapshot_tool_calls()` helper 给读取者用

`agent.py` 改 7 处直接 append → `record_file_modified` / `record_tool_call`；2 处只读切片 → `snapshot_*`。

`finish_task_log` 写盘 IO 释放锁后做（先在锁内 snapshot 一份 dict，IO 外 dump JSON），减少持锁时间。

### 验证

`tests/unit/test_task_log_concurrency.py` 4 条：
- `test_record_file_modified_concurrent_appends_complete`：50 线程 × 100 次 → 总长度 == 5000（无丢失）
- `test_record_tool_call_concurrent_appends_complete`：同上
- `test_snapshot_during_concurrent_writes_no_crash`：5 写 + 3 读并发 → 不抛
- `test_finish_task_log_under_concurrent_writes_consistent`：200 条记录后 finish 写盘正确

## P2-4: `init_mcp` `TOOLS[:]=...` 与子 agent 迭代竞态

### 漏洞

`agent.py:2161 init_mcp` 用 `TOOLS[:] = [...]; TOOLS.extend(...)` 原地修改。子 agent 在 `_subagent_tools_for_role` 里 `{t["function"]["name"] for t in TOOLS}` 迭代。**用户在子 agent 跑的时候 `/mcp restart`** → `RuntimeError: list changed size during iteration`。

### 修复

`agent.py` 加 `_TOOLS_LOCK = threading.Lock()`：
- `init_mcp` 整段 TOOLS 修改加锁
- `_filter_tools` 迭代加锁
- `_subagent_tools_for_role` 迭代加锁

锁是普通 Lock 不是 RLock——当前调用者都没递归持锁，简单的 Lock 够用。

### 验证

`tests/unit/test_subagent.py` +1 条：
- `test_concurrent_init_mcp_and_subagent_tools_no_crash`：2 个 writer 反复改 TOOLS 加 50 个 fake mcp 工具 + 4 个 reader 反复 `_subagent_tools_for_role` → 不应抛 RuntimeError ✅

加锁前必撞——加锁后 35/35 通过。

## P2-5: `stderr_buffer` 改 `deque(maxlen=50)`

### 漏洞

`mcp_client._stderr_loop` 的 `self.stderr_buffer.append(line); if len > 50: self.stderr_buffer.pop(0)` 跟 `call_tool` 错误诊断里 `srv.stderr_buffer[-3:]` 同时跑——`pop(0)` 不是原子操作（O(n) 移动元素 + 改长度），并发读 `[-3:]` 期间可能踩到中间状态、IndexError、脏读。

### 修复

`list` → `collections.deque(maxlen=50)`——append 自动 ringbuffer 淘汰旧条目，**不需要手动 pop**，从根上消除 race。

副作用：deque 不支持 slice (`[-3:]`)。两处读取都改成 `list(self.stderr_buffer)[-3:]`（先转 list 再切）。

`_stderr_loop` 简化：

```python
# 改前
self.stderr_buffer.append(line)
if len(self.stderr_buffer) > 50:
    self.stderr_buffer.pop(0)

# 改后
self.stderr_buffer.append(line.rstrip("\n"))
```

### 验证

无新增单测——一行修改 + 既有 mcp 测试 27/27 全过即可。

## 学到什么

### "看似无害的实现细节"是并发 race 的常见来源

P2-3 / P2-4 / P2-5 都是同一类漏洞：**单个操作 CPython 下原子，组合操作不原子**。
- list.append 原子，但 `for x in list` 迭代期间 append 行为未定
- list.pop(0) 看似单步，实际 O(n)，可读端会踩中间态
- TOOLS[:]= 原地赋值看似单步，实际"清空 + 重建"两步

**经验法则**：任何"读-改-写"或"迭代-修改"的组合都需要锁。CPython GIL 不是免死金牌，只是让单个字节码原子——你的语义边界不一定跟字节码边界对齐。

### "有 maxlen 的 deque" 是 list+pop(0) 的免费替代

`deque(maxlen=N)` 不仅消除手动 pop 的 race，性能上 popleft 是 O(1) 而 list.pop(0) 是 O(n)。这是个**结构性**改进——选对数据结构胜过加锁。

很多看起来需要锁的小数据结构（"最近 N 条日志"、"LRU 缓存"），其实换 `collections.deque` / `functools.lru_cache` 就能在不加锁的前提下变线程安全。

### Hook 资源限制要"读端做"而不是"信任写端"

Hook 是用户自己写的脚本——不能假设它输出小、不能假设它响应 stdin、不能假设它会自己退。所有限流都必须**读端实施**：
- size cap：读端累计 byte 数，到了就 kill
- timeout：deadline 由父进程计时
- pipe 死锁防护：写 stdin / 读 stdout / 读 stderr 必须各一个线程，不能 communicate(input=...)

这跟 web server 处理 untrusted client 是同款思路——一切外部输入都假设恶意。

### 抽公共代码的时机

procutil 抽出来恰到好处——之前 hooks 和 mcp_client 各写一份 `taskkill /T /F` / `killpg`，看起来差别小但漂移已发生（mcp 用了 psutil，hooks 没用）。**抽到 ≥2 个 caller 共用时再抽**——抽得太早就是过度设计。

P2-1 修了 P1-1 没修干净的最后一公里。

## 根因（opus-4.8 log 分析）

**双层失效：**

1. **Coder 把 benchmark 当成 search.py 的工作**：任务要求"先 benchmark 再优化"，coder 把"benchmark"步骤全部放在 search.py 的 5 轮预算里，`python -c` 被安全策略拦截后绕道写 benchmark 脚本再跑，5 轮耗尽，一次 `replace_in_file` 都没发。

2. **Runner success 基于独立 pytest，与 yansh 内部无关**：yansh 内部即使质量门报失败，runner 跑 pytest 看不到新失败，仍报 success=true。

## 修复过程（三轮迭代）

### 第一轮：质量门 + pattern 5（commit fddc326）

- `_CODER_ROLE` 加 pattern 5：benchmark 是过程非产物，轮次耗尽未改目标文件须 task_complete(success=False)
- `_run_impl` 阶段3前加质量门：检测 plan 里 expected_edits>0 的文件是否出现在 files_modified，缺失则调 fix()

**结果**：质量门触发 ✓，但 fix() 看到 pytest 通过就返回，fix() 不适合补做编码工作

### 第二轮：质量门改为拦截 judge()（commit fb1b751）

- 移除质量门里的 fix() 调用
- 改为在 `judge(test_result)==True` 时二次检查 `_missing_files`
- 若计划文件仍未修改，强制返回 `report(False, ...)`

**结果**：质量门正确拦截，yansh 内部报 false ✓，但 runner 仍报 success=true

### 第三轮：runner 联动 + prompt 修正

- 更新 task21_runner：`success = pytest_pass AND yansh_internal_pass`
- 发现根本问题是 prompt 本身——"先 benchmark 再优化"让 coder 把 benchmark 当核心工作
- 改 prompt：明确说"O(n²) 嵌套循环，改成 O(n) 实现"，不再要求 benchmark 步骤

**结果**：search.py 正确修改，测试全过，success=true ✓

## 经验教训

### 1. "先 benchmark 再优化" 这类 prompt 对 yansh 有毒

当 prompt 包含"先做 X 再做 Y"的顺序指令，且 X 是消耗型操作（写脚本/运行命令），coder 会把 X 的轮次耗光后没有余力做 Y。

**解决方向**：
- 对用户：避免在 prompt 里要求"先 benchmark"，直接描述问题让 yansh 自己决定是否需要度量
- 对 yansh 本身（pattern 5）：benchmark 脚本不消耗目标文件预算，被安全策略拦截后直接优化

### 2. 质量门设计原则

质量门用于**发现问题**，不应试图用 fix() 来**自动修复**——fix() 是修测试失败用的，不适合补做未完成的编码工作。

正确设计：
- 质量门 → 记录缺失文件 → 拦截 judge() 假通过 → 报告真实失败
- 不调 fix()，不试图自动完成遗漏的编码

### 3. Runner success 要同时考虑 yansh 内部结果

yansh 的质量门/task_complete 报告的 success 是更准确的信号，runner 应与它联动：
`success = pytest_pass AND yansh_internal_pass`

### 4. Prompt 质量是第一道防线

task21 三轮迭代后，最终解决方案是改 prompt——这说明好的 prompt 比复杂的 pipeline 保护机制更有效。先把 prompt 写清楚，再加 pipeline 安全网。

## 关键观察

### task17：迭代器失效 bug 被正确识别

注入的 bug：`emit()` 直接迭代 `self._handlers[event]`，不复制列表。  
handler 内调用 `off()` 时修改了被迭代的列表，导致后续 handler 被跳过。

yansh 的修复：
```python
snapshot = list(handlers)  # 浅拷贝快照，防止迭代中 off() 修改原列表导致跳位
for handler in snapshot:
    handler(*args, **kwargs)
return len(snapshot)  # 返回触发前的 handler 数
```
定位精准，甚至连 return 的语义（触发前 count 而非触发后 count）也正确理解。

### task18：通配符扩展只改了 emitter.py

files_modified 只有 `eventsys/emitter.py`，没有新建测试文件——说明 yansh 把新测试追加到了现有 test_emitter.py。这是正确的代码风格判断。

### task20：可观测性需求模糊，yansh 设计自洽

只改了 `eventsys/emitter.py`，没有创建新文件或修改 bus.py，说明 yansh 选择了"在 EventEmitter 上直接加 emit_count 方法"这一最小化设计，没有过度设计。pattern 5 生效——没有出现数值断言写错的问题。

### CC task17：只加了 list() 没写测试

CC 的 files_modified 里没有 `eventsys/emitter.py`（只有 `test_emitter.py`），说明 CC 是通过**修改测试**来让测试通过，而不是修复实现。这是一个有趣的发现：CC 在 bug fix 场景下有时会选择"改测试适配现有实现"而非"修复实现"。

## 经验积累

1. **非主场泛化能力已验证**：yansh 在两个完全陌生的项目（strkit / eventsys）上稳定通过，不依赖对 yansh-code 本身的了解。

2. **pattern 5 有效**：task20 需求模糊 + 可观测性查询，yansh 直接通过，没有出现 task15 第一轮的数值断言写错问题。

3. **yansh 的"按需生长"策略持续奏效**：每次 AB test 暴露盲点 → 加 pattern → 立即验证有效。task1-20 共积累的 pattern 数量和质量是 yansh 竞争力的核心。

4. **CC 费用构成分析**：CC 在所有 task 上 tokens 都在 600K-900K 量级，yansh 在 30K-350K。差距主要来自：
   - CC 系统提示本身体量大（出厂覆盖所有场景）
   - CC 不走捷径（每个 task 都做完整的探索-实现-验证循环）
   - yansh simple-fast 路径跳过 plan()，直接进 coder，对简单任务有显著节省

# P2 #12 跨 Session 持久记忆

承接 [_21](./2026-05-22_21-hooks.md)：Hooks 完成后做 #12——这一波**收官**整个 ROADMAP。
跟 Claude Code 内置 memory 系统同款架构（就是我现在写笔记用的那个 system）。

## 目标

让 yansh 跨会话沉淀事实——用户偏好 / 项目背景 / 反馈 / 外部资源——
下次启动仍能调取，不用每次重头解释。

## 改了什么

### 1) memory.py 新模块

#### 数据模型

```python
@dataclass
class Memory:
    name: str               # kebab-case slug，唯一标识
    description: str        # 一行索引（决定下次调取相关性）
    type: str               # user | feedback | project | reference
    body: str               # markdown 主体
    scope: str              # project | global
    source_path: Optional[str]
```

#### 双路径存储（对齐 mcp / hooks）

```
<workspace>/.yansh/memory/<slug>.md      项目级（跟代码库走、可提交）
<workspace>/.yansh/memory/MEMORY.md      项目级索引
~/.yansh/memory/<slug>.md                全局（跨项目、用户偏好）
~/.yansh/memory/MEMORY.md                全局索引
```

同 slug 时**项目级覆盖全局**——跟 skills / mcp 一致。

#### 4 种 type 对齐 Claude Code

- `user` ：用户是谁、用户偏好（"用 vim"、"前端 React"）
- `feedback` ：用户反馈如何工作（"不要写测试除非我说"）。约定 body 末尾带 `Why:` / `How to apply:`
- `project` ：项目背景 / 关键决策（"用 pytest 不用 unittest"）
- `reference` ：外部资源（API 文档 URL、内部 Confluence 链接）

#### API

```python
parse_memory_file(path, scope) -> Optional[Memory]   # 含嵌套 metadata.type 的 frontmatter 解析
discover_memories(workspace_dir) -> list             # 双路径扫描，项目覆盖全局
find_memory(name, workspace_dir) -> Optional[Memory] # 按 name 找一条
save_memory(name, type, description, body, scope, workspace_dir) -> dict
delete_memory(name, scope, workspace_dir) -> dict
load_memory_index(workspace_dir) -> str              # 拼好两个 MEMORY.md → system prompt 注入
list_all(workspace_dir) -> list                       # /memory list 用
```

#### MEMORY.md 索引自动维护

每次 save / delete 后调 `_update_index(target_dir, scope, ws)` 重建对应目录的
MEMORY.md：每行一条 `- [type] name — description`。
load_memory_index 把两个目录的 MEMORY.md 拼起来 + 加调用提示，作为
system prompt 注入。

### 2) tools.py / tools_schema.py 加 2 工具

- **save_memory(name, type, description, body, scope='project')** ：LLM 主动调
- **recall_memory(name)** ：按 name 读完整内容

加进 `READONLY_TOOL_NAMES` ——save 写的是 `.yansh/memory/`，不是 workspace 代码，
audit / explorer 子 agent 都该能写（比如 audit 跑出"项目用 pytest"自然该沉淀）。

schema 的 description 关键引导：
- save_memory：写**何时主动调** + **何时不要写**清单（避免每次都写）
- recall_memory："system prompt 里只给索引，看到相关索引调这个"

### 3) agent.py 集成

- 模块级 `_ACTIVE_MEMORY_INDEX: str = ""` 跟 `_ACTIVE_SKILLS_PROMPT` 平行
- `_run()` 入口加载 MEMORY 索引
- 5 个 system prompt 注入点都加上 `_ACTIVE_MEMORY_INDEX`：plan / code（已存在 / 新建两路径） / audit / fix（review_rejection / test_failure 两路径）
- plan_chat() 独立扫一次（跟 skills 同处理）
- `_build_subagent_system_prompt` 也加索引——子 agent 能看到 + 通过 READONLY 白名单也能 save/recall

### 4) main.py 命令

```
/memory list                  按 scope 分组列所有 memory
/memory show <name>           显示完整内容（项目级优先）
/memory delete <name>         删除（先项目级、后全局）
```

### 学到什么

- **"LLM 主动调"vs"用户显式存"**：让 LLM 自己判断什么值得 memory 是关键的——schema description 写清楚 What/When/When-not 让 LLM 形成稳定的判断模式。**最关键的一行：在 description 里写"何时不要写"**——光说要写不说不要写，LLM 会写一堆没用的。
- **索引/详情的两层结构**：把"索引"（短描述）和"详情"（完整 body）拆开是经典 token 预算优化——索引每次都注入（每条 ~50 token）但详情按需 read（每条 ~500 token）。100 条 memory 索引 ~5k token，全注入要 ~50k——10× 节省。
- **type 系统的价值**：不同 type 在 LLM 眼里有不同语义——`user` 不会被覆盖、`feedback` 强调"why"、`project` 跟着代码库走、`reference` 是外部链接。这套分类直接决定 LLM 怎么用。
- **"跨 Session"的关键检验**：必须用**新 Python 进程**测——同进程跑两次只能证明"内存里能存"，不能证明"重启不丢"。

## 不做（留给后续）

- `[[memory-name]]` 跨引用解析
- LLM 智能调取（不靠索引文字直接 fuzzy 选 memory，复用 P2 #8 LLM skill 选择思路）
- memory 反向索引（哪些任务读过这条 memory，用于评估 memory 价值）
- memory 自动过期（90 天没被 recall 过的提示用户清理）
- memory 合并（重复主题自动合并）
- 安全标记（"不要把这条 memory 给 MCP server 看到" 反 prompt injection）

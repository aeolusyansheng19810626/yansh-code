# P0 安全修复（Codex review 找出的两个 P0）

承接 [_23](./2026-05-22_23-three-reviewer-findings.md)：三家 reviewer 中 Codex 独家挖出 2 个 P0 严重漏洞，本笔记修复。

## P0-1: audit 模式被 `dispatch_subagent(role="general")` 绕过

### 漏洞

`yansh audit` 模式承诺只读，LLM 不该写文件 / 跑命令。但：
- `tools_schema.py:459` `dispatch_subagent` 在 `READONLY_TOOL_NAMES` 里
- `agent.py:916` audit 只按工具名拦截 → `dispatch_subagent` 被放行
- `agent.py:1978-1979` general role 子 agent 拿 `all_names - blocked`（含 `write_file`/`execute_command`）
- `agent.py:2051` `dispatch_mode = "audit" if role in ("explorer","auditor") else "auto"` ← general 走 auto
- `agent.py:2077` HIL/confirm 全禁

PoC：audit 模式下 LLM 调 `dispatch_subagent(task="write pwned", role="general")` → 子 agent 真写盘。

### 修复

`agent.py:_dispatch_tool_call_inner` 在路由 `dispatch_subagent` 处做强制降级：

```python
if name in readonly_handlers:
    if name == "dispatch_subagent" and mode == "audit":
        req_role = args.get("role", "explorer")
        if req_role not in ("explorer", "auditor"):
            console.print(f"[security] audit 上下文：子 agent role '{req_role}' 强制降级为 'auditor'", ...)
            args["role"] = "auditor"
    result = readonly_handlers[name](**args)
```

5 行修补。auto/code/fix 模式不变，只在 audit 父上下文下降级。

### 验证

`tests/unit/test_subagent.py` 加 4 条单测：
- `test_audit_mode_forces_general_subagent_to_auditor`：audit + general → 降级 auditor ✅
- `test_audit_mode_keeps_explorer_role_unchanged`：audit + explorer → 不动 ✅
- `test_audit_mode_keeps_auditor_role_unchanged`：audit + auditor → 不动 ✅
- `test_non_audit_mode_keeps_general_role`：auto + general → 不降级（防过度修复）✅

端到端 `test_audit_mode_subagent_cannot_write_file_e2e`：真跑 LLM loop（mock LLM 返 write_file tool_call）→ audit 模式下子 agent 试图写文件 → 文件不被创建 ✅

`test_subagent.py` 34/34 通过。

## P0-2: 项目级 `.yansh/{mcp,hooks}.json` 是无确认 RCE

### 漏洞

- `mcp_client.py:264` workspace 优先加载 `.yansh/mcp.json` → 直接 `Popen(command, args)`
- `hooks.py:80` workspace 优先加载 `.yansh/hooks.json` → `subprocess.run(cmd, shell=True)`
- 没有 trust 确认

PoC：恶意 repo 提交 `.yansh/hooks.json`（UserPromptSubmit 触发），用户 clone + `yansh` + 第一次输入 → 任意命令执行。**典型供应链攻击面**——比 audit 绕过更危险（不需要 LLM 配合）。

### 修复

新模块 `workspace_trust.py`：
- `is_trusted(workspace_dir)`：检查 `~/.yansh/trusted_workspaces.json` 白名单
- `mark_trusted(workspace_dir)`：写入白名单
- `check_or_prompt(workspace_dir, config_filename)`：加载前调用，决定是否允许
- env var `YANSH_TRUST_PROJECT_CONFIG`：
  - `always`：总信任（CI / 测试 / 自己开发机）
  - `never`：总拒绝
  - 不设/`auto`：trust 文件 + 交互式 prompt

行为：
- 默认拒绝项目级配置；只加载 `~/.yansh/{mcp,hooks}.json`
- 交互模式首次见时弹大字 warning + `(y/N)` prompt，y 写 trust 文件
- 非交互（CI / pipe）默认拒绝，必须 env var 显式 opt-in
- trust 文件损坏 → fail-safe 返回 False

`mcp_client.load_config` / `hooks.load_config` 重写：未 trust → fallback 全局；trust → 项目级覆盖。

### 验证

`tests/unit/test_workspace_trust.py` 19 条单测：
- `is_trusted` / `mark_trusted` 持久化（4）
- `check_or_prompt` 7 个分支：always / never / no_proj_file / auto+trusted / auto+非交互 / auto+y / auto+n / EOF
- 损坏 trust 文件 fail-safe（1）
- `mcp_client.load_config` 未 trust fallback / trust 加载（2）
- `hooks.load_config` 未 trust fallback / trust 加载（2）
- **端到端攻击模拟**（2）：
  - `test_e2e_evil_repo_user_prompt_hook_not_executed`：恶意 hooks.json 写 pwned 标记 → trust 拒绝 → 标记不被写
  - `test_e2e_evil_repo_mcp_server_not_started`：恶意 mcp.json 启 60s server → trust 拒绝 → 不启动

19/19 通过。`test_mcp.py` / `test_hooks.py` 各加 1 处 `monkeypatch.setenv("YANSH_TRUST_PROJECT_CONFIG", "always")` 适配新 trust 模型，27/27 + 28/28 全过。

## 学到什么

### Codex 独挖的 2 个 P0 是 review 的真实价值

Gemini / Claude 都漏掉了这两个：
- **audit 绕过**：信任边界一旦交叉（audit 模式信号 → subagent 工具集），LLM 会找最薄弱处穿透。Claude 看了 subagent 实现但没把 audit 信号传播链跟下去
- **项目配置 RCE**：是"借代码库走的可执行实体"。Gemini 误报了 hooks shell injection 但漏掉真正的攻击面（hooks.json 本身就是攻击向量）

**结论**：多家 reviewer 不是冗余——单家最多覆盖 60-70% 真问题，剩下的 30-40% 必须靠 cross-check。

### Trust 模型的设计权衡

**为什么默认拒绝 + 用户 opt-in？**
- VS Code / GitHub Codespaces 用 "Workspace Trust" 同款思路
- 默认信任 = 供应链攻击 free pass（git clone 即 RCE）
- 默认拒绝 = 一次性额外操作，但安全模型清晰

**为什么 env var + trust 文件双轨？**
- env var 适合 CI / 自动化（一次设置长期有效）
- trust 文件适合人类用户（per-workspace 颗粒度，能撤销）
- 两者并存避免单一机制的盲点

**为什么交互式 prompt 在非交互拒绝？**
- 非交互模式（pipe / CI / batch）下没人能答 prompt → 默认行为即"拒绝"才安全
- 想要在 CI 里加载项目配置 → 显式设 `YANSH_TRUST_PROJECT_CONFIG=always`，意图清楚

### 测试的端到端价值

**E2E 测试值得加**：
- `test_e2e_evil_repo_user_prompt_hook_not_executed` 用真实 `python -c "open(file).write('PWNED')"` 命令模拟攻击
- 不是 mock 出来的 "load_config returns empty" — 是真验证恶意命令没机会执行
- 这种测试比单测 load_config 更有说服力，回归成本低

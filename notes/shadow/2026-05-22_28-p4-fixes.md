## P4-1: 抽 `frontmatter.py` 共用

### 动机

`skills.py` 和 `memory.py` 各写一份 YAML frontmatter 解析（含 `[list]` 语法 vs `metadata:` 嵌套），行为已不一致。Gemini / Claude 都点出这是漂移源。

### 修复

新模块 `frontmatter.py` 提供 `parse(text) -> (meta, body)`，统一支持：
- 标量 `key: value`（去引号）
- 列表 `key: [a, b, "c d"]`（引号内逗号不切）
- 一级嵌套 `metadata:\n  type: x` → `meta["metadata"] = {"type": "x"}`

skills/memory 各 50+ 行解析码删掉，换成 `from frontmatter import parse as _parse_frontmatter`。

## P4-3: `state.Session` 镜像 `_ACTIVE_*` / `_SUBAGENT_STATS`

### 漏洞

`_ACTIVE_SKILLS_PROMPT` / `_ACTIVE_MEMORY_INDEX` / `_SUBAGENT_STATS` 没进 `Session.pull/push/reset` → 单测互相污染：
- `test_A` 加载 memory 索引 → `test_B` 看到（即便 `scoped_session(tmp_path)` 也兜不住）
- `test_subagent_stats_updated` 累计 → 下个 test 看到旧值（之前是用 `n_before = stats["calls"]` 兜底，模式不优雅）

### 修复

- `active_memory_index: str = ""`

`push` 时 `_SUBAGENT_STATS.clear() + update()`（**不替换引用**——别处持有的 dict reference 不过期）。

### 验证

## P4-4: general subagent summary 追加修改文件清单

### 漏洞（Gemini 独家）

并发 subagent 中 `role=general` 的子 agent 改了文件 → 父 agent 的 `conversation_history` 不含这些 tool_call 记录。父 agent 后续基于旧 context 生成代码 → **Lost Update Race**。

### 修复

`_run_subagent` 内本地 `files_modified_locally` list，每次 dispatch 后扫描 `outs`：
- `out["name"] in _WRITE_TOOLS` 且 `"success" in result` → 记 `args` 里的 filename / file_path
- 跑完后 `role=="general"` 且有改动 → summary 末尾追加：
```
[系统提示] 此子任务修改了文件: X, Y；父 agent 后续操作前请重新 read_file 这些文件以刷新认知...
```

`_WRITE_TOOLS` 包含：write_file / replace_in_file / apply_patch / replace_symbol / append_to_file / delete_file / move_file。

### 设计权衡

**为什么不用 `task_log` 的 `_task_files_modified` snapshot diff？**
并发 subagent 之间会互相污染——A 跑时 B 也在 append，A 的 diff 含 B 的文件。本地 `files_modified_locally` 是 _run_subagent 的局部变量，天然 thread-safe。

**为什么只加 `general` role？**
`explorer` / `auditor` 走 `dispatch_mode="audit"` 工具集，`write_file` 等会在 inner dispatch 处被拦截——不可能实际改文件。即便记下来也没意义，反而误导父 agent。

### 验证

`tests/unit/test_subagent.py` +3 条：
- `test_general_subagent_summary_lists_modified_files`：写 2 个文件 → summary 含 `[系统提示]` + 文件名 + "重新读取" 字样
- `test_explorer_subagent_summary_no_files_addendum`：explorer role 即使尝试也不该有提示
- `test_general_subagent_no_files_modified_no_addendum`：general role 但只 read 没 write → 不加

`test_subagent.py` 35 → 38 全过。

## P4-5: 拆 `subagent.py`（agent.py 瘦身）

### 动机

`agent.py` 2859 行——三家 reviewer 都说"该拆"。优先拆 subagent 因为最独立：`_run_subagent` 的局部状态（`_subagent_state`、`_SUBAGENT_STATS`、`_IN_SUBAGENT`）跟 agent.py 主流程没耦合。

### 修复

新建 `subagent.py`（296 行），从 agent.py 搬出：
- 状态：`_subagent_state` / `_SUBAGENT_STATS` / `_SUBAGENT_STATS_LOCK` / `_SUBAGENT_HARD_CAP` / `_SUBAGENT_CONCURRENCY_CAP`
- 函数：`_is_in_subagent` / `_set_in_subagent` / `_subagent_tools_for_role` / `_build_subagent_system_prompt` / `_run_subagent` / `_subagent_handler` / `get_subagent_stats`
- 常量：`_SUBAGENT_ROLE` prompt 字符串

### 设计权衡：lazy import 解循环依赖

subagent.py 顶层只依赖标准库 + `tools_schema`（无 agent.py）。`_run_subagent` 内的 `agent._dispatch_tool_calls` / `call_llm` 等通过函数体内 lazy import 拿：
```python
def _run_subagent(...):
    import agent as _a
    import interrupt
    from llm_client import call_llm
    ...
```

agent.py 顶部 `from subagent import (_run_subagent, ...)` re-export——既有 caller / state.Session / tests 一行不改。

**`_SUBAGENT_STATS` 是同一个 dict 对象**（agent._SUBAGENT_STATS is subagent._SUBAGENT_STATS）——既不破坏 state.Session 的 `getattr(_a, "_SUBAGENT_STATS")` 访问、也不破坏 in-place mutation。

### 实施细节

agent.py 改动：
1. 顶部加两段 `from subagent import (...)`（13 个名字）
2. **删除** 原 _run_subagent / _build_subagent_system_prompt / _subagent_tools_for_role / _subagent_handler / get_subagent_stats / _SUBAGENT_ROLE / 状态常量定义（共 181 行）

agent.py: 2859 → 2681（**减 178 行**，3 行净增是新增的 import 块）。

## 学到什么

### 1. 拆模块不一定缩总行数

agent.py 2859 → 2681（减 178 行），但 subagent.py 新增 296 行（含 docstring / import / 类型注解）。**总行数从 2859 → 2977**（实际还多了一些）。

值的不是"少代码"，是"少耦合"：agent.py 的核心流程 plan/code/audit/fix 现在不再夹杂 subagent loop 实现细节。后续给子 agent 加 token budget / per-subagent log 在 subagent.py 内做，不会污染主流程。

### 2. lazy import 是循环依赖的实用解

完美方案：subagent 接受 callbacks 注入（call_llm / dispatch / config 等）。但改造面大，且现实中"agent 用 subagent / subagent 也调 agent helper" 是真的双向依赖。

务实方案：subagent.py 顶层无 agent，函数体内 `import agent`。Python import 系统支持这种模式：
1. import agent → 顶部 `from subagent import ...` → import subagent
2. subagent.py 顶层执行完成（不需要 agent 已加载）
3. agent.py 顶部 import 完成
4. 之后任何调用进 _run_subagent → `import agent` 已是 cached module

零 runtime 开销（import cache），破除循环。

### 3. dict 引用 vs 替换的细节

`Session.push` 写回 `_SUBAGENT_STATS` 用 `clear() + update()`，**不是 `agent._SUBAGENT_STATS = self.subagent_stats`**。后者会让 agent.py 和 subagent.py 持有不同对象——之前 `with _SUBAGENT_STATS_LOCK: _SUBAGENT_STATS["calls"] += 1` 改的是旧引用，state.Session 看不到。

**经验**：跨模块共享可变容器（dict / list / set），永远 in-place 改而非替换引用。否则 alias 会断开。

### 4. "改文件后告诉父 agent" 不只是"加日志"

Gemini 提的看起来很小（summary 加一行），但属于**信息系统设计**问题：父 agent 的 conversation_history 是它对世界的认知模型——子 agent 改了文件而父 agent 不知，模型与现实就不一致，后续生成的代码都基于错误前提。

`[系统提示]` 这行加在 summary 末尾，强迫父 agent 在下一轮把这些文件重新 read_file。这是"用消息让 LLM 跟现实重新同步"——本质上是 LLM agent 设计中的 cache invalidation 模式。

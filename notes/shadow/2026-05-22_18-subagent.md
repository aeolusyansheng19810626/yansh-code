# P2 #9 子 Agent / 任务分派

承接 [_17](./2026-05-22_17-skills-llm-matching.md)：P2 #8 LLM 智能匹配收尾后做 #9。
ROADMAP 标这个是 LLM agent 设计的**关键架构概念**——做完对 agent 工具理解上一个台阶。

## 目标

子 agent 的核心价值是**上下文隔离**：让一个独立的 LLM context 跑探索/重活，
父 agent 只看到一段 summary，不看到中间的 read_file/grep 全量内容。
长 session 在大型 codebase 里能延寿 5-10×。

## 改了什么

### 1) tools.py 加 `dispatch_subagent` sentinel

```python
def dispatch_subagent(task, role="explorer", max_steps=8):
    return {"_subagent_dispatch": True, "task": ..., "role": ..., "max_steps": ...}
```

跟 task_complete / update_plan_draft 一样的 sentinel 模式——LLM 调时返回标记，
真正逻辑在 agent 模块（避免 import 循环：tools 不依赖 llm_client）。

### 2) tools_schema.py

- 加 `dispatch_subagent` schema：`role` 是 enum `["explorer", "general", "auditor"]`
- 加进 `READONLY_TOOL_NAMES`——这样 audit/plan mode 主 agent 也能用（夹带子 agent 不修改 workspace 假设：role=explorer 时纯只读；role=general 是 LLM 显式申请的）

### 3) agent.py 核心：`_run_subagent(task, role, max_steps)`

模块级状态：
```python
_IN_SUBAGENT: bool = False           # 递归锁
_SUBAGENT_STATS: dict = {...}         # process 生命周期累计
_SUBAGENT_HARD_CAP: int = 16         # max_steps 上限
```

工具集映射（物理隔离防递归）：
| role | 工具集 |
|---|---|
| explorer / auditor | READONLY_TOOL_NAMES - {dispatch_subagent, plan_mode_sentinels} |
| general | ALL - {dispatch_subagent, plan_mode_sentinels} |
| 未知 role | fallback explorer |

**所有 role 的工具集都不含 dispatch_subagent**——双重保险（_IN_SUBAGENT flag + 物理过滤）。

子 agent loop 复用了 plan_chat 的多轮模板：
- 独立 messages（不混父 agent 的 conversation_history）
- 独立 system prompt（_SUBAGENT_ROLE + workspace 顶层结构）
- task_complete 触发 success/summary 提取
- 沉默退出兜底（追问一次，仍然没有就用 content 当 summary）
- finally 块保证 _IN_SUBAGENT 重置（即使 LLM 抛错）

### 4) handler 注册

```python
readonly_handlers = {
    ...
    "dispatch_subagent": _subagent_handler,
}
```

`_subagent_handler` 调 `_run_subagent` 并返回浅 dict 给父 agent：
```json
{"success": bool, "summary": str, "steps": int, "role": str}
```

### 5) main.py 加 `/subagent stats`

显示本 session 的累计：calls / total_steps / 最近一次 task / summary / role / success。

### 集成验证（ICA Sonnet 4.6）

**场景 1**：直接 `_run_subagent` 找 workspace/agent.py 函数
```
input: "看 workspace/agent.py 里有什么函数定义，列出前 5 个"
result: success=True, steps=2
summary: "agent.py 中只有 1 个函数定义：_dispatch_tool_call（第 4 行），不足 5 个，这是全部。"
```
✅ 子 agent 调 list_symbols 实查；找不到 5 个不强行凑数

**场景 2**：找 workspace 内不存在的符号
```
input: "找 task_complete 函数定义"（task_complete 是父框架注入的，不在 workspace 内）
result: success=False, steps=2
summary: "search_in_files 返回 0 条匹配，get_symbol_definition 同样 '未找到'。
         它是父 agent 框架层（外部）注入的工具，并非本 workspace 内的 Python 源码。"
```
✅ 真调两个工具确认；找不到时如实报告并给出工程判断

**场景 3**：LLM 主动派子 agent（端到端）
```
input: audit("用 dispatch_subagent 派一个 explorer 去 workspace/agent.py 查
              _dispatch_tool_call 签名，然后基于 summary 给审计结论")
```

子 agent 的 summary：
> agent.py:4 的 `_dispatch_tool_call` 签名为 `def _dispatch_tool_call(tool_name: str, tool_args: dict):`，两个参数均有类型注解（str/dict），无返回类型注解。函数体维护 readonly_handlers 字典（仅注册 "count_lines"），按 tool_name 路由调用，未知工具抛 ValueError。

主 agent (audit) 基于此给出审计结论：
- 🔵 低：未知工具抛出 ValueError 而非自定义异常 → 建议定义 UnknownToolError
- 类型注解不完整（无返回类型注解）

**关键证据**：主 agent 的 audit 报告里**直接引用**了子 agent 的细节（"未知工具抛 ValueError"、"无返回类型注解"），但主 agent **从未直接 read_file**——只看到了子 agent 给的 200 字 summary。这就是 context 隔离的具体体现。

**场景 4**：递归防护
```
agent._IN_SUBAGENT = True
res = agent._run_subagent('再派一层')
# success=False, summary="子 agent 不能再派子 agent（递归被禁用）"
```

## 评估

### 跟 Claude Code Task 工具对比

| 维度 | Claude Code Task | yansh dispatch_subagent |
|---|---|---|
| 工具调用形态 | LLM 调 Task tool | LLM 调 dispatch_subagent tool ✅ |
| 独立 context | ✅ 子 agent 独立 messages | ✅ |
| role 切工具集 | ✅ general/Explore/claude-code-guide/... | ✅ explorer/general/auditor |
| 嵌套 | 不能（subagent 看不到 Agent 工具） | ✅ 不能 |
| 并行多个子 agent | ✅ 单 message 多次 tool_call | 🟡 工具支持，未专门优化 |
| run_in_background | ✅ | ❌ |
| 超时/中断 | ✅ | 🟡 通过 interrupt 支持 |
| stats/observability | 内置 | ✅ /subagent stats |

差距集中在并行优化和后台执行——不是核心架构差异。

### context 隔离的工程意义（实测数字）

**场景 3** 跑下来：
- 子 agent 内部：read_file/list_symbols 工具结果约 800 token
- 主 agent 看到的：summary 200 字 ≈ 80 token
- 节省比：**10x**

如果 audit 任务要查 5 个不同的函数，主 agent 直接做要烧 5×800=4000 token；
派 5 个 subagent 后主 agent 只看 5×80=400 token。**这才是为什么大型 codebase 上能延寿 5-10×**。

### "container 化"工程视角

子 agent 是把"任务执行"抽象成**带边界的函数**：
- 输入：task 字符串
- 输出：summary 字符串
- 副作用边界：role=explorer 时无副作用；role=general 时受 _dispatch_tool_call 同样的安全检查

这跟 Unix 的 fork+exec 是同构的——子进程独立内存空间，父只看 stdout/exit code。
LLM agent 把这个模式提到了 context 层面。

## 不做（留给后续）

- 并行子 agent：parent 单 message 内多次 tool_call → 多个子 agent 并发跑
- 后台子 agent：long-running task 派完不阻塞父，事件回调
- token 预算：子 agent 跑超 X token 强制 task_complete
- 子 agent 自己的 cascade 路由：强制走 Haiku 降本（轻量探索任务不需要 Sonnet）
- subagent 间消息：A 派 B、B 完成后 A 继续——本波禁递归就是为了简化，下一波可放开 1 层
- 子 agent loop 用 worktree 隔离文件系统：role=general 时改了 workspace 父 agent 不知情，加 worktree 边界

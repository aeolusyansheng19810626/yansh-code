## 测试项目：eventsys（事件系统库）

### 项目结构

```
eventsys/
├── eventsys/
│   ├── __init__.py
│   ├── emitter.py    # EventEmitter：on/off/emit 核心实现
│   └── bus.py        # EventBus：全局单例，转发到内部 EventEmitter
├── tests/
│   └── unit/
│       ├── test_emitter.py
│       └── test_bus.py
└── pyproject.toml
```

### 核心设计

`EventEmitter`：
- `on(event, handler)` — 注册处理器
- `off(event, handler)` — 移除处理器
- `emit(event, *args, **kwargs) -> int` — 触发事件，返回调用次数

`EventBus`：全局单例，包装 `EventEmitter`，暴露同名接口

### 注意

base 代码写**正确版本**（无 bug，无 `once`，无 wildcards，无 priority，无 metrics）。
task17 workspace 在 base 基础上**手动注入 bug**（emit 不复制 handlers 列表）。

## Task 16（中等）— 新功能：once() 方法

**类型**：新功能，有明确 spec

**Prompt**：
```
给 eventsys 的 EventEmitter 添加 once(event, handler) 方法：
处理器只触发一次，触发后自动移除。
加 3 个单测：once 只触发一次 / on 不受影响 / 多个 once 各自只触发一次。
```

**预期改动文件**：`eventsys/emitter.py`、`tests/unit/test_emitter.py`

**难点**：需要在 emit 内部或 wrapper 层做自动移除，理解"触发时移除 vs 注册时包装"两种实现路径的区别

**成功标准**：test_result=pass，emitter.py 修改，新增 3 个单测

## Task 17（中等）— bug fix：handler 内调用 off() 导致跳过后续 handler

**类型**：并发/迭代器失效 bug，无 failing test 引导

**注入 bug**：`emit()` 直接迭代 `self._handlers[event]`，不复制列表

**Prompt**：
```
eventsys 的 EventEmitter 有一个 bug：
当一个 handler 在被调用时通过 off() 移除自身（或其他 handler），
后续的 handler 可能被跳过或触发次数不对。
示例：注册 handler_a 和 handler_b，handler_a 执行时调用 off('click', handler_a)，
handler_b 应该还是被调用，但实际上被跳过了。
定位根因，修复，加 2 个单测：handler 内调用 off(self) 不影响其他 handler /
emit 返回值等于注册时的 handler 数。
```

**预期改动文件**：`eventsys/emitter.py`、`tests/unit/test_emitter.py`

**难点**：需理解 Python list 迭代时修改的行为；根因是"迭代器失效"而非逻辑错误

**成功标准**：test_result=pass，emit() 用 list 副本迭代

## Task 18（中等）— 新功能：通配符事件匹配

**类型**：新功能，需理解现有 emit/on 流程后才能正确扩展

**Prompt**：
```
给 eventsys 的 EventEmitter 添加通配符支持：
on('user.*', handler) 能匹配 emit('user.login')、emit('user.logout') 等。
匹配规则用 fnmatch（Python 标准库），* 匹配单段，** 不需要支持。
已有的精确事件名不受影响。
加 4 个单测：精确匹配仍正常 / 通配符匹配多个事件 / 不匹配的不触发 / 精确+通配符共存。
```

**预期改动文件**：`eventsys/emitter.py`、`tests/unit/test_emitter.py`

**难点**：需在 `emit()` 里同时查精确匹配和通配符匹配，两路 handler 合并后去重；
理解 `fnmatch.fnmatch` 的语义

**成功标准**：test_result=pass，现有测试全部通过

## Task 19（中高）— 新功能：handler 优先级

**类型**：跨文件新功能，改变 handler 执行顺序

**Prompt**：
```
给 eventsys 的 EventEmitter 添加 handler 优先级支持：
on(event, handler, priority=0)，数字越小优先级越高，同优先级按注册顺序执行。
off(event, handler) 不需要指定 priority，按 handler 引用删除即可。
EventBus 的 on/off/emit 接口也要同步支持 priority 参数。
加 4 个单测：高优先级先执行 / 同优先级按注册顺序 / 默认 priority=0 / EventBus 透传。
```

**预期改动文件**：`eventsys/emitter.py`、`eventsys/bus.py`、`tests/unit/test_emitter.py`

**难点**：内部数据结构从 `list[callable]` 改为 `list[(priority, callable)]`；
`off()` 要按 handler 引用找，不能依赖 priority；bus.py 接口同步

**成功标准**：test_result=pass，emitter.py + bus.py 都有改动

## Task 20（中高）— 需求模糊：可观测性

**类型**：spec 留白，需设计决策（类似 task10/task15）

**Prompt**：
```
eventsys 的 EventEmitter 目前是黑盒：无法知道某个事件被触发了多少次、
有多少 handler 在监听、最后一次触发是什么时候。

给 EventEmitter 添加可观测性支持，让调用方能查到这些信息。
具体接口形式自行设计，但要满足：
- 能查询某个事件的触发次数
- 能查询某个事件当前的 handler 数量
- 加单测覆盖上述两个查询
```

**预期改动文件**：`eventsys/emitter.py`、`tests/unit/test_emitter.py`

**难点**：返回形式完全由 LLM 决定（方法 vs 属性 vs 独立 stats 对象）；
需决定是否统计 off() 后的 handler 数量变化；数值断言需要 execute_command 验证（pattern 5）

**成功标准**：test_result=pass，至少 2 个新查询接口，2 个单测

# P2 #11 Hooks 系统

承接 [_20](./2026-05-22_20-mcp.md)：MCP 完成后做 #11。让用户用 shell 命令 hook 进
yansh 关键事件——对齐 Claude Code 的 settings.json hooks。

## 目标

4 个事件 + block/modify 二种动作 + shell stdin/stdout JSON 协议。
最常见用例：自动 prettier 写完后跑 / 删敏感文件前拦 / 用户输入提交后加上下文。

## 改了什么

### 1) hooks.py 新文件

#### 协议

事件 4 种：`PreToolUse / PostToolUse / UserPromptSubmit / Stop`

Hook 子进程协议（stdin/stdout JSON）：
```
stdin  ← {"event": "...", "tool_name": "...", "tool_input": {...},
          "tool_output": {...}, "user_input": "...", "task_summary": "...", "cwd": "..."}
stdout → {}                                              空 / 无输出 = allow
       → {"decision": "block", "reason": "..."}          阻止
       → {"modify": {"tool_input": {...}}}               改输入
       → {"modify": {"tool_output": {...}}}              改输出
       → {"system_message": "..."}                        给 LLM 加 context
```

#### `run_hook_event(event, payload, match_target, workspace_dir)` 聚合规则

- 多个匹配的 hook 串行跑（按配置顺序）
- 任意一个 block → 整体 block，**剩余 hook 不跑（短路）**
- modify 链式累积：第二个 hook 看到第一个改后的 payload
- system_message 全部收集
- 单个 hook 失败/超时 → 进 errors 列表，不影响整体决策（保守 allow）

#### 超时杀进程树（Windows 关键修复）

最初用 `subprocess.run(..., timeout=)` 在 Windows + shell=True 下会留孙进程：
shell（cmd.exe）被 kill 但孙进程（python sleep）继续跑，wait 也卡住。
改成 `Popen` + 超时后用 `taskkill /F /T /PID`（Windows）/ `os.killpg(SIGKILL)`（POSIX）
杀整个进程树。测试证明 `timeout=1` 现在真的 1 秒后退出。

### 2) agent.py 集成 4 触发点

**PreToolUse / PostToolUse**（在 `_dispatch_tool_call` 内）

把现有 `_dispatch_tool_call` 拆成两层：
- `_dispatch_tool_call_with_hooks`（外层）：跑 PreToolUse → 调内层 → 跑 PostToolUse
- `_dispatch_tool_call_inner`（内层）：原有的工具分发逻辑（接受预解析的 args）

PreToolUse 改 args（modify）；PostToolUse 改 result（modify）；任何一个 block 都返回 error 给 LLM。

**UserPromptSubmit**（在 `run()` 入口）：用户输入解析图片/上下文后、调 `_run` 前。
hook 可改 user_input、加 system_message（注入 requirement 头部）、拒绝整个请求。

**Stop**（在 `run()` 出口）：`_run` 返回后、return 前。
任务已结束，hook 主要作用是 system_message——直接打印给用户看（而不是注入下一轮 LLM）。

### 3) 跳过场景

- 子 agent 内部（`_is_in_subagent()`）：父 agent 派工具时已触发 PreToolUse，
  子 agent 不重复触发（避免一个 hook 命令被同一个文件操作触发 N 次）
- 全局禁用（`hooks.set_disabled(True)`）：批处理 --json 模式由 main.py 设置
- 单个 hook 失败：`_run_one_hook` 返回 `_hook_error` → 聚合时进 errors 列表，
  整体仍 allow（不卡死主流程）

### 4) main.py

- 启动时 `--json` 自动 `hooks.set_disabled(True)`
- `/hooks list` 列当前配置（每事件下每条 hook 的 matcher/timeout/command）

### 集成验证（真 hook 跑）

写两个 Python hook 脚本作为外部命令：
- `hook_pre_delete.py`：拦截 delete_file 删 .txt
- `hook_post_read.py`：read_file 输出前加 `[hook 注入: N 行]`

跑 3 个场景：

| 场景 | 输入 | 结果 |
|---|---|---|
| PostToolUse modify read_file | read sample.txt（4 行） | content 前缀 `[hook 注入: 5 行]\n` ✅ |
| PreToolUse block delete .txt | delete_file keep.txt | error: "Hook 阻止 delete_file：禁止删 .txt"，文件还在 ✅ |
| matcher 命中但 hook 放行 .py | delete_file throwaway.py | success: "文件删除成功" ✅ |

**一个 Windows 转义教训**：最初把 hook 命令直接内联到 hooks.json 里
（`python -c "..."`），cmd.exe 转义破坏 \n，整条 hook 静默失败。
**最佳实践**：hook 写成独立脚本文件，hooks.json 里只调 `python script.py`。

### "为什么 hooks 是开放扩展点"

之前要修改 yansh 行为只能改源码：
- 想让所有 write_file 后 prettier？改 agent.py 加调用
- 想拦截 delete .env？改 _dispatch_tool_call 加判断

现在用户在 hooks.json 写一行就行——**用户跟 yansh 维护者解耦**。
yansh 只暴露事件触发点，实现策略让用户决定。

跟 MCP 是镜像关系：
- MCP：扩展**能力**（加新工具）
- Hooks：扩展**策略**（拦截 / 修改既有工具）

两者结合就是"开放架构"——既能加工具又能拦行为。

### 学到什么

- **事件驱动架构嵌入 agent 的关键**：触发点要够"原子"——`_dispatch_tool_call`
  外层包是天然的 Pre/Post 切点。如果触发点太粗（"任务开始/结束"）能做的事就少；
  太细（"每行 LLM token"）开销爆炸。Pre/Post Tool 是黄金粒度。
- **失败容错**：hook 默认 allow 是必须的——一个错误的 hook 配置不能卡死整个 agent。
  用户改坏 hooks.json 还能用 yansh 修。这跟"宁愿不安全也要可用"的取舍恰好相反——
  hook 失败 → 跑工具（保用户能干活）；用户希望反过来需要在 hook 里显式 block。
- **跨平台超时**：subprocess.run + shell=True + timeout 在 Windows 是个坑——
  必须 Popen + 平台特定 kill 整个进程树。POSIX 用 killpg + start_new_session；
  Windows 用 taskkill /F /T /PID + CREATE_NEW_PROCESS_GROUP。

## 不做（留给后续）

- matcher 正则（"write_file|append_to_file"）
- 异步 hook（fire-and-forget；当前都是同步阻塞）
- hook 之间的依赖（"hook A 先跑完 hook B 才跑"）
- hook 优先级（同事件多 hook 的执行顺序当前按配置数组顺序）
- hook 自身可调用 yansh 工具（嵌套）——会引入复杂度
- 在 PostToolUse 的 modify 里改 tool_call 让 LLM 重新发起调用（"自动重试"模式）

## P3-1: hooks timeout 测试改 psutil pid 死亡断言

### 漏洞

`test_run_one_hook_timeout` 当前断言：
```python
assert "_hook_error" in result
assert "超时" in result["_hook_error"]
assert elapsed < 5
```

只验证"主线程 1s 后返回错误"——**没验证进程树真被杀**。如果 `procutil.kill_tree` 实现错误（比如 taskkill 路径写错、psutil 没装），子/孙进程会留下来当孤儿，主线程依然 timeout 返回，测试依然绿。

Claude / Codex 都明确点出：这是"假阳性测试"——CI 绿不代表 kill 真生效。

### 修复

新增 `test_run_one_hook_timeout_kills_process_tree`：
1. hook 命令是 Python 脚本：写自己 PID 到 marker 文件，然后 spawn 一个 Python 孙进程 sleep(60)（孙也写自己 PID 到 marker），自己 sleep(60)
2. timeout=1s 触发后 hook 返回错误
3. 测试读 marker 文件拿到父 + 孙的 PID
4. **psutil.pid_exists(pid) 验证两个 pid 都不存活**
5. 兜底清理（如果断言失败，避免残留进程拖累后续测试）

这是真正的端到端验证——任何 procutil.kill_tree 退化（比如 taskkill /T 失效、psutil.Process 没枚举到孙）都会让测试失败。

保留旧 `test_run_one_hook_timeout` 不动——它验证主线程 1s 内返回的快速 sanity check 仍有价值。

### 验证

新测试通过，hook 套件 30 → 31 全过。

## P3-2: `test_run_subagent_max_steps_clamped_to_hard_cap` 真测 hard cap

### 漏洞

Codex 找出的假阳性：
```python
def fake_llm(msgs, **kw):
    call_count["n"] += 1
    return _mk_resp(content=f"step {call_count['n']}")  # 永不调工具，沉默退出
...
res = agent._run_subagent("永远跑不完的任务", max_steps=999)
assert res["steps"] <= 16
```

第一轮 LLM 就返 content 无 tool_call → 子 agent loop 走"沉默退出兜底"路径，2 步退出。`assert steps <= 16` 永真但**没真撞 cap**。如果未来 `_SUBAGENT_HARD_CAP` 被改成 100，测试不会发现。

### 修复

让 fake LLM 每轮都返 read_file tool_call——绝不沉默退出，loop 必须由 max_steps 兜底：

```python
def fake_llm(msgs, **kw):
    call_count["n"] += 1
    return _mk_resp(tool_calls=[
        ("c" + str(call_count["n"]), "read_file", {"filename": "f.py"})
    ])

res = agent._run_subagent("永远跑不完的任务", max_steps=999)
assert res["steps"] == agent._SUBAGENT_HARD_CAP   # 精确等于
assert call_count["n"] == agent._SUBAGENT_HARD_CAP
```

精确等于（== 而非 ≤）——cap 真生效时步数和 LLM 调用次数都恰好是 16；cap 退化（比如改成 32）会立即被发现。

### 验证

`test_subagent.py` 35/35 全过；新断言强度从"≤ 16 但 ≤ 16 都过"升级为"精确 16，cap 退化即报错"。

## P3-3: GitHub Actions ubuntu-latest matrix

### 漏洞

之前没有 CI 配置——`tests/run_unit.py` 只在我本地 Windows 跑过。子进程管理 / 进程树 kill 有两条路径：
- Windows：`CREATE_NEW_PROCESS_GROUP` + `taskkill /F /T` + psutil
- POSIX：`start_new_session=True` + `os.killpg(SIGKILL)` + psutil

POSIX 路径**0 测试覆盖**——`procutil.kill_tree` 的 `killpg` 分支只在 psutil 没装时才走，但单测都装了 psutil，所以 fallback 永不被测。psutil 路径在 Linux 也跑得通，但 Linux 上 psutil 是否能正确 children(recursive=True) 没真测过。

### 修复

新增 `.github/workflows/unit-tests.yml`：
```yaml
strategy:
  matrix:
    os: [ubuntu-latest, windows-latest]
    python-version: ["3.11"]
```

Linux + Windows 矩阵跑同一份 `tests/run_unit.py`。20 个测试文件含：
- `test_procutil.py`：5 条端到端进程树 kill 测试
- `test_mcp.py`：1 条端到端真起 Python 父子进程 + psutil 验证孙 pid 死亡
- `test_hooks.py`：P3-1 新增 1 条 + 1 条 stdout cap 端到端

这些都会在 Linux 上跑，验证 POSIX 路径 + psutil Linux 行为。

`requirements.txt` / `pyproject.toml` 加 `psutil>=5.9.0`——之前是测试隐式依赖，现在显式。生产代码 `procutil.py` / `mcp_client.py` 已经在用，加进主依赖更准确（之前的 `try: import psutil except ImportError` fallback 仍保留作为不装时的兜底）。

## 学到什么

### "测试覆盖率 ≠ 测试有效"

P3-1 和 P3-2 是同一类问题：测试代码量绿，但没真验证目标行为。两类常见 trap：
1. **Mock 太狠**（P3-2）：fake LLM 走了一条不到目标的快路径，目标行为根本没触发
2. **断言太弱**（P3-1）：`elapsed < 5` 这种"上界断言"在 kill 失效时也成立，没盯到关键不变量

**经验**：写每个测试问自己一遍——"如果我把目标实现改成 no-op，这个测试还会过吗？" 如果会过，测试是假阳性。

### `精确等于` 比 `小于等于` 强

P3-2 把 `assert steps <= 16` 改成 `assert steps == _SUBAGENT_HARD_CAP`。差别看似细——但前者允许任意 ≤ 16 的实现，后者锁定具体语义。**cap 应该刚好用满，不是上界但实际很少触及**——这是 spec，不是实现细节。

### POSIX vs Windows 进程语义差异不要靠"看起来对"

`os.killpg` 在 Linux/macOS 上行为不完全相同（macOS 对 process group leader 的 kill 信号会传给所有组成员，Linux 默认也是；但 setsid 创建的新 session leader 才是 process group leader——`subprocess.Popen(start_new_session=True)` 已经自动 setsid）。

**没在那个平台跑过 = 没测过**——CI matrix 是最低成本的验证。10 行 yaml 解决"我只在 Windows 跑过"的盲点，比写一段 100 行的兼容性论证有用。

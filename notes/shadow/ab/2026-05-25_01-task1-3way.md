## 关键差异分析

### 1. cc：直觉式探索，最简洁

cc subagent 表现接近"程序员手工查代码"：

```
Grep -l _dispatch_tool_calls    # 先找哪个文件有
Grep -C 5 in subagent.py        # 探一下用法
Grep -C 3 "def _dispatch_tool_calls" in agent.py   # 定位定义
Read agent.py:1264-1323         # 读函数体
```

4 个工具，没有 plan / review / audit 阶段，直出答案。这是最贴合"探索任务"的形态。

### 2. yansh：探索任务被 plan agent 转成了"代码任务"

yansh 在 code mode 下，plan agent 把这个只读探索硬塞成"修改 agent.py"的 task：
- `expected_edits=1, files_modified=["agent.py"]`
- coder 跑完 search_in_files 就发了 task_complete（第一次完成 ← 实际答案在这里）
- 但 plan 还要求改文件，于是 coder 又 read_file → replace_in_file ×2 删了 2 行无关的未使用 import
- 跑了 pytest 12 passed，再发 task_complete

副作用：**该测试任务下 yansh 修改了 agent.py 文件**（删了 `get_model_price` 和 `dispatch_subagent` import）—— 虽然这俩确实没被用到，但**不在 task 范围内**。

历史 task #1 yansh 用 audit mode 只跑了 2 个工具（24.5s），没改文件。**audit vs code 是关键差异**。

### 3. yscode：修复 bug 后改走"绕过路径"，但答案没 surface

**修复前（PlanFailed bug，已修）**：architect 转圈把 input token 撑到 248K，plan 没出来 → exit_code=1，没产出。

**修复后**：architect 看完 search_in_files + read_file 后，识别出"这是探索任务"，**submit 一个空 plan**：
```json
{
  "requirement": "User repeatedly requested submit_plan but provided no actionable requirement.",
  "files": [],
  "notes": "The only prior task was a read-only analysis of _dispatch_tool_calls, which was answered directly. Please describe a concrete feature, bug fix, or refactor so a real plan can be produced."
}
```

走完 plan→code→test 流程时三个 phase 全是空操作（code phase 没改文件，test phase no test command 跳过），最终 `success: true`，summary 是 "all tests pass"。

**问题**：
- 答案确实出现在 architect 的 stream 输出（stderr 能看到 "dispatch_subagent 用 ThreadPoolExecutor 并发"）
- 但 tasklog 的顶层 summary 字段没有这个答案，stdout JSON 也没有
- 用户拿到 stdout JSON 看不到答案，需要翻 stderr 才能找到

**架构启示**：yscode 修复 PlanFailed 后能"软着陆"探索任务，但缺一个**"explorer 模式"**或**"exploration 直接答复"通道**——让 architect 在识别出探索任务后，能把答案显式写到 summary 而不是塞 stderr。

## Caveats（必读）

1. **mode 不一致带来的偏差**：本次三方都用 code mode（为跟 yscode 对齐）。yansh 历史 task #1 用 audit mode（24.5s / 2 工具 / 无副作用），而 code mode 下 yansh 会触发 plan→coder→test 流程，多干无关活。**对 yansh 不利**。

2. **gateway 差异**：cc 走 Anthropic API gateway，yansh/yscode 走 ICA gateway。同名 sonnet 4.6 在两侧后端可能行为略不同。

3. **工具集差异**：cc subagent 工具集仅 Grep/Read/Edit/Write/Bash/Glob/WebFetch；yansh/yscode 还有 search_in_files / get_symbol_definition / dispatch_subagent / replace_symbol 等专门工具。但本次三方实际都没用到 AST 类工具，影响不大。

4. **yscode .env 兼容性问题**：第一次跑直接 404 失败 —— yscode 要求 `CLAUDE_BASE_URL` 必须以 `/v1` 结尾，而 yansh 仓的 .env 写的是不带 `/v1`（yansh 代码内自动补）。复用 yscode 仓自己的 .env 后才跑通。这是两边实现差异（不是配置错误），写在这里以备后跑参考。

5. **PowerShell stdout 是 UTF-16 LE**：yscode 的 `task1_stdout.json` 是 UTF-16 编码（PowerShell 默认重定向行为），影响后续解析，但不影响数据本身。

6. **task #1 类型对 yscode 不利**：纯只读探索是 yscode 多 agent 架构的盲区。后续 task #2-#5 都是写代码任务，预期 yscode 表现会显著改善。

---

## 关键发现

- **架构 vs 任务匹配度**：cc 的"单 agent + 通用工具"对探索任务最贴合；yansh 单流程在 code mode 下会过度执行；yscode multi-agent 修复后能软着陆但答案不上 summary。
- **token 成本不直接反映价值**：yscode 修复后 65K 是三方中等价值 / 最低答案可见性的组合。yansh 167K 答对主任务+无害副作用。cc 50K 直接命中是性价比之王。
- **mode 选择对结果影响巨大**：yansh 的 audit mode（不在本次测试中）历来是探索任务的最佳路径——为对齐 yscode 用了 code mode，掩盖了这一优势。
- **yscode 还差一个 explorer 出口**：修复 PlanFailed 后，探索任务走了"空 plan 绕过"，但架构上缺一个让答案显式写到 summary 的路径。后续 task #2-#5 都是写代码任务，不会触发这个边角。

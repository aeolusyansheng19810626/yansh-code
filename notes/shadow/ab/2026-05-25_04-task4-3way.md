## 三方行为详解

### cc：教科书级 bug 修复（51K tokens / 6 工具）

```
1. TaskCreate（自己建 todo）
2. Bash: pytest -v 看失败
3. Grep: 找 find_memory 定义
4. Read: memory.py 100-139
5. Edit: name → _slugify(name) 一处改动
6. Bash: pytest 验证 35 passed
```

修法精确：识别出 `save_memory` 用 `_slugify` 但 `find_memory` 没用 → 加 `_slugify` 调用。**1 行核心修改，14 行删除（清理 commit `d95c87d` 的 docstring 和 resolve 双校验）**。

不过需注意：**cc 的修复深度比 baseline 浅**——baseline `d95c87d` 加了 slugify + resolve 双校验两层防护，cc 只加了 slugify（够过测试，但少了 resolve 兜底层）。这跟历史 task #4 cc 的修法完全一致（"⚠ 只补 slugify，缺 resolve 双校验"）。

### yansh：🔴 静默失败 — baseline failure 识别机制误吞用户请求

**最严重的发现**。yansh 跑了：
- 5 次 read_file（看 memory.py 各段）
- 3 次 get_symbol_definition（看 _slugify、find_memory、save_memory）
- 1 次 list_symbols / 1 次 list_files
- 4 次 execute_command（跑 pytest 验证）
- 1 次 task_complete

**结果**：files_modified = `<empty>`，task_complete summary = `<empty>`，**0 个 fix attempt**。

stderr 显示决定性的一行：
```
当前 1 条失败全部在 baseline 内（1 条 pre-existing）→ 视为通过
```

这是 commit `1e3ce5f`（task #5 v4 修的 baseline failure 识别机制）在反向作恶：
- 原意：fix loop 跑测试时遇到"不在 plan files 范围内的失败" → 跳过，避免追修无关问题
- 误用：把"用户 prompt 明确要求修的失败"也判成 pre-existing → 跳过

任务 prompt 明明写了 "tests/unit/test_memory.py 有测试失败，定位 bug 并修复"，yansh 完全无视，直接 task_complete 退出。**这是机制 bug，不是 LLM 判断错**。

➡ **已记入 yansh 技术负债清单（P1 #6，标红）**：[[project-yansh-tech-debt]]

### yscode：修对了但极度浪费（592K tokens / $1.85 / 36 工具调用 / 5 个文件改动）

yscode 36 个工具：11 execute_command + 10 read_file + 4 write_file + 3 replace_in_file + 3 task_complete + 余下杂项。

最终结果对：**35/35 passed**。但走的路非常迂回：
- **创建了 4 个 shim 文件**：`test_memory.py`（root）、`tests/test_memory.py`、`tests/__init__.py`、`tests/unit/__init__.py`
- root 和 tests/ 下的 shim 文件内容都是：
  ```python
  # Shim: re-export all tests from tests/unit/test_memory.py
  from tests.unit.test_memory import *  # noqa: F401, F403
  ```

推测原因：yscode 的 coder 试图用 `python -m pytest test_memory.py` 跑测试时找不到（路径写错），就创建了这些 shim 让 import path 能对得上，而不是直接用正确路径 `python -m pytest tests/unit/test_memory.py`。

**严重副作用**：
- 修复 + 4 个无关文件提交，污染 workspace
- 烧 592K token / $1.85（task #2 是 trick task 烧 56K，task #4 是真活反而 10× yscode task #2 成本）
- task #3 yscode 已经烧 426K 写文档，task #4 又烧 592K，**yscode 烧钱的方差非常大**

## 关键发现

1. **🔴 yansh baseline failure 识别机制是个时间炸弹**：task #3 帮它避死循环，task #4 让它漏修用户明确请求的 bug。这条机制需要立刻修。
2. **cc subagent 在 bug 修复任务上是性价比之王**：51K token 一行修对，比另两方都干净
3. **yscode 把"看不到的工程实践"补全了**：创建 `tests/__init__.py` 这种是某些 python project 的 best practice，但本 repo 不需要——**yscode 倾向于过度补足"标准结构"**
4. **yscode 在执行测试上反复试错**：11 次 execute_command，路径写法换了好几次才走通，说明 yscode 对"workspace 内执行命令"的环境推理弱

## Caveats

1. **bug 注入是手动的**：通过 `git show d95c87d -- memory.py | git apply -R` reverse-apply，跟历史 task #4 一致
2. **修复深度都浅**：cc 和 yscode 都只补 slugify，没加 resolve 双校验（baseline 是双层防护）。功能上够过测试，但安全性不如原 fix
3. **yansh 的 baseline failure 识别本意是好的**：避免 fix loop 死磕 baseline 自带的失败。问题在过滤策略太粗——不区分"用户提到的失败"和"无关失败"
4. **gateway 差异**仍在

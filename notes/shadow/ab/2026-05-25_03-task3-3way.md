## 关键差异分析

### yansh：plan agent 凭"上下文知识"直接出文档（44K token，4 个工具调用）

yansh 的 4 个工具调用：
```
1. write_file → notes/shadow/2026-05-24_01-task-complete-signal-migration.md
2. task_complete (主声明：报告已写好，覆盖 4 个要点)
3. task_complete (fix 循环里识别 216 条 lint 错误是 baseline 失败 → 跳过)
4. task_complete (最终，跑测试触发"未知错误"→ 仍判定不属于任务范围)
```

**plan agent 没让 coder 做任何代码探索**就直接进入"写文档"阶段。这意味着：
- ✓ 极快（44K token，全 5 方 task #1-3 中最少之一）
- ⚠️ 文档内容是 LLM 从 system prompt 已注入的 repo 信息 + 训练知识里"记忆"或"推断"出来的，**不一定 100% 反映 baseline 实际代码**。需要单独审核文档准确性。

历史 task #3 yansh 用 audit mode 跑了 50 个工具调用 + 73 万 token，深度探索了代码再写文档；这次 code mode 走了"短路径"。

### yscode：穷举式探索 + 把整篇文档塞 task_complete summary（426K token，$1.35）

yscode 31 个工具调用里 **24 个是 read_file**，把整个 codebase 一遍读了。然后把 5,226 字的 markdown 文档**直接塞到 task_complete 的 summary 字段**里。

**问题**：
- summary 是个 string 字段，塞 5K 字符的 markdown 不是设计意图
- summary 内容会回放到后续每一轮 messages，token 翻倍消耗
- 用户拿 stdout JSON 看 summary 才能拿到文档，**没有独立文件落盘**

这是 yscode 在"任务要求输出文档但 plan 阶段没识别 file_path"时的退化行为。比 task #1 探索任务的"答案塞 stderr"好一点（至少在 summary 里能找到），但仍不理想。

### cc：均匀探索，最务实

cc 26 个工具调用里：14 次 Read（细读 agent.py 多个段落）+ 3 次 Grep + 2 次 Glob。读了 agent.py 的 plan/code/fix/audit 4 个核心循环段落，subagent.py，tools_schema.py 等。

写出 7,215 字文档到 `AB-test/cc/task3_doc.md` —— **不污染 workspace**。这是 cc 的好习惯：subagent 默认不在 workspace 内写文件，输出走 result.json。

### yansh "plan files 仅文档" 触发的退化路径

stderr 里出现：
```
[安全拦截] 检测到危险命令：python -c (内联执行)
测试失败 (尝试 2/3)
[Agent: Tester]
开始修复代码...
执行 1 个修复操作...
修复结束（task_complete: 成功）：Plan files 仅包含文档文件 ...
```

yansh 的 fix 循环触发了：
1. plan 写了 `test_command: python -c "import os; assert os.path.exists('notes/shadow/...')"` 验证文档存在
2. yansh 安全拦截 `python -c` → 测试"失败"
3. 进 fix loop，Tester agent 主动声明"plan files 仅含文档，测试失败不属于任务范围" → 跳出

**这是 task #5 v4 修的 baseline failure 识别机制起作用了**（commit `1e3ce5f`）。如果没这个机制，task #3 yansh 会卡在 fix 死循环。

## 跨 task 趋势

| Task | yansh tokens | yscode tokens | cc tokens | 任务性质 |
|---|---|---|---|---|
| #1 探索 | 167K | 65K（修复后） | 50K | 只读 |
| #2 写代码 trick | **915K** | 56K | 70K | 已实现需识别 |
| #3 论证 | **44K** | **426K** | 128K | 写文档 |

观察：
- **yansh 成本极不稳定**（44K ~ 915K，21× 差距）：取决于 plan 是否准确划定 scope。task #2 plan 出了 4 个文件子任务 → 烧爆；task #3 plan 出 1 个文档 → 极省
- **yscode 成本相对稳定但偏高**（56K ~ 426K，8× 差距）：multi-agent 流程是"广度优先 + plan+code+review 三阶段"基线开销
- **cc 成本最稳定**（50K ~ 128K，2.5× 差距）：单 agent，开销跟任务复杂度直接挂钩

**对 yansh 的启示**：plan agent 的 expected_edits 准确性直接决定后续 token 开销。task #2 plan 把"已实现的 task"误划为"4 个文件需要改"，触发灾难；task #3 plan 把"写文档"准确划成"1 个文件" → 走最优路径。**这是 plan agent 优化的高 ROI 方向**。

## Caveats

1. **plan agent 的探索深度差异**：yansh code mode 下 plan agent 直接出文档；yscode 在 plan 阶段做大量探索；cc 在执行中边探索边写。三种模式各有取舍。
2. **yscode 文档没独立文件**：yscode 把文档塞 summary 字段是退化行为，缺一个"explicit file output"通道，建议跟 task #1 探索任务的"答案塞 stderr"一起放进 yscode 改进清单。
3. **yansh fix loop baseline 失败识别机制起作用了**：commit `1e3ce5f`（task #5 v4 验证）的修复在 task #3 实际生效，避免了 fix 死循环。
4. **gateway 差异**仍在。

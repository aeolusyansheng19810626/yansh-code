## 三个工具的"画像"

### 🥇 cc (Claude Code subagent + general-purpose)

**优势**：
- 单 agent + 通用工具集（Grep / Read / Edit / Write / Bash / Glob），简单直接
- 5/5 全部任务成功完成
- token 消耗最稳（50K - 132K，方差最小）
- 没有 plan/coder 解耦，没有 plan agent 转圈成本

**劣势**：
- self-report 字段（`files_modified` / `tool_calls`）经常误报，**只有 git diff 才是真相**
- 缺 AST 类专门工具（`get_symbol_definition` 等），靠 grep + read 组合
- 修复深度偏浅（task #4 只补 slugify 缺 resolve 双校验）

**适合**：所有 5 类任务都能稳定完成，是 baseline 中最好的"程序员替代品"

### 🥈 yscode (multi-agent CLI: plan + coder + review + audit)

**优势**：
- 写代码任务表现好（task #2 完美 / task #4 修对）
- plan→code→test 阶段清晰可观测
- 修复深度通常完整（不像 cc 浅）

**劣势**：
- 探索 / 论证类任务退化严重：
  - task #1 答案塞 stderr 不上 summary（已修过一次但仍不理想）
  - task #3 用 24 次 read_file 穷举式探索，烧 426K
  - task #5 architect 试图自己跑 cmd 探索，cp932 编码错耗光 budget → PlanFailed
- 倾向"工程洁癖"过度补结构（task #4 创建 4 个无关 shim）
- windows cp932 / console 编码兼容差
- 整体偏贵（$1.85 / $2.58 在 task #4 / #5）

**待修**：task #5 PlanFailed 触发路径（架构 architect 自己跑 cmd 时容错差）

### 🥉 yansh (单 agent CLI + plan→code→fix 解耦)

**优势**：
- plan agent 划 scope 准的时候极快（task #3 仅 44K）
- 专门工具（`get_symbol_definition` / `search_in_files` / `dispatch_subagent`）
- replay 系统完整可观测

**劣势 — 暴露 4 个 P1 级机制问题**（已全部记入 yansh 技术负债）：
1. **P1 #4 plan 不接受 coder "无需修改"信号**（task #2，烧 91 万 token 改 task 范围外）
2. **P1 #5 plan agent 写代码细节文档时零探索就交付**（task #3，文档 1 错 2 偏）
3. **P1 #6 baseline failure 识别误吞用户请求**（task #4，静默失败）
4. **P1 #7 主仓 _err 签名不一致 CLI crash**（task #5，30 分钟可修，必修）

**当前状态**：4 个 P1 集中修一次半天能搞定（P1 #7 必先修，task #5 暴露的就是它本身）

## 关键发现

### 1. self-report 不可信 → 只信 git diff

cc 的 `files_modified` 字段经常误报（task #2 标了 tools.py 但 diff 空；task #5 callsites_updated=48 但实际 57）。yansh 的 task_complete summary 也可能为空但 git diff 显示已改。**评估时必须现场跑 git diff + pytest，不能依赖 LLM 的自我报告**。

### 2. mode 选择对 yansh 影响巨大

yansh 历史 task #1 用 audit mode 是它的最佳路径（24.5s / 2 工具）。本次为对齐 yscode 用 code mode，yansh 在 task #1 / #3 都损失了它的天然优势。**code mode 强制走 plan→coder→fix 流程，对探索 / 论证类任务过度执行**。

### 3. plan agent 准确性是 yansh 性能的决定因素

| Task | yansh tokens | plan 准确性 |
|---|---|---|
| #3（plan 划"1 个文档文件"） | 44K | ✓ 准确 |
| #1 / #4 | 167K-205K | 一般 |
| #5（plan 划 4 个文件，未识别 baseline 半实现） | 692K | 偏差 |
| #2（plan 误划"4 个文件需要改"，实际 baseline 已实现） | 915K | ✗ 完全错 |

**plan/coder 解耦的成本**：plan 错的时候，coder 按 plan 推进会烧爆 token；plan 对的时候极省。优化 plan agent 是 yansh 的最高 ROI 方向。

### 4. yscode 多 agent 架构的稳定性问题

| 类型 | 表现 |
|---|---|
| 写代码任务 | ✓ 强（task #2 完美 / task #4 修对） |
| 论证 / 探索 | ⚠️ 退化（穷举式探索 / 答案塞 summary / cp932 失败） |
| windows 兼容 | ⚠️ cp932 编码错触发 architect 死循环（task #1 / task #5） |

yscode 的 architect 在某些边角任务上"广度过载"，烧 token 但产出低。需要更多"早退"路径。

### 5. cc 是真正稳的"程序员替身"

cc 5 个 task 全部完成，token 消耗最稳。这反映 Claude Code 的单 agent + 通用工具组合在大多数场景下足够好，**多 agent 架构（yansh / yscode）的额外复杂度并不总是带来收益**。但要注意：
- cc 修复深度偏浅
- self-report 不可信
- 没有 dispatch_subagent / 跨文件批量编辑等高级工具，硬重构（task #5）依赖 LLM 一次性写对

## 决策建议（基于本次 AB）

### yansh 优先级（半天 + 30 分钟）
1. **必修（30 分钟，必须）**：P1 #7 _err 签名一致性（agent.py 用 keyword arg 或者 tools.py 加 tool 形参）
2. **高优（半天）**：P1 #4 / #5 / #6 三个 plan-coder 协议问题集中修
   - #4 coder 报"无需修改" → plan 跳过剩余 expected_edits
   - #5 plan 写代码细节文档前必须 explorer 子 agent 扫码
   - #6 baseline failure 识别加"是否在用户 prompt 提及"过滤
3. 修完后回归 task #2 / #4 / #5（预期 yansh 表现显著改善）

### yscode 优先级
1. task #5 PlanFailed 触发路径（cp932 / cmd 反复重试 → budget 耗光），加超时 / 错误率上限早退
2. 探索 / 论证类任务的"答案 surface 通道"（不要塞 stderr / summary）

### 工具选型建议
- **日常 coding 助手**：cc 是最稳的选择
- **重型重构 / 跨文件改动**：yansh 修完 P1 #4-#7 后预期是最佳（专门工具 + replay 优势）
- **从零写代码 / 多阶段开发**：yscode（plan→code→review 流程匹配该场景）

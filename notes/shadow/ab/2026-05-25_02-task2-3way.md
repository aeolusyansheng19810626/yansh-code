## 三方行为详解

### cc：识别对了，但自报告字段不可靠

8 个工具调用：
```
Glob → Grep×2 → Read×2 → Bash(pytest) → ...
```
最终 git diff 完全空 —— cc 实际没动任何文件。但 `task2_result.json` 里 `files_modified: ["tools.py", "tests/unit/test_tools.py"]` 是错的（**LLM 自报告字段** vs **客观 git diff** 不一致）。

cc 的 5 个 pre-existing failures 也是 baseline 自带的，跟本 task 无关。

### yansh：第一次答对了，但 plan 不放手 → 跑 41 个工具调用 + 91 万 token

yansh 的执行序列（从 task_log replay 看）：
1. **第一次 task_complete**：search + read + get_symbol_definition + pytest → 正确识别"三处均已存在且实现正确" ✓
2. **第二次 task_complete**：又检查一次 agent.py 的分发逻辑 → 再次确认"无需修改"
3. **但 plan 继续派 coder**：plan 列了 4 个 expected_edits 子任务（tools.py / tools_schema.py / agent.py / test_tools.py），coder loop 触发 ruff lint 检查 → 发现一些 lint 问题 → 顺手"修了"：
   - `agent.py`: 删 `get_model_price` import（task #1 已观察到的"额外清理"模式）
   - `agent.py`: 删 `dispatch_subagent` import
   - `tests/unit/test_tools.py`: `for l in lines` → `for line in lines`（避 E741 ambiguous）
   - `tests/unit/test_tools.py`: `import base64, io` → 拆两行（避 E401）
   - `tests/unit/test_tools.py`: 删未使用的 `PIL = ` 赋值
4. 4 个子任务全部触发"已用尽 5 轮工具调用上限"警告
5. 最后 task_complete signal 仍报 success=true

**yansh code mode 的固有偏差**：plan agent 即使收到 coder 的"无需修改"信号，仍会按 expected_edits 推进；fix loop 会带着 lint 修复"顺手清理"。这跟 task #1 的"删 import"行为是同源的。

### yscode：架构胜利

yscode 流程（从 stderr 看）：
1. plan phase: search_in_files → read_file（看 read_file 现状）
2. plan agent submit_plan with `files: []`（识别"已实现"）
3. code phase: 执行 task_complete with summary "需求已完整实现，无需任何修改"
4. test phase: 跑了一遍 pytest 验证（execute_command pytest 看到全 pass）
5. exit_code=0, success=true

**关键**：yscode 把"需求已实现"的判断**显式写到 summary**，stdout 里能直接读到。这次比 task #1（探索任务）的"答案塞 stderr"行为要好。

## 关键差异：plan 退出机制

| 工具 | 收到"无需修改"信号后的行为 |
|---|---|
| **cc** | 一次性流程，没有显式 plan/coder 分离 → 没有"plan 不放手"问题 |
| **yansh** | plan 是上下文中的 description list，coder 报 task_complete 后 fix loop 仍按 expected_edits 推进 → 烧 token |
| **yscode** | architect 在 plan phase 直接 submit `files: []` → 后续 phase 全部空操作走完 |

yscode 的多 agent 架构在这种边角任务上反而**最高效**，因为它有明确的"plan 阶段定 scope"边界。

## Caveats

1. **trick task 的诚实性**：本次 baseline 已实现，**真正的能力差异在"识别 + 退出"机制**，不是"实现能力"。后续 task #3（论证）/ #4（bug 修复）/ #5（重构）应能更全面对比"实现能力"。
2. **cc 的 self-report 字段不可靠**：`task2_result.json` 里 `files_modified` 是 LLM 写的，跟 git diff 客观结果不一致。**只有 git diff 是真相**。
3. **yansh 的 plan/coder 协议**：当 coder 早退（task_complete 报"无需修改"），plan agent 不会放弃后续 expected_edits 推进 → 烧大量 token。这是 yansh 一个值得关注的能效问题。
4. **gateway 差异**仍在：cc 走 Anthropic gateway，yansh/yscode 走 ICA gateway。

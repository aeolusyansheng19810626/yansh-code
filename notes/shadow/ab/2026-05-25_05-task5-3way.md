## 三方行为详解

### cc：64 工具调用稳健完成（132K tokens）

cc 的修法路径：
- 改 `tools.py` 的 `_err` 函数签名 + 56 个调用点
- 改 `subagent.py` 1 个调用点
- 加 1 条新单测 `test_err_helper_includes_tool_field`
- **没改 agent.py**——cc 准确识别出 baseline `agent.py:1236/1244/1248/1310` 已经在用 3 位置参数调用 `_err("internal", "msg", name)`（baseline 的 agent.py 写得"超前"），所以加 tool 参数后调用就匹配了

cc 自报告 callsites_updated=48（实际 tools.py 56 + subagent.py 1 = 57，self-report 又一次不可信）。但 git diff 客观结果：tools.py 115 行变化，跟任务要求一致。

最终 pytest test_tools.py: **41 passed, 5 failed**（5 是已知 baseline 失败，`test_build_diff_lines_exactly_50_no_truncation` 等跟本任务无关），新加的单测过 → 任务正确完成。

### yansh：🔴 改了大部分但被自身 latent bug 干掉

yansh git diff 跟 cc 的修改极为相似（tools.py 120 行 / subagent.py 2 行 / test_tools.py 12 行），说明 yansh 也按同样思路改了。但 **yansh CLI 进程在 fix loop 跑过程中崩溃了**：

```
File "agent.py", line 1236, in _dispatch_tool_call_inner
    result = _tools_mod._err("internal", f"工具调用异常: {e}", name)
TypeError: _err() takes 2 positional arguments but 3 were given
```

崩溃链：
1. coder LLM 给 `search_in_files` 传了非法 regex（`missing )`）
2. tools.py `search_in_files` 抛 `re.error`
3. `agent.py:1236` except 块调 `_err("internal", f"...", name)`（3 个位置参数）
4. **但主仓 yansh-code 的 tools.py `_err(kind, msg, **extra)` 只接 2 个位置参数** → TypeError
5. yansh CLI crash, exit=1, stdout 空

**这是 yansh 主仓 latent bug**：agent.py 已经按"未来 task #5 重构后"的方式调用 _err，但 tools.py 还没适配。平时不走错误分支不会暴露；task #5 LLM 给只读工具传错参数就触发了。

→ **已记入 yansh 技术负债 P1 #7（标红，30 分钟可修）**：[[project-yansh-tech-debt]]

讽刺的是：**这个 bug 正是 task #5 要修的内容本身**。yansh 在修这个 bug 的过程中被这个 bug 干掉了。

token 消耗 692K 也很高，但比历史 task #5 的 1.86M 少 63%（baseline 自带的"Anti-pattern" 注释 line 1361 提示 LLM 用 `replace_all` / `write_file` 批量改，应该减少了 yansh 的 tool round 数）。

### yscode：PlanFailed × 2（task #1 之后再次出现）

yscode 跑了 24 个工具调用、烧 789K token / $2.58，**0 文件修改**。失败原因：

```
ERROR: <PlanFailed: architect did not submit a valid plan within budget>
```

stderr 显示 architect 在循环试 `python -c "..."` 多行命令，触发 cp932 编码错（windows console），LLM 反复重试切换写法（`io.TextIOWrapper(sys.stdout.buffer)` 等），耗光 plan budget。

跟 task #1 PlanFailed 不是同一根因：
- task #1：architect 不知道怎么把"探索任务"转 plan（已修）
- task #5：architect 试图自己跑 cmd 探索（用 `python -c` 列出所有 _err 调用点），但 windows cp932 编码反复出错，转圈耗光 budget

## 总结：3 个工具的"画像"

### cc (Claude Code subagent + general-purpose)
- **优势**：单 agent + 通用工具集，简单直接，结果稳，token 低
- **劣势**：self-report 字段不可靠（`files_modified` 经常误报），缺 AST 类专门工具，需要靠 grep + read 组合
- **适合**：所有 5 类任务都能稳定完成，是 baseline 中最好的"程序员替代品"

### yansh (单 agent CLI + plan→code→fix 解耦)
- **优势**：plan agent 划 scope 准的时候极快（task #3 44K token）；专门工具（`get_symbol_definition` / `search_in_files` / `dispatch_subagent`）；replay 系统完整可观测
- **劣势**：
  - plan/coder 协议在边角任务上"不放手"（task #2 烧 91 万）
  - baseline failure 识别机制吞用户请求（task #4 静默失败）
  - 主仓 latent bug：_err 签名不一致 → 工具异常时 CLI crash（task #5）
  - 文档生成时零探索（task #3 文档准确度有 1 错 2 偏）
- **当前状态**：task #2 / #4 / #5 三个 P1 级别的机制问题已经全部记入技术负债清单 [[project-yansh-tech-debt]]，需要集中修一次

### yscode (multi-agent CLI: plan + coder + review + audit)
- **优势**：写代码任务（task #2、#4 修对）表现好；plan→code→test 的清晰阶段划分
- **劣势**：
  - 探索 / 论证类任务退化严重（task #1 答案塞 stderr，task #3 426K 穷举式 read，task #5 PlanFailed）
  - architect 容易在 plan phase 转圈耗光 budget（task #1 已修，task #5 因 cp932 编码错重现）
  - 倾向"工程洁癖"过度补结构（task #4 创建 4 个无关 shim 文件）
  - cp932 / windows console 编码兼容差
- **当前状态**：task #1 修复后回归良好，task #5 暴露的 PlanFailed 触发路径需要 yscode 那边再看一次

## Caveats

1. **gateway 差异**：cc 走 Anthropic gateway，yansh/yscode 走 ICA gateway。同名 sonnet 4.6 在两侧后端可能行为略不同
2. **mode 不一致代价（task #1）**：yansh 历史 task #1 用 audit mode 是它的最佳路径，本次为对齐 yscode 用 code mode 损失了它的优势
3. **yansh 主仓在 AB-test 中有 latent bug 暴露（task #5）**：跟 AB-test 流程无关，是 yansh 自身代码问题
4. **yscode 在 windows 上有 cp932 编码兼容问题**：影响其 architect 自己跑 `python -c` 探索的能力

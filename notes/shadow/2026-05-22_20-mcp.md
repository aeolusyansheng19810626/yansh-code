# P2 #10 MCP 协议（最小版）

承接 [_19](./2026-05-22_19-subagent-concurrent.md)：子 agent 完成后做 #10。
ROADMAP 标这个为 LLM agent 设计的**关键架构概念**——做完对工具生态的理解上一个台阶。

## 目标

让 yansh 接入 MCP（Model Context Protocol）生态——用户能配置任意第三方
MCP server（GitHub / Linear / Sentry / 自写的内部工具 server），yansh 自动发现并把
工具注入 TOOLS 列表，LLM 像调内置工具一样调它们。

## 改了什么

### 1) `mcp_client.py` 新文件

#### `MCPServer` 类——管一个子进程的完整生命周期

```python
class MCPServer:
    def __init__(self, name, command, args=None, env=None, cwd=None): ...
    def start(self, init_timeout=15):    # spawn + initialize 握手 + tools/list
    def call_tool(self, tool_name, arguments, timeout=60): ...
    def shutdown(self): ...
    def is_alive(self) -> bool: ...
```

实现关键点：
- `subprocess.Popen` 三 pipe（stdin/stdout/stderr）+ `text=True` 行缓冲
- 后台 reader 线程读 stdout，按 JSON-RPC `id` 分发到 `_pending` 队列
- 后台 stderr 线程收集错误（保留最近 50 行用于诊断）
- `_request(method, params, timeout)` 用 `threading.Event` 阻塞等响应——超时 → `TimeoutError`，server 报错 → `RuntimeError`
- `_send_line` 加 `_writer_lock` 串行化写入（防止多线程交错）

#### MCP 协议序列（实现）

```
client  → server : {"jsonrpc":"2.0","id":1,"method":"initialize",
                    "params":{"protocolVersion":"2024-11-05","capabilities":{},
                              "clientInfo":{"name":"yansh"}}}
server → client  : {"jsonrpc":"2.0","id":1,"result":{...}}
client  → server : {"jsonrpc":"2.0","method":"notifications/initialized"}   # 通知
client  → server : {"jsonrpc":"2.0","id":2,"method":"tools/list"}
server → client  : {"jsonrpc":"2.0","id":2,"result":{"tools":[{name,description,inputSchema}, ...]}}
（之后调用工具）
client  → server : {"jsonrpc":"2.0","id":3,"method":"tools/call",
                    "params":{"name":"echo","arguments":{"text":"hi"}}}
server → client  : {"jsonrpc":"2.0","id":3,"result":{"content":[{"type":"text","text":"hi"}]}}
```

#### 模块级 registry

```python
_servers: dict = {}   # name -> MCPServer，加 _servers_lock 保护

load_config(workspace_dir) -> dict          # 加载 mcp.json
start_all_servers(workspace_dir) -> tuple   # spawn + initialize 全部
discover_tools_as_schemas() -> list         # 把 server 工具转 yansh TOOLS schema
parse_prefixed("mcp__a__b") -> ("a", "b")   # 拆前缀
call_tool(prefixed_name, args) -> dict      # 路由到对应 server
shutdown_all() -> None                      # atexit 钩子
```

#### 工具命名空间：`mcp__<server>__<tool>`

对齐 Claude Code。LLM 看到的是带前缀的名字；`_dispatch_tool_call` 拆前缀转发。
完全不会跟内置工具撞名。

#### 配置格式（兼容 Claude Code 的 mcp.json）

路径优先级：`<workspace>/.yansh/mcp.json` → `~/.yansh/mcp.json`

```json
{
  "mcpServers": {
    "everything": {
      "command": "npx.cmd",
      "args": ["-y", "@modelcontextprotocol/server-everything"]
    },
    "github": {
      "command": "npx.cmd",
      "args": ["-y", "@modelcontextprotocol/server-github"],
      "env": {"GITHUB_PERSONAL_ACCESS_TOKEN": "ghp_..."}
    }
  }
}
```

Windows 注意：npx 实际是 npx.cmd——subprocess 找不到 npx 直接报 FileNotFoundError。
首版就让用户自己写 `.cmd` 后缀；下一波加 PATHEXT 自动探测。

### 2) `agent.py` 集成

```python
import mcp_client as _mcp_mod

# _dispatch_tool_call 末尾加路由（在"未预期工具"分支前）
if name.startswith("mcp__"):
    result = _mcp_mod.call_tool(name, args)
    return {...}

# 新增
def init_mcp(verbose=True) -> dict:
    """启动 mcp.json 里的 server，把工具注入 TOOLS"""
    started, errors = _mcp_mod.start_all_servers(_get_workspace())
    if started:
        new_schemas = _mcp_mod.discover_tools_as_schemas()
        # 原地修改 TOOLS（保持引用稳定，audit/subagent 各路径读同一份）
        TOOLS[:] = [t for t in TOOLS if not t["function"]["name"].startswith("mcp__")]
        TOOLS.extend(new_schemas)
    ...

def shutdown_mcp() -> None: ...   # atexit 钩子
```

关键设计：**TOOLS 原地修改而非重赋值**——agent.py 各路径（audit/code/fix/subagent）
持有的是 list 引用，原地 `[:]` 修改让所有读者拿到新工具不需重启。

### 3) `main.py` 集成

```python
# 启动时
import atexit
atexit.register(_agent_mod.shutdown_mcp)
_agent_mod.init_mcp(verbose=True)

# 命令
/mcp list           列出已启动 server + 工具数 + alive 状态
/mcp tools [name]   列指定 server 的全部工具（带 mcp__ 前缀）
```

### 4) 安全：audit 模式拦截 mcp 工具

audit 模式 `mode == "audit" and name not in READONLY_TOOL_NAMES` 自动拦截 mcp 工具——
第三方 mcp 工具可能改外部状态（如 GitHub MCP 的 create_issue），audit 默认禁用。
要让某个 mcp 工具在 audit 可用，需用户显式把它加进 READONLY_TOOL_NAMES。

子 agent role：
- explorer/auditor：只读工具集，不含 mcp（保守）
- general：全工具，含所有 mcp 工具

## 评估

### 跟 Claude Code 的差距

| 维度 | Claude Code | yansh |
|---|---|---|
| stdio 传输 | ✅ | ✅ |
| HTTP/SSE | ✅ | ❌（最小版不做） |
| tools/list + tools/call | ✅ | ✅ |
| resources（文件类资源） | ✅ | ❌ |
| prompts（提示模板） | ✅ | ❌ |
| sampling（server 反向调 LLM） | ✅ | ❌ |
| mcp.json 兼容 | ✅ | ✅ |
| `mcp__<server>__<tool>` 命名 | ✅ | ✅ |
| `/mcp` 命令 | ✅ | ✅ |
| 自动重连 | ✅ | ❌ |

差距集中在"非 tools 的 capability"——本波目标是打通最常用的 tool 通道，**80% 收益的 20% 实现**。

### 工程意义：从"一次实现内置工具"到"一次实现协议"

这一波之前，yansh 加一个新工具需要：
1. tools.py 写函数
2. tools_schema.py 加 schema
3. tools_schema.py 加进 READONLY_TOOL_NAMES（如果是只读）
4. （可能）在 agent.py 的 readonly_handlers 注册 handler

每加 N 个工具就改 N 次。

接入 MCP 后：用户在 mcp.json 写一行配置，就能拿到该 server 的全部工具。
GitHub MCP 一行 → 自动有 list_issues / create_pr / get_file_content 等十几个工具。
**生态扩展点**——这才是协议的价值。

### 学到什么

- **JSON-RPC over stdio 的简洁性**：相比 gRPC / HTTP，stdio 几乎零配置。
  Claude / yansh 这种 CLI 程序用 subprocess 启 server 就是 native 做法。
- **client / server / 用户三方信任模型**：
  - client（yansh）：相信用户配的 server 是良性的
  - server：相信 client 给的参数有效（schema 能挡住一部分）
  - 用户：必须只配置信任的 server——server 看到任意 LLM 上下文 + 任意工具参数
- **协议版本协商**：`protocolVersion: "2024-11-05"`——server 可以拒绝不兼容版本
- **生命周期管理**：subprocess 必须显式 shutdown（atexit），否则进程泄漏

## 不做（留给后续）

- HTTP/SSE 传输：最主流的 MCP 是 stdio，远程 server 用 HTTP 但目前生态还少
- resources / prompts：tools 是 80% 用例，余下两个 capability 加起来 < 20%
- sampling（server 反向调 LLM）：协议复杂，且会让 server 看到模型/账号信息——安全敏感
- 自动重启 / 心跳：server 崩了让 yansh 重启即可
- 工具结果中的图片/文件：当前 content[] 非 text 项原样转 JSON（LLM 看到的是 JSON 串）
- Windows 上自动探测 `.cmd` / `.exe` / `.bat`：现需手写 `npx.cmd`
- prompt injection 防护：第三方 server 返回的 text 直接进 LLM context；至少在 description 加"以下来自外部 server"标记

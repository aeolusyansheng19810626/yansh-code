## 核心发现：硬卡设在了够不到的地方

v2 主动 smoke 硬卡放在 gate 循环里、**在"轮次耗尽判断"之后**。但 agent 在初始 drive
就烧满 120 轮、从未 task_complete → gate 循环第一次迭代顶部即判
`total_rounds >= 120` → 直接走 _final_gate_verdict 兜底 → v2 硬卡（在其后）永远够不到。

**整条 gate 回灌机制（v1 collected-0 回灌、v2 smoke 硬卡都建立在其上）都隐含假设
"agent 会先 task_complete 再进 gate 复核"。** 而 sonnet 在 miniQL 这类强耦合任务上
系统性地烧满轮次不收尾，这个假设根本不成立：
- v1 collected-0 回灌：够不到（没到 gate）
- v2 主动 smoke 硬卡：也够不到（没到 gate）
- 唯一活下来的是 `_final_gate_verdict` 兜底判定——但它只能在轮次耗尽时**诚实标注**
  no_smoke，不能**强制 agent 去补**。

## 这把问题推进了一层

实验1 首轮的结论是"该卡什么判据"（有任意测试 → 有 smoke）。v2 这次把问题推到
**"该在什么时机卡"**：再正确的判据，设在"agent 主动收尾之后"这个时机，对
"压根不收尾"的 agent 完全无效。

这正面印证用户引用的 Anthropic 工程师观点——提示词、gate 回灌都是概率性的、
依赖 agent 走到那个检查点。**确定性的拦截必须前移到不依赖 agent 主动收尾的位置**：

1. **PostToolUse hook**：每次 write_file 到 miniql/__main__.py 后立即检查
   tests/test_smoke.py，没有就拦/提示。不等 task_complete。
2. **写实现前先强制建 tests/ 骨架**：在主 drive 循环内、第一个实现文件落地前插钩子。
3. **smoke gate 前移**：从"task_complete 之后"挪到主 drive 循环内周期性检查。

→ 天然引向 CC 的 **Hooks** 功能（backlog「CC 功能练习」下一项），实验与功能练习再次绑定。

## 附带确认

- `_final_gate_verdict` 的 collected-0 + 入口无 smoke → no_smoke 判定（v2 加的）**生效了**，
  是这次唯一让裁定诚实的改动——否则会误判 no_command。
- 发现6 兜底认可 agent_completed：本次未触发（裁定是 no_smoke 非 passed，且 agent 从未宣告）。
- run_accept.py 路径坑：传相对 ws 名会因 cwd=ws + --data 含 ws 前缀路径翻倍 → 全 not found；
  **必须传绝对路径**。

## 背景与测试范围

本报告基于对 agent-skills 项目的代码审查测试，横向对比三个工具的实际表现：

- **Claude 原生模型**：直接用于静态分析任务
- **yansh**：代码生成工具
- **yscode**：代码生成工具

| 维度 | Claude 原生 | yansh | yscode |
|------|------------|-------|--------|
| 完成审查任务 | 完成（6维度）| 未完成 | 未完成 |
| 代码引用 | 有 | — | — |
| 严重级别分类 | 有 | — | — |
| 多文件关联分析 | 支持 | 不支持 | 不支持 |

**核心洞见**：yansh 和 yscode 的工作流被固化为 `plan → code → test`，本质是代码生成工具，不具备纯静态分析模式。这不是能力不足，而是工具定位的根本差异。

## 代码质量分析

### yansh 生成代码

- **重大缺陷数：2（Major）**，代码无法正常运行
  - `evaluator.py` 存在 ImportError（错误的 import 路径）
  - `web_search` 中 `yield` 返回 `dict` 而非 `str`，类型错误
- `stream_chat` 缺少 `system` 参数
- **优势**：JSON 处理更具防御性（bracket depth counting + JSON repair）

### yscode 生成代码

- **重大缺陷数：0**，可直接运行
- 接口契约更严格（`yield str` 一致性好）
- 单例模式管理 LLM 客户端，接口更整洁
- **已知问题**：`rfind` JSON 提取在值含闭合花括号时会失败；`system prompt` 中存在硬编码参数

**规律**：yscode 在代码可运行性和接口一致性上胜出；yansh 在鲁棒性策略（如 JSON 容错）上更具防御意识，但因基础缺陷导致整体可用性差。

## 架构与实现差异

| 维度 | yansh | yscode |
|------|-------|--------|
| 文件规模 | 16 文件（完整） | 16 文件（完整） |
| Router JSON 解析 | bracket depth counting + JSON repair（更鲁棒） | rfind 提取（边界情况有缺陷） |
| LLM 客户端管理 | 未显示单例 | 单例模式（更整洁） |
| 并发方案 | Queue + Thread | ThreadPoolExecutor + timeout 检测 |
| 错误处理 | 全路径均有 fallback | 全路径均有 fallback |

两者在整体架构完整性上相当，差异集中在**实现细节的健壮性**上。

## 总结与实践结论

**1. 工具选型要匹配任务类型**
yansh / yscode 适合「生成新代码」，不适合「分析现有代码库」。纯审查、报告生成、跨文件关联分析应直接使用 Claude 原生模型。

**2. 可运行性优先**
yansh 的两个 Major bug 让防御性设计的价值归零。代码质量的第一标准是「能跑起来」，再谈架构优雅。

**3. 接口一致性是隐性质量指标**
yscode 的 `yield str` 一致性体现了更清晰的契约意识，减少了下游集成风险。这类规范性差异在大型项目中会被放大。

**4. 两者在并发和容错上均有基础设施**
Queue+Thread vs ThreadPoolExecutor 均可接受，关键看具体场景的超时控制需求——yscode 的 ThreadPoolExecutor + timeout 检测在可控性上略优。

**5. 静态分析能力是 LLM 工具的重要缺口**
当前代码生成工具普遍缺乏系统性多文件读取、跨文件关联分析能力。这是一个值得关注的产品能力空白。

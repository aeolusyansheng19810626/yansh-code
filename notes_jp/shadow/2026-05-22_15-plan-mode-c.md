# P2 #7 Plan Mode スキーム C 実装

[_14](./2026-05-22_14-p1-batch-4-5-6.md) から引き継ぎ：P1 の 3 項目完了後に P2 を開始、ユーザーの要求「1 つずつ、先に #7」に従う。
スキーム B/C の選択肢について協議した結果、ユーザーが **スキーム C：完全なステートマシン** を選択——session レベルのフラグ、複数ターンの対話を通じた洗練されたスキーム、ユーザーの /approve によるトリガー実施。

## 何を変更したか

### 1) state.py に plan フィールドを追加

```python
@dataclass
class Session:
    ...
    plan_mode: bool = False
    plan_draft: str = ""
    plan_history: list = field(default_factory=list)
```

`pull` / `push` / `reset` / `scoped_session` はすべて新しいフィールドを同期処理する。
agent.py は対応するモジュールレベルの `_PLAN_MODE` / `_PLAN_DRAFT` / `_PLAN_HISTORY` を管理する——段階的に保つ（読み書きパスは変更しない）。

### 2) tools.py に 2 つの sentinel ツールを追加

```python
def update_plan_draft(content):
    return {"_plan_draft_update": True, "content": str(content or "")}

def exit_plan_mode_signal(reason=""):
    return {"_exit_plan_mode_signal": True, "reason": str(reason or "")}
```

`task_complete` と同じ sentinel 形式——plan_chat ループによって認識された後に処理される。
2 つのツールを `READONLY_TOOL_NAMES` ホワイトリストに追加。

### 3) agent.py に plan パスを追加

**`_PLANNER_ROLE` システムプロンプト**：「書き込みツールは禁止」「update_plan_draft で草稿全体を置き換える」「exit_plan_mode_signal で審査待ちを表明」「task_complete を呼び出さない（終了はユーザーの /approve によって起動）」を明確化、plan 構造の提案を添付（## 目標 / ## 変更ファイル / ## 手順 / ## リスク）。

**`plan_chat(user_input)`**：完全なループ
- workspace トップレベルのシンボルインデックスを注入（audit と同様）
- システムプロンプト末尾に前ターンの `_PLAN_DRAFT` を追加（連続性を保つ）
- ツールホワイトリスト = `_filter_tools(READONLY_TOOL_NAMES)`
- マルチターン（最大 12 ターン）：`_plan_draft_update` を認識 → `_PLAN_DRAFT` に書き込み；`_exit_plan_mode_signal` を認識 → 終了
- 沈黙終了のフォールバック：最初はツール呼び出しがない場合は一度追い質問して明示的な exit signal を出させる
- ユーザー入力と assistant テキストを `_PLAN_HISTORY` に沈殿させる（tool_calls は保存しない、膨張を避ける）

**状態遷移ヘルパー**：
- `enter_plan_mode()` / `cancel_plan_mode()`
- `is_plan_mode()` / `get_plan_draft()`
- `approve_plan() -> str`：草稿を requirement に結合（「元の要求 + 【承認された実装スキーム - 厳密に従う】+ draft」）、plan 状態をクリア、`run()` 実施用の文字列を返す

### 4) main.py のスラッシュコマンドファミリー

```
/plan_on   Plan Mode に進入
/plan_off  終了（実施しない、草稿を破棄）
/plan      現在の草稿を表示
/approve   承認して run() 実施に進む
```

メインループは `agent.is_plan_mode()` を判定：yes → `plan_chat()` を実行；no → 元の classify_input → run/chat パス。

## 検証

### ユニットテスト（tests/unit/test_plan_mode.py、新規 17 件）

ツール sentinel：
- update_plan_draft / exit_plan_mode_signal の形式、None / デフォルト値

ツールホワイトリスト：
- READONLY は 2 つの新しいツールを含む、write_file / replace_in_file / execute_command など を含まない
- `_filter_tools(READONLY_TOOL_NAMES)` の出力リストが期待値と一致

ステートマシン：
- enter / cancel はクリア
- approve は requirement を結合（元の要求 + 草稿を含む）；plan 状態をクリア
- approve は空の草稿の場合、空文字列を返す

state.Session ミラー：
- pull / reset / scoped_session の 3 つすべてが plan_mode/plan_draft/plan_history を同期

plan_chat ループ（mock LLM）：
- update_plan_draft + exit signal は 1 ターンで完了、草稿は `_PLAN_DRAFT` に入る
- 沈黙 → フォールバック追い質問 → 2 ターン目で exit signal
- 2 ターン目のシステムプロンプトが前ターンの草稿を含む（連続性検証）

11/11 ファイル全てクリア；新しいファイルは単独で 17/17。

### 統合検証（ICA Sonnet 4.6）

workspace は calc.py（add/subtract）+ test_calc.py を準備。

**R1**：`enter_plan_mode()` → `plan_chat("calc.py に multiply(a,b) 関数と対応するテストを追加")`
- LLM は read_file で calc.py / test_calc.py を参照
- update_plan_draft は完全な草稿を書き込む（## 目標 / ## 変更ファイル / ## 手順 / ## リスク）
- exit_plan_mode_signal で完了
- 草稿 ~600 字

**R2**：`plan_chat("さらに divide(a,b) を追加、ゼロ除算を処理")`
- LLM はシステム内の前ターンの草稿を見る
- update_plan_draft は **全体を置き換え**（追加ではなく）：草稿は multiply と divide の両方を含む
- リスク段落は ValueError vs ZeroDivisionError の選択について詳しく議論
- 草稿は ~1500 字に拡張

**/approve**：
- 充実した requirement は 1404 字 = 元の R1 ユーザー入力 + 「【承認された実装スキーム - 厳密に従う】」+ 草稿
- plan_mode はオフ、草稿はクリア

**run(enriched, mode="auto")**：
- plan() → code() → test に進む
- LLM は厳密に草稿に従う（**multiply のみを追加、divide は乱して追加しない**——草稿は強い制約）
- テスト rc=0 で成功

**主要な効果の証拠**：
1. **ターン間のコンテキスト保持**：R2 の草稿は R1 に基づいている、ユーザーが要求を繰り返す必要がない
2. **書き込みツール遮断**：R1+R2 中、LLM が見るツールリストに write_file がない、物理的に不可能
3. **草稿は強い制約**：実装段階の LLM は厳密に草稿に従う、計画外の変更を引き入れない

## 評価

P0 エラー回復クローズドループや P1 エンジニアリング基盤と異なり、**Plan Mode はユーザーエクスペリエンスのイノベーション**：

- 「要求を理解する」と「実行する」を分離——ユーザーは LLM が token を消費する前にスキームを見ることができる
- 複数ターンの対話によってスキームを洗練させることは、単一 plan() 出力 JSON より柔軟
- 書き込みツール遮断は **物理的保証** であり prompt 約定ではない——LLM が見えないツールは呼び出されない

### Claude Code との差

Claude Code の Plan Mode にはまだある：
- **終了承認 UI**：承認/拒否/編集の 3 択で、単なる y/n ではない
- **plan 草稿は編集可能**：ユーザーが markdown を直接編集できる、LLM に書き直させる必要がない
- **subagent 探索隔離**：plan 段階で探索が深い場合、子 agent コンテキストはメインラインを汚さない

yansh は現在最小実行可能バージョン、最初の 2 つは main.py に数行追加するだけで補完可能；3 つ目は P2 #9 subagent 実装の後。

### スキーム B との本質的な違い

スキーム B は単一タスク内の plan→exit→approve→implement——一度入ったら y/n を 1 回だけできる。
スキーム C は session レベルのフラグ——ユーザーはスキームが満足するまで繰り返し対話でき、その後に /approve できる。**重要なシナリオ**：ユーザーがスキームを何度も変更してから実行を決定する、このような反復はスキーム B では完成しない。

次の波（このスコープ外）：
- 終了承認 UI：承認/拒否/編集の 3 択
- 草稿手動編集エントリー：`/plan_edit` は $EDITOR で現在の草稿を開く
- approve 後の実装段階が plan() をもう一度実行するかどうか——現在は実行する（enriched requirement で再分解）、将来的には enriched requirement が plan 段階をスキップできる
- plan_chat の token 予算制御（現在は 12 ターンのハード上限のみ、token 予算なし）

# 2026-05-21 公平性の反思 + max_depth タスク再測定

## このノートの主な価値

**実験設計エラーの発見と修正**を記録する — 「成功の比較」を記録するより価値がある。なぜなら、今後の対照実験で同じ過ちを犯さないよう自分自身に注意するからだ。

## 前回の A/B テストの致命的な欠陥

前3回の「Claude Code vs yansh」比較は実際には**不公平**だった：

1. **バグは自分が注入した** — 第2回目の1行のバグは `tools.py:287` にあることを直接知っていたため、デバッグの必要がなかった
2. **タスクは自分が設計した** — 第3回目の max_depth は、ユーザーとの議論を終えたばかりで、「max_depth=1 は最上位層のみをリストする」という ground truth は自分にはあるが、yansh には単なるプロンプトテキストでしかない
3. **コードベースは既に熟知していた** — セッション全体で数時間チャットしており、yansh-code の内部構造は完全に記憶している一方、yansh は冷起動で最初のタスク1文のみを目にする

したがって「Claude Code は X ステップ、X 秒かかった」というデータはすべて、**カンニング選手 vs 完全な白紙状態の選手**の比較データであり、使用できない。

## どの結論が有効で、どの結論が無効か

| 結論 | 有効か | 理由 |
|---|---|---|
| yansh の review ループが無限ループする | ✅ 有効 | アーキテクチャの問題で、自分のカンニングに無関係 |
| yansh は過度に機能を発揮する（無関係なコードを変更） | ✅ 有効 | プロンプトの問題で、自分のカンニングに無関係 |
| yansh の実装と テストが矛盾している | ✅ 有効 | plan/code プロトコルの分裂で、自分のカンニングに無関係 |
| 「Claude Code は 5 ステップ、30 秒かかった」などの具体的な数字 | ❌ 無効 | 完全に誇張されたデータ |
| 「Claude Code は yansh より 9 倍高速」 | ❌ 無効 | 同上 |

## 公平なテスト方案：subagent を実行

Agent ツールを使って general-purpose subagent を起動し、**タスクの原文とプロジェクト位置のみを提供**し、以下を伝えない：
- これが A/B テストであること
- yansh がどのように対処したか
- タスク内の隠れた落とし穴（例：dispatch を変更する必要）
- 答えやヒント

subagent には現在のセッションコンテキストがなく、yansh と同様に**冷起動**で探索するしかない。

## 最初の公平テスト結果（Opus 4.7 subagent vs Sonnet 4.6 yansh）

タスク：「list_files ツールに max_depth パラメータを追加（max_depth=1 は最上位層のみをリスト）。tools.py + tools_schema.py を変更し、単体テストを追加。」

| 次元 | subagent (Opus) | yansh (Sonnet) |
|---|---|---|
| 実行時間 | 99s | 242s |
| ツール呼び出し | 16 | 39 |
| 変更ファイル数 | 3 | 4 |
| 実装は正確か | ✅ はい | ❌ off-by-one エラー |
| 単体テストは通過するか | ✅ | ❌ 自分のテストと実装が矛盾 |
| **agent.py dispatch を変更したか** | ❌ **見落とし** | ✅ 変更（review ループで追跡） |
| タスク判定 | 完了 | 失敗 |

**モデルの不一致**はこの回でも残存する欠陥 — Opus は Sonnet より強力だが、差の中でモデル能力が占める割合と、アーキテクチャ/プロンプトが占める割合は不明確。次回は sonnet subagent で再実行すること。

## 本当に興味深い発見：双方が異なる方向のバグを見落とした

**subagent (Opus) は正確な list_files を書いた** — ユーザーの原話を単純なフィルタに直訳し、ロジックは堅牢だった。  
**しかし subagent は agent.py の dispatch を見落とした** — `list_files` は dispatch で硬コードされており、パラメータが渡されないため、LLM がツールを使用する際 max_depth は依然として無視される（単体テストは通るが、これはテストが関数を直接呼び出し、dispatch を迂回しているから）。

**yansh (Sonnet) の実装は間違っていた** — 剪定ロジックが off-by-one エラー。max_depth=1 で実際には最上位層と第1レベルのサブディレクトリが返される。  
**しかし yansh は dispatch バグを見つけた** — review/fix ループの多ラウンド反復で追跡したため。

この非対称性は深刻な問題を露呈している：

### 洞察：**subagent に「フルチェーン意識」が不足**

エンジニアが関数シグネチャを変更した後、すべての呼び出しポイントで grep を実行するのは当たり前だ。しばしば subagent はこの習慣がない — タスクの表現に厳密に従う（「tools.py + tools_schema.py を変更し、テストを追加」）が、主動的に境界外のチェックはしない。

yansh の review/fix ループは「フルチェーン意識」の**醜い補償メカニズム** — フルチェーンを主動的に審視するインテリジェンスはないが、「タスクが失敗したら何度も再試行」という愚直な方法がある代わりに、実は問題を発見した。

→ ROADMAP P0 #2 に新しい条款を追加（_CODER_ROLE 向け）：
> 関数シグネチャを変更（パラメータの追加削除）する場合、すべての呼び出しポイントで grep を実行し、新しいパラメータが正しく渡されることを確認する。関数本体とスキーマの変更だけで終わらないこと。

このルールの本質は、LLM に**タスク表現を厳密な境界として扱わないよう教える** — タスクで X を変更するよう指示されても、X のすべてのユーザーが対応できることを確認する必要がある。

## yansh の「フルチェーン意識」の反思

前2回のノートで、yansh が「dispatch バグを発見した」ことを yansh の長所と見なしていた。今回改めて見直すと：

**yansh は「主動的にフルチェーンを審視した」わけではなく、「バグが出た後、無限ループの中で偶然発見した」** 。

yansh の実装が最初から正確だったなら、agent.py を再度確認することはなかっただろう。つまり、この「長所」は実は review/fix アーキテクチャの副産物であり、yansh 設計の本来の意図ではない。

→ このことで reviewer アーキテクチャへの見方も変わった。**reviewer を削除したとき、「減法の勝利」と言ったが、reviewer の無限ループで時々追加情報が出ることに気づいた**。reviewer を削除した後、yansh の fix-test ループで最初のパスが通過したら再度反復することなく、「運が良ければバグを発見」する機会は失われる。

しかしこれは reviewer を保持する理由にはならない — **フルチェーンを主動的に審視する**ことは、prompt で coder に教えるべき問題であり、「エラー + ループ」の運頼みメカニズムに依存すべきではない。Claude Code の subagent もこれをやっていないことから、Anthropic の prompt にもこれについての特別な教示がない。**これは LLM agent 全体の共通の盲点**だ。

## 総括的思考

1. 対照実験を設計する時、**決してLLMに自分自身をテストさせないこと** — それは答えを知っている
2. A/B テストを実行する場合、subagent を起動して冷起動する必要がある。モデルもアライメントが取れている必要がある
3. 単一のテストでは全体は見えない — 双方が異なる方向のバグを見落としているため、**複数タスクのカバレッジ**によって初めてあり方が明確になる
4. yansh の review/fix は醜い補償メカニズムで、バグを発見できるが効率が低い。正解は prompt で coder に主動的にフルチェーンを審視するよう教えることだ
5. 公平なテスト自体がテスト結果より記録する価値がある — このような「自分は何を間違えたのか」という反思こそが、shadow ノートの真の価値だ

## 第2回の公平テスト：Sonnet subagent vs yansh（同一モデル）

モデルの差を排除するため、subagent を再実行する時に明示的に `model: sonnet` を指定。

### 3者完全比較

| 次元 | Sonnet subagent | Opus subagent | yansh (Sonnet, mode=code) |
|---|---|---|---|
| アーキテクチャ | 単 agent | 単 agent | plan/code/test 複数ステージ |
| 実行時間 | 134s | 99s | 242s |
| ツール呼び出し | 23 | 16 | 39 |
| 変更ファイル数 | 3 | 3 | 4 |
| 実装は正確か | ✅ | ✅ | ❌ off-by-one |
| 単体テストは通過するか | ✅ | ✅ | ❌ 実装とテストが矛盾 |
| **agent.py dispatch を変更したか** | ❌ 見落とし | ❌ 見落とし | ✅ 変更（fix ループの副産物） |
| タスク判定 | 完了 | 完了 | 失敗 |

### モデルの差を排除した後の真の結論

1. **同モデル（Sonnet）下で、yansh は subagent より 1.8 倍遅く、70% 多くのツール呼び出しをしているのに、それでも間違っている**
   - 1.8 倍遅いのは**アーキテクチャの差**（plan/code/test 複数ステージ直列 vs 単一 agent）
   - ツール呼び出しが多いのは**プロトコルの差**（ロール間で情報を渡す際に上下文を再度読み込む必要がある）
   - 実装エラーは **plan→code 上下文の分裂** — Sonnet モデルが不十分ではなく（同じモデルの subagent は正確に実装した）

2. **dispatch 変更見落としはすべての LLM agent の共通の盲点**
   - Opus subagent が見落とし → Sonnet subagent が見落とし → モデル能力の問題ではない
   - **フルチェーン意識の盲点**：LLM agent は一般的にタスク表現を厳密に実行し、主動的に境界外のチェックはしない
   - **Anthropic の Claude Code subagent も解決していない**

3. **yansh の「dispatch を発見した」ことは補償メカニズムの副産物**
   - 主動的なフルチェーン審視ではなく、impl が間違っていたため、fix ループが反復的に追跡した結果
   - 100秒以上費やしても最終的には失敗と判定。効率が極めて低い
   - **しかし確実に subagent が見逃した問題を捕捉した**

4. **Sonnet subagent の「落とし穴を自検」は単一 agent 設計の強みを示す**
   - subagent の報告：「最初 `>= max_depth` を誤って書きましたが、自分で対象テストで問題を発見し、`>= max_depth - 1` に修正しました」
   - **自己検証ループが同じコンテキスト内で発生** — これは単一 agent 設計の中核的な強み
   - yansh の mode=code ではこのような自検がない（その「テスト」は自分の汚染を受ける）

### 前の認識 vs データが示すこと

| 前の考え | データが示すこと |
|---|---|
| Claude Code は yansh より 9 倍高速 | **同モデルで単一 agent は複数 agent より約 2 倍高速** — 9 倍はカンニング選手の詐欺データ |
| reviewer は yansh の中核的問題 | reviewer は削除されたが**アーキテクチャの差は残っている** — plan/code/test 複数ステージも単一 agent より遅い |
| yansh の「フルチェーン意識」は長所 | それは fix ループの副産物。**Claude Code も同様にフルチェーンを主動的に審視していない** |
| モデル能力が重要な変数 | **アーキテクチャ + prompt > モデル** — 同じ Sonnet で yansh は遅くて間違い、subagent は速くて正確 |

### ROADMAP への優先順位調整

| ROADMAP 項目 | 調整 |
|---|---|
| P0 #2 prompt 最適化 | **最初の項目を上げる**：「関数シグネチャ変更時は必ずすべての呼び出しポイントで grep を実行」 — Claude Code subagent も解決していない共通の盲点、yansh が正確に対応できたら実は先頭に出られる |
| P0 #3 エラー回復クローズドループ | **優先度を下げる** — subagent はこのメカニズムなしでも十分実行できる。「フルチェーン意識を主動的に」「plan/code プロトコルの分裂を減らす」ことができれば、エラー回復の需要は大幅に減少 |

新しい洞察：**アーキテクチャのアップグレード（単一 agent 化 + prompt でフルチェーン意識を教える）** はエラー回復クローズドループより ROI がはるかに高い。

# P3 修正（テスト品質の真の測定 + クロスプラットフォーム CI）

[_26](./2026-05-22_26-p2-fixes.md) から引き継ぎ：P2 完了後に P3 を実施――3人の reviewer が共同指摘した「テスト偽陽性」問題に加えて、クロスプラットフォーム CI のギャップ。

## P3-1: hooks timeout テスト改 psutil pid 死亡アサーション

### 脆弱性

`test_run_one_hook_timeout` 現在のアサーション：
```python
assert "_hook_error" in result
assert "超时" in result["_hook_error"]
assert elapsed < 5
```

「メインスレッド 1s 後にエラー返却」の検証のみ――**プロセスツリーが実際に強制終了されたかは検証しない**。`procutil.kill_tree` 実装に誤りがある場合（例：taskkill パスの誤り、psutil 未インストール）、子/孫プロセスが残留してオーファンプロセスとなるが、メインスレッドは依然 timeout を返し、テストは依然成功する。

Claude / Codex 両者が明確に指摘：これは「偽陽性テスト」――CI の成功は kill が実際に有効であることを保証しない。

### 修正

新しい `test_run_one_hook_timeout_kills_process_tree` を追加：
1. hook コマンドは Python スクリプト：自分の PID をマーカーファイルに書き込み、その後 Python 孫プロセスを spawn（sleep(60) 実行、孫プロセスも自分の PID をマーカーに記録）し、自分もスリープ(60)
2. timeout=1s でトリガーされ hook がエラーを返す
3. テストがマーカーファイルから親 + 孫の PID を読み込む
4. **psutil.pid_exists(pid) で両 PID が生存していないことを検証**
5. フォールバック清理（アサーション失敗時に残留プロセスが後続テストに影響しないように）

これは真のエンドツーエンド検証――`procutil.kill_tree` の退化（例：taskkill /T 無効化、psutil.Process が孫を列挙できない）が起こると即座にテスト失敗になる。

既存の `test_run_one_hook_timeout` は変更なし――メインスレッド 1s 内での返却の高速 sanity check として依然価値がある。

### 検証

新テスト成功、hook スイート 30 → 31 全て成功。

## P3-2: `test_run_subagent_max_steps_clamped_to_hard_cap` 真の hard cap テスト

### 脆弱性

Codex が発見した偽陽性：
```python
def fake_llm(msgs, **kw):
    call_count["n"] += 1
    return _mk_resp(content=f"step {call_count['n']}")  # tool 呼び出さず、静かに終了
...
res = agent._run_subagent("永遠に終わらないタスク", max_steps=999)
assert res["steps"] <= 16
```

第 1 ラウンドの LLM が content のみを返す（tool_call なし）→ 子 agent ループが「静かな終了フォールバック」パスを通り、2 ステップで終了。`assert steps <= 16` は永真だが**実際には cap に到達しない**。将来 `_SUBAGENT_HARD_CAP` が 100 に変更されたとしても、テストは発見できない。

### 修正

fake LLM が毎ラウンド read_file tool_call を返すように修正――決して静かに終了させず、ループは max_steps のフォールバックでのみ終了：

```python
def fake_llm(msgs, **kw):
    call_count["n"] += 1
    return _mk_resp(tool_calls=[
        ("c" + str(call_count["n"]), "read_file", {"filename": "f.py"})
    ])

res = agent._run_subagent("永遠に終わらないタスク", max_steps=999)
assert res["steps"] == agent._SUBAGENT_HARD_CAP   # 正確に等しい
assert call_count["n"] == agent._SUBAGENT_HARD_CAP
```

正確に等しい（== ではなく ≤）――cap が真に有効な場合、ステップ数と LLM 呼び出し回数はちょうど 16；cap の退化（例：32 に変更）は即座に検出される。

### 検証

`test_subagent.py` 35/35 全て成功；新しいアサーション強度は「≤ 16 だが ≤ 16 は全て成功」から「正確に 16、cap の退化は即エラー」にアップグレード。

## P3-3: GitHub Actions ubuntu-latest matrix

### 脆弱性

以前は CI 設定がなく――`tests/run_unit.py` はローカル Windows 環境でのみ実行。サブプロセス管理/プロセスツリー kill には 2 つのパス：
- Windows：`CREATE_NEW_PROCESS_GROUP` + `taskkill /F /T` + psutil
- POSIX：`start_new_session=True` + `os.killpg(SIGKILL)` + psutil

POSIX パス**テストカバレッジ 0**――`procutil.kill_tree` の `killpg` ブランチは psutil 未インストール時のみ動作するが、単体テストは全て psutil をインストール済みのため、フォールバックは絶対に テストされない。psutil パスは Linux でも動作するが、Linux 上で psutil が `children(recursive=True)` を正しく実行できるか実際にはテストされていない。

### 修正

新規 `.github/workflows/unit-tests.yml` を追加：
```yaml
strategy:
  matrix:
    os: [ubuntu-latest, windows-latest]
    python-version: ["3.11"]
```

Linux + Windows matrix で同じ `tests/run_unit.py` を実行。20 のテストファイルには：
- `test_procutil.py`：5 つのエンドツーエンドプロセスツリー kill テスト
- `test_mcp.py`：1 つのエンドツーエンド真実の Python 親子プロセス起動 + psutil による孫 pid 死亡検証
- `test_hooks.py`：P3-1 追加 1 条 + stdout cap エンドツーエンド 1 条

これらは全て Linux で実行され、POSIX パス + psutil の Linux 動作を検証。

`requirements.txt` / `pyproject.toml` に `psutil>=5.9.0` を追加――以前はテストの暗黙的依存だが、現在は明示的に指定。本番コード `procutil.py` / `mcp_client.py` は既に使用中であり、メイン依存関係に追加がより正確（以前の `try: import psutil except ImportError` フォールバックは未インストール時の安全弁として残す）。

### 検証

- ローカル `python -c "import yaml; yaml.safe_load(...)"` で YAML 構文 OK を確認
- Push 後 GitHub Actions が自動実行、結果が commit status に表示される
- macOS は未追加（Codex / Claude 両者が当面延期可能と認識）――Push 後 Linux が本当に成功するか確認してから判断

## 学んだこと

### 「テストカバレッジ ≠ テスト有効性」

P3-1 と P3-2 は同じ問題：テストコード量は合格だが、目標動作を真に検証していない。2 つの一般的なトラップ：
1. **Mock が過剰**（P3-2）：fake LLM が目標に到達しない高速パスを通り、目標動作が全くトリガーされない
2. **アサーション不十分**（P3-1）：`elapsed < 5` のような「上界アサーション」は kill 失敗時も成立し、重要な不変量を追跡できない

**経験**：各テストを書く際に自問――「もし目標実装を no-op に変更したら、このテストはそれでも成功するか？」成功するなら、テストは偽陽性。

### `正確に等しい` は `小以下` より強力

P3-2 が `assert steps <= 16` を `assert steps == _SUBAGENT_HARD_CAP` に変更。差は微細に見えるが――前者は ≤ 16 の任意実装を許可し、後者は具体的なセマンティクスをロック。**cap はちょうど満杯まで使用され、上界ではなく実際の仕様**――これは実装詳細ではなく仕様。

### POSIX vs Windows プロセスセマンティクス差は「正しく見える」に頼ってはいけない

`os.killpg` は Linux/macOS で完全に同じ動作ではない（macOS のプロセスグループリーダーへの kill シグナルは全グループメンバーに伝播、Linux でも基本的に同じ；ただし setsid で作成した新 session リーダーのみがプロセスグループリーダー――`subprocess.Popen(start_new_session=True)` は既に自動 setsid）。

**そのプラットフォームで実行していない = テストしていない**――CI matrix は最低限のコスト検証。10 行の yaml で「Windows でのみ実行」の盲点を解決できるのは、100 行の互換性論争より価値がある。

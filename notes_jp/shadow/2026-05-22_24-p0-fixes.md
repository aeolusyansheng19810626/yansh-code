# P0セキュリティ修正（Codex reviewで発見された2つのP0）

[_23](./2026-05-22_23-three-reviewer-findings.md)に続いて：3つのreviewerのうち、Codexだけが2つのP0深刻な脆弱性を発見しました。本ノートでそれらを修正します。

## P0-1: audit モードが `dispatch_subagent(role="general")` でバイパスされる

### 脆弱性

`yansh audit` モードは読み取り専用を約束し、LLMはファイル書き込みやコマンド実行を行うべきではありません。しかし：
- `tools_schema.py:459` の `dispatch_subagent` は `READONLY_TOOL_NAMES` に含まれている
- `agent.py:916` の audit はツール名でのみブロック → `dispatch_subagent` が許可される
- `agent.py:1978-1979` の general role サブagentが `all_names - blocked`（`write_file`/`execute_command` を含む）を取得
- `agent.py:2051` `dispatch_mode = "audit" if role in ("explorer","auditor") else "auto"` ← general は auto で実行
- `agent.py:2077` で HIL/confirm は全て禁止

PoC：audit モード下でLLMが `dispatch_subagent(task="write pwned", role="general")` を呼び出す → サブagentが実際にディスクに書き込み。

### 修正

`agent.py:_dispatch_tool_call_inner` で `dispatch_subagent` のルーティング時に強制ダウングレード：

```python
if name in readonly_handlers:
    if name == "dispatch_subagent" and mode == "audit":
        req_role = args.get("role", "explorer")
        if req_role not in ("explorer", "auditor"):
            console.print(f"[security] audit context: subagent role '{req_role}' を 'auditor' に強制ダウングレード", ...)
            args["role"] = "auditor"
    result = readonly_handlers[name](**args)
```

5行のパッチ。auto/code/fix モードは変更なし、audit親コンテキストでのみダウングレード。

### 検証

`tests/unit/test_subagent.py` に4つのユニットテストを追加：
- `test_audit_mode_forces_general_subagent_to_auditor`：audit + general → ダウングレード auditor ✅
- `test_audit_mode_keeps_explorer_role_unchanged`：audit + explorer → 変更なし ✅
- `test_audit_mode_keeps_auditor_role_unchanged`：audit + auditor → 変更なし ✅
- `test_non_audit_mode_keeps_general_role`：auto + general → ダウングレードなし（過剰修正防止）✅

エンドツーエンド `test_audit_mode_subagent_cannot_write_file_e2e`：実際にLLM loop を実行（mock LLMが write_file tool_call を返す）→ audit モード下のサブagentがファイル書き込みを試みる → ファイルが作成されない ✅

`test_subagent.py` 34/34 通過。

## P0-2: プロジェクトレベルの `.yansh/{mcp,hooks}.json` は無確認 RCE

### 脆弱性

- `mcp_client.py:264` workspace がまず `.yansh/mcp.json` をロード → 直接 `Popen(command, args)`
- `hooks.py:80` workspace がまず `.yansh/hooks.json` をロード → `subprocess.run(cmd, shell=True)`
- trust確認なし

PoC：悪意のあるrepoが `.yansh/hooks.json`（UserPromptSubmit トリガー）をコミット、ユーザーが clone + `yansh` + 初回入力 → 任意コマンド実行。**典型的なサプライチェーン攻撃面**——audit バイパスより危険（LLM協力不要）。

### 修正

新規モジュール `workspace_trust.py`：
- `is_trusted(workspace_dir)`：`~/.yansh/trusted_workspaces.json` ホワイトリストをチェック
- `mark_trusted(workspace_dir)`：ホワイトリストに書き込み
- `check_or_prompt(workspace_dir, config_filename)`：ロード前に呼び出し、許可を決定
- env var `YANSH_TRUST_PROJECT_CONFIG`：
  - `always`：常に信頼（CI / テスト / 自分の開発マシン）
  - `never`：常に拒否
  - 未設定/`auto`：trust ファイル + 対話的 prompt

動作：
- デフォルトでプロジェクトレベル設定を拒否；`~/.yansh/{mcp,hooks}.json` のみをロード
- 対話モード初回時に大文字の warning + `(y/N)` prompt を表示、y でtrust ファイルに書き込み
- 非対話モード（CI / pipe）はデフォルト拒否、env var で明示的にオプトイン必須
- trust ファイル破損 → fail-safe で False を返す

`mcp_client.load_config` / `hooks.load_config` を再実装：未trust → フォールバック全体；trust → プロジェクトレベルをオーバーライド。

### 検証

`tests/unit/test_workspace_trust.py` 19条のユニットテスト：
- `is_trusted` / `mark_trusted` 永続化（4条）
- `check_or_prompt` 7ブランチ：always / never / no_proj_file / auto+trusted / auto+非対話 / auto+y / auto+n / EOF
- 破損した trust ファイル fail-safe（1条）
- `mcp_client.load_config` 未trust フォールバック / trust ロード（2条）
- `hooks.load_config` 未trust フォールバック / trust ロード（2条）
- **エンドツーエンド攻撃シミュレーション**（2条）：
  - `test_e2e_evil_repo_user_prompt_hook_not_executed`：悪意のあるhooks.json が pwned マーク書き込み → trust 拒否 → マークが書き込まれない
  - `test_e2e_evil_repo_mcp_server_not_started`：悪意のあるmcp.json が60s server 起動 → trust 拒否 → 起動なし

19/19 通過。`test_mcp.py` / `test_hooks.py` に各1箇所 `monkeypatch.setenv("YANSH_TRUST_PROJECT_CONFIG", "always")` を追加して新trust モデルに適応、27/27 + 28/28 全て通過。

## 学んだこと

### Codex独占発見の2つのP0がreviewの真実の価値

Gemini / Claude はこれら2つを見落とした：
- **audit バイパス**：信頼境界が交差すると（audit モード信号 → subagent ツールセット）、LLMは最も弱い場所を貫通しようとします。Claude はsubagent実装を見ましたが、audit 信号伝播チェーンを追跡しませんでした
- **プロジェクト設定 RCE**：「リポジトリコード経由の実行可能エンティティ」です。Gemini は hooks shell injection を誤報しましたが、真の攻撃面（hooks.json 自体が攻撃ベクトル）を見落としました

**結論**：複数のreviewer は冗長ではありません——単一のreviewer は最大60-70%の真の問題しかカバーできず、残りの30-40%は cross-check が必須です。

### Trust モデルの設計トレードオフ

**なぜデフォルト拒否 + ユーザーopt-in？**
- VS Code / GitHub Codespaces が同じ "Workspace Trust" アプローチを使用
- デフォルト信頼 = サプライチェーン攻撃フリーパス（git clone が即RCE）
- デフォルト拒否 = ワンタイム追加操作だが、セキュリティモデルが明確

**なぜenv var + trust ファイルの二重トラック？**
- env var はCI / 自動化に適した（一度設定したら長期有効）
- trust ファイルは人間ユーザーに適した（per-workspace 粒度、撤回可能）
- 両方を並存させることで単一メカニズムの盲点を回避

**なぜ対話的 prompt が非対話で拒否？**
- 非対話モード（pipe / CI / batch）では誰も prompt に答えられない → デフォルト動作として「拒否」が安全
- CI でプロジェクト設定をロードしたい → 明示的に `YANSH_TRUST_PROJECT_CONFIG=always` を設定、意図が明確

### エンドツーエンドテストの価値

**E2Eテストを追加する価値**：
- `test_e2e_evil_repo_user_prompt_hook_not_executed` は実際の `python -c "open(file).write('PWNED')"` コマンドで攻撃をシミュレート
- mock の「load_config が空を返す」ではなく、悪意のあるコマンドが実行機会を持たないことを真に検証
- このようなテストは単体テスト load_config より説得力があり、回帰コストが低い

# P2 #9 サブ Agent / タスク分配

[_17](./2026-05-22_17-skills-llm-matching.md) から継続：P2 #8 LLM インテリジェントマッチング完了後に #9 を実施。
ROADMAP ではこれを LLM agent 設計の**主要アーキテクチャコンセプト**としており、完成すると agent ツール理解が次のレベルへ進む。

## 目標

サブ agent の中核的価値は**コンテキスト隔離**：独立した LLM context で探索/重作業を実行し、
親 agent はサマリーのみを見て、中間の read_file/grep の全量コンテンツは見ない。
長い session では大規模 codebase で寿命を 5-10 倍延ばせる。

## 改善内容

### 1) tools.py に `dispatch_subagent` sentinel を追加

```python
def dispatch_subagent(task, role="explorer", max_steps=8):
    return {"_subagent_dispatch": True, "task": ..., "role": ..., "max_steps": ...}
```

task_complete / update_plan_draft と同じ sentinel パターン——LLM 呼び出し時にマーク返却、
実際のロジックは agent モジュール内（循環 import 回避：tools は llm_client に依存しない）。

### 2) tools_schema.py

- `dispatch_subagent` schema を追加：`role` は enum `["explorer", "general", "auditor"]`
- `READONLY_TOOL_NAMES` に追加——こうすることで audit/plan mode の主 agent も使用可能（サブ agent が workspace を修正しない仮定を満たす：role=explorer 時は純粋に読取のみ；role=general は LLM の明示的な申請）

### 3) agent.py コア：`_run_subagent(task, role, max_steps)`

モジュールレベルの状態：
```python
_IN_SUBAGENT: bool = False           # 再帰ロック
_SUBAGENT_STATS: dict = {...}         # process ライフサイクル累計
_SUBAGENT_HARD_CAP: int = 16         # max_steps 上限
```

ツールセット マッピング（物理隔離による再帰防止）：
| role | ツールセット |
|---|---|
| explorer / auditor | READONLY_TOOL_NAMES - {dispatch_subagent, plan_mode_sentinels} |
| general | ALL - {dispatch_subagent, plan_mode_sentinels} |
| 不明 role | fallback explorer |

**全 role のツールセットに dispatch_subagent は含まない**——二重保険（_IN_SUBAGENT フラグ + 物理フィルタリング）。

サブ agent ループは plan_chat の多ラウンド テンプレートを再利用：
- 独立 messages（親 agent の conversation_history と混在しない）
- 独立 system prompt（_SUBAGENT_ROLE + workspace トップレベル構造）
- task_complete によるトリガー success/summary 抽出
- サイレント終了時の フォールバック（追問一度、やはり応答がない場合は content を summary に）
- finally ブロックで _IN_SUBAGENT リセット保証（LLM エラー時も）

### 4) ハンドラー登録

```python
readonly_handlers = {
    ...
    "dispatch_subagent": _subagent_handler,
}
```

`_subagent_handler` は `_run_subagent` を呼び出し、浅 dict を親 agent に返却：
```json
{"success": bool, "summary": str, "steps": int, "role": str}
```

### 5) main.py に `/subagent stats` を追加

本 session の累計を表示：calls / total_steps / 最近のタスク / summary / role / success。

**シナリオ 3**：LLM が主動的にサブ agent を派遣（エンドツーエンド）
```

              _dispatch_tool_call 署名を検索、その後 summary に基づいて監査結論を出す")
```

サブ agent のサマリー：
> agent.py:4 の `_dispatch_tool_call` 署名は `def _dispatch_tool_call(tool_name: str, tool_args: dict):` で、2 つのパラメータ共に型注釈あり（str/dict）、戻り値型注釈なし。関数本体は readonly_handlers 辞書を管理（"count_lines" のみ登録）、tool_name で路由呼び出し、未知ツールは ValueError を発生。

主 agent (audit) はこれに基づいて監査結論を出力：
- 🔵 低：未知ツール時に ValueError を発生させるべく自定義例外定義を推奨 → UnknownToolError 定義を推奨
- 型注釈が不完全（戻り値型注釈なし）

**主要証拠**：主 agent の audit レポートは**サブ agent の詳細を直接参照**（"未知ツール時に ValueError を発生"、"戻り値型注釈なし"）だが、主 agent は**一度も直接 read_file していない**——サブ agent の 200 字 summary を見ただけ。これがコンテキスト隔離の具体的実装。

### コンテキスト隔離のエンジニアリング意義（実測値）

**シナリオ 3** 実行結果：
- サブ agent 内部：read_file/list_symbols ツール結果は約 800 token
- 主 agent が見る：200 字 summary ≈ 80 token
- 節約比：**10x**

監査タスクが 5 つの異なる関数をチェックする場合、主 agent が直接実施すると 5×800=4000 token 消費；
5 個のサブ agent に派遣後は主 agent は 5×80=400 token のみ。**これが大規模 codebase で 5-10 倍の延命を実現する理由**。

### "コンテナ化"エンジニアリング観点

サブ agent は"タスク実行"を**境界を持つ関数**に抽象化：
- 入力：task 文字列
- 出力：summary 文字列
- 副作用の境界：role=explorer 時は副作用なし；role=general 時は _dispatch_tool_call と同じセキュリティチェック下

これは Unix の fork+exec と同型——子プロセスは独立メモリ空間、親は stdout/exit code のみ参照。
LLM agent はこのパターンを context レベルに引き上げた。

## P1-1: mcp サブプロセス ライフサイクル（reader_loop EOF + shutdown プロセスツリー強制終了）

### 脆弱性 A：`_reader_loop` EOF が pending を起動しない（Codex + Claude）

`mcp_client.py:_reader_loop` は `for line in proc.stdout` ループ。server クラッシュ → stdout EOF → for 終了 → reader スレッド終了。ただし `self._pending` に保留されているすべての `(Event, holder)` は set されない——`_request` の `ev.wait(timeout)` は `_CALL_TIMEOUT_SEC=60s` までデッドロック状態。

LLM が目にするのは「server がダウンした」ではなく「ツールがタイムアウト」——誤診が完全に起きている。

### 脆弱性 B：`shutdown` がひ孫プロセスを強制終了しない（Gemini + Claude）

`mcp_client.py:shutdown` は単に `proc.terminate()`／`proc.kill()` するだけ。npx → node → mcp-server.js というチェーン上のひ孫プロセスが孤児化する。長時間実行シナリオ（ユーザーが複数回 /mcp restart）で孤児 node プロセスが蓄積。

### 修正

**A**：`_reader_loop` に `try/finally` を追加——finally ブロックで `_pending` をすべてエラー応答で set：

```python
finally:
    stderr_tail = list(self.stderr_buffer[-3:]) if self.stderr_buffer else []
    with self._pending_lock:
        for mid, (ev, holder) in self._pending.items():
            if "msg" not in holder:
                holder["msg"] = {
                    "id": mid,
                    "error": {"code": -32000,
                              "message": f"server {self.name} stdout は閉じられています..."},
                }
            ev.set()
```

**B**：Popen にプロセスグループを追加 + shutdown で `_kill_tree` を使用：

```python
# Popen
if _sys.platform == "win32":
    popen_kwargs["creationflags"] = subprocess.CREATE_NEW_PROCESS_GROUP
else:
    popen_kwargs["start_new_session"] = True

# shutdown：graceful をスキップして直接 kill_tree（親がまだ活きているうちに列挙する必要あり）
if proc.poll() is None:
    self._kill_tree(proc)

# _kill_tree：psutil 優先（最も信頼性高），フォールバックはプラットフォーム標準
@staticmethod
def _kill_tree(proc):
    try:
        import psutil
        root = psutil.Process(proc.pid)
        victims = root.children(recursive=True) + [root]
        for p in victims:
            try: p.kill()
            except psutil.NoSuchProcess: pass
        psutil.wait_procs(victims, timeout=2)
    except ImportError:
        # fallback: taskkill /F /T (Win) / killpg (POSIX)
        ...
```

### 重要な設計上の権衡

**なぜ graceful をスキップして直接 kill_tree するのか？**

最初は `terminate() + wait(2)` で graceful 終了を試し、タイムアウト後に `_kill_tree` という方法を試みた。問題：親プロセスが graceful 終了する可能性がある（wait 成功）が、ひ孫プロセスは独立した sleep で影響を受けない。親退出後に `psutil.Process(pid)` が NoSuchProcess をスロー——ひ孫リストが失われ、ひ孫がメモリリーク。

正解案：**親プロセスが活きているうちにひ孫リストを列挙する**。`children(recursive=True)` は親がまだ生存している場合に呼び出す必要があります。したがって stdin をクローズ（server に終了シグナル）してから直ちに `_kill_tree` を実行し、graceful の機会を与えません。

MCP server も強制的にクローズ可能として設計（stdin クローズはプロトコルレベルのシグナル）で、graceful クリーンアップは不要。

**なぜ psutil 優先で taskkill /T ではなく？**

Windows の `subprocess.Popen + CREATE_NEW_PROCESS_GROUP` は Job Object を構成しない——子プロセスが `Popen → Popen` 派生時、ひ孫は親の「プロセスツリー」に含まれない。`taskkill /T /PID parent_pid` はひ孫を見つけられない。

一方 `psutil.Process.children(recursive=True)` は OS のプロセス親子関係チェーンを辿る——本当に「全ツリーを見る」ことができます。Linux/macOS では `killpg` が信頼でき、psutil も動作。したがって psutil はクロスプラットフォーム一貫性で最も信頼できるソリューション。

## P1-2：`memory.find_memory` パストラバーサル

### 脆弱性

`memory.py:141` は直接 `f = d / f"{name}.md"` で `_slugify` なし。`save_memory` は slugify で安全、**read パスのみ不安全**。

PoC：`recall_memory(name="../../README")` → `<workspace>/.yansh/memory/../../README.md` = `<workspace>/README.md` に構成、workspace 任意の .md ファイルを読取可能。

### 修正

```python
def find_memory(name, workspace_dir=None):
    name = str(name).strip()
    if not name:
        return None
    slug = _slugify(name)   # 新規：save と一貫
    for d, scope in (...):
        f = d / f"{slug}.md"
```

## P1-3：tree-sitter `_TS_PARSER` 並行非安全

### 脆弱性

`tools.py:691` の `_TS_PARSER` はモジュールレベルシングルトン、遅延初期化でロックなし；`tools.py:743/581/792` 3 箇所の `parser.parse(src_bytes)` スレッド間共有。tree-sitter Python バインディングの Parser は**スレッドセーフではない**——並行 subagent が `agent.py:1995 workspace_symbols()` を起動時すべてが parser に競合、コールドキャッシュ下ではデータ汚損が発生可能。

### 修正

グローバルロックを追加して parse 呼び出しを直列化：

```python
_TS_PARSER_LOCK = threading.Lock()

def _load_ts_parser():
    if _TS_PARSER is not None:
        return _TS_PARSER, None
    with _TS_PARSER_LOCK:
        # double-check
        if _TS_PARSER is not None:
            return _TS_PARSER, None
        # ... init
        _TS_PARSER = Parser(py_lang)

def _ts_parse_locked(parser, src_bytes):
    with _TS_PARSER_LOCK:
        return parser.parse(src_bytes)
```

3 箇所の `parser.parse(src_bytes)` を `_ts_parse_locked(parser, src_bytes)` に変更。

### 設計上の権衡

**なぜ thread-local parser ではなく単一ロック？**

thread-local は「洗練」に見える——各スレッドが独自 parser で、ロックなし。しかし：
1. tree-sitter Parser init は低コストではない（~50ms grammar ロード）
2. yansh 並行シナリオ：典型的に ≤4 subagent が同時 parse
3. 単回 parse は通常 < 10ms

**アルゴリズム**：4 並行スレッド × 10ms parse = 直列総 40ms（単一ロック使用）vs 4 × 50ms init + 4 × 10ms parse = 240ms（thread-local）。**単一ロックの方が高速**。

将来 yansh が大量並行 parse（例：background indexer）を行うようになれば、thread-local に切り替えることも可能。

## 3 つの P1 共通の設計教訓

### 1. 「graceful 終了」vs 「強制完結」——サブプロセス管理の重要な権衡

最初のバージョンの `shutdown` は server を graceful 終了させようとした（terminate + wait）が、ひ孫プロセスが親の graceful シグナルに応答しないことを考慮していない。**サブプロセス管理は常に最悪を想定：プロセスツリーが深い、シグナルに応答しない、sleep がある**。

正しいパラダイム：
- シグナルを送信（stdin クローズ / SIGTERM）して良民が自ら終了するよう
- 極めて短いタイムアウト（≤1s であり ≤60s ではなく）
- その後**無条件で kill_tree**——待たない

### 2. パス検証：slugify + resolve() 二重保険

slugify のみでは不十分（`../../X` は防ぐが symlink 攻撃を防がない）；
resolve() のみでも不十分（symlink は防ぐが、slugify で防いだ字義的な `../` をブロックしない）。
**両者の組み合わせで初めて完全**——限界効用コスト 5 行コード。

### 3. スレッド間共有オブジェクトの「見かけ上の安全性」罠

tree-sitter Parser の `parse()` は純粋関数に見える（入力 src_bytes 出力 tree）——ただし Parser インスタンス内部に可変状態あり。この種の「見かけ無状態だが実は状態持ち」ライブラリは非常に一般的——SQLite connection、numpy random、re.compile キャッシュ。

**経験則**：**サードパーティライブラリインスタンスがスレッド間共有される場合は必ずスレッドセーフティ文書を確認**——文書が明確に thread-safe と記載されていなければ、デフォルトで非安全。ロック 1 つで包むコストは小さく、データ汚損リスクを回避。

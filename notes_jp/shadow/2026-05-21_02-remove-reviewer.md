# 2026-05-21 architecture: 独立 reviewer agent を廃止する

## 背景

[list-tools ノート](./2026-05-21_01-list-tools.md) の A/B 比較の後に 2 回目のバグ修正比較を行ったところ、
yansh の reviewer セクションで無限ループが発生していることが判明——しかし coder の初回は実は既に正しく修正していた。

さらに追問：**Claude Code には reviewer ステップがあるか？** 答えはノーである。

## Claude Code の実際のアーキテクチャ

```
単一 agent（1 つの LLM context）
   ↓
混合呼び出し：Read / Grep / Edit / Bash / ...
   ↓
自分でテストを実行して自分で確認
   ↓
完了を報告
```

**ポイント**：すべての情報が同じ対話履歴にあり、agent 自身が完全な記憶を持ち、自身が品質判断を行う。
diff を抽出して「別の自分」にレビューしてもらう必要はない。

## yansh が当初 reviewer を導入した理由

2023-2024 年の LLM agent 業界では multi-agent アーキテクチャ（CrewAI/AutoGen/LangGraph）が流行していた。
「分業協力＝より専門的」というのは聞こえがいいので、yansh は architect → coder → reviewer → tester の 4 つのロールに設計された。

## 実測で判明した根本的な問題

実験タスク：「注入された 1 行のバグを修正する」

### 1 回目（reviewer あり）

- 総実行時間 272 秒、ツール呼び出し 35 回
- coder は 1 回目で正しく修正、テスト合格
- reviewer が拒否：「テストファイルが見えない」→ **read_file を実行していない**が、read_file ツールはそのスキーマに含まれている
- review→fix→review→fix... 6 回の上限
- reviewer の 2 回目で JSON 以外を返す、`_extract_json` 失敗をトリガー
- 最終的に**タスク失敗**と判定（実際はコードはすでに正しい）

### 2 回目（reviewer ループを削除）

- 総実行時間 164 秒（**-40%**）、ツール呼び出し 20 回（**-43%**）
- タスクは**正しく成功と判定**
- ただしまだ遅い——残りのボトルネックは architect の過度な計画 + fix ループ

## 学んだこと

### 1. Multi-agent は無料ランチではない

agent が 1 つ増えるたびに、LLM 呼び出し 1 回 + コンテキスト分断 1 個 + プロトコル脆弱性 1 個が増える。
yansh の reviewer 失敗の全ての原因はアーキテクチャレベルのものである：

| 問題 | 根本原因 |
|---|---|
| 「テストファイルが見えない」 | reviewer には完全な対話履歴がなく、ツール呼び出しへの内発的動機が欠けている |
| JSON 出力の乖離 | reviewer は厳密に JSON を出力する必要があり、モデルが少し発揮するだけで崩壊 |
| 無限ループ | マルチ agent プロトコルに「完了した」という統一信号がない |

これらはすべてプロンプト調整では根治できない——**アーキテクチャエラー**である。

### 2. Claude Code の「退屈なアーキテクチャ」が正解

単一 agent + ツール + 自己検証。multi-agent ほど「先進的」に聞こえないが、
実際の効果は 4 倍の専門分業を圧倒する。

**深い理由**：LLM の推論は完全な context に基づいている。
context を人為的に切断すれば（たとえ「専門分業」のためだとしても）、利益より損失が大きい。

### 3. エンジニアリング文化とツール設計の対比

人間のエンジニアリングチームの PR レビューが有効なのは——reviewer は**本当に別の人間**だからである。
異なる視点、異なる経験、異なる盲点を持っている。

LLM の「reviewer agent」は別の LLM ではなく、**同じモデルが別のプロンプト**を使ったもの。
真の視点の違いはない。いわゆる review は LLM に自分でもう一度見させるのと同等である——
しかし yansh は JSON プロトコルで context を切断したため、むしろ**自分で見させるより悪い**。

### 4. アーキテクチャ簡素化の勇気

コード削除は追加より難しい。
私は reviewer ループコード 47 行 + コメント 4 行を削除した。
yansh の全体的な動作はすぐに改善した。**引き算**は時々**足し算**より ROI が高い。

→ ROADMAP P1 #5（グローバルステート再構築）の精神に対応：複雑さの多くは過度設計の産物である。

## 今回は何を保持し、何を削除したか

| 保持 | 理由 |
|---|---|
| `_REVIEWER_ROLE` 文字列 | 実行時コストを占有しない、将来 `/review` skill を追加する際に再利用可能 |
| `review()` 関数 | 統合テストが使用；独立して呼び出し可能なツールとして保持 |
| `_parse_review_response` | 単体テストが使用 |
| `_TESTER_ROLE` | fix ループは依然としてそれを使用してテスト失敗を分析 |

| 削除 | 理由 |
|---|---|
| `_run()` 内の review_attempts ループ | アーキテクチャエラー、根本的な問題 |
| review 失敗後のユーザー確認ポップアップ | ユーザーがタスク終了ロジックは review から派生したもの、一緒に削除 |

## 後続のバックログ

yansh がまだ遅い残りの理由（ROADMAP 対応順）：

| 現象 | 根本原因 | ROADMAP 項 |
|---|---|---|
| architect が 2 ファイルを計画、実際は 1 つだけ必要 | プロンプトが「未変更リスト」に収束していない | P0 #2（追加済みだが不十分に調整） |
| fix ループ 6 回ハードリミット | ステートマシンがハードコード | P0 #3（エラー回復クローズドループ） |
| coder が無意識に関連のないテストを変更 | 計画が広すぎる + 「タスク境界」制約の欠如 | P0 #2 |

次のステップで **ROI が最大**：ROADMAP P0 #3 を実装（task_complete + token 予算ソフト終了）。
これは「6 回ハードリミットの廃止」の根本的なソリューションであり、今日の reviewer 廃止と同じラインである——どちらも
**LLM 自身にステータス宣言させる**、プロセスをハードコードするのではなく。

## Claude Code vs yansh 完全比較表

タスク：「tests/unit/test_tools.py の test_replace_in_file_multiple_matches が失敗した、修正してください」
（注入されたバグ：`tools.py:287` で `count > 1` を `count == -1` に変更）

両側は **claude-sonnet-4-6** を使用。

| 次元 | Claude Code | yansh 変更前（reviewer あり） | yansh 変更後（reviewer なし） |
|---|---|---|---|
| 実行時間 | **30 秒** | 272 秒 | 164 秒 |
| ツール呼び出し合計 | **5** | 35 | 20 |
| ツール組合 | Bash×3 + Read×1 + Edit×1 | execute×10 / search×9 / read×8 / symdef×3 / replace×3 / list×2 | read×6 / search×5 / execute×4 / symdef×3 / replace×2 |
| タスク結果 | ✅ 完了 | ❌ 失敗（コード実際は正しい） | ✅ 完了 |
| Claude Code との相対値 | 1 倍（ベースライン） | 9.1 倍遅い | **5.5 倍遅い** |

### Claude Code のツール順序（5 ステップ）

| ステップ | ツール | 重要パラメータ |
|---|---|---|
| 1 | Bash | `pytest -v` 具体的な失敗情報を確認 |
| 2 | Read | `tools.py:283-292`（10 行の精密読み） |
| 3 | Edit | `count == -1` → `count > 1` |
| 4 | Bash | `pytest` で修復を検証 |
| 5 | Bash | 全テスト回帰 |

### 変更後 yansh がまだ 5.5 倍遅い理由

reviewer を廃止すれば「無限ループ」と「判定エラー」が解決されたが、基本的な効率ボトルネックは残っている：

1. **architect の過度な計画**：2 ファイルを変更する予定（test + tools）、実際は tools のみ必要
2. **coder が無意識に関連のないコードを変更**：`for l in lines` を `for line in lines` に変更
3. **fix ループ 6 回ハードリミット**：タスクが早期に修正されたとしても、ループはまだ実行中
4. **plan/code/test 3 段階が直列**：各段階は新しい LLM 呼び出しを開始する必要があり、Claude Code の単一 context 内の自然展開と比べてプロトコルオーバーヘッドが増加

→ ROADMAP P0 #2（プロンプト収束 architect 範囲） + P0 #3（task_complete ソフト終了）が次段階の重点。

---

## 3 文の要約

1. Claude Code は独立 reviewer がない——これはアーキテクチャの意図的な選択
2. multi-agent はドキュメントでは美しい、本番では**context 分断 + プロトコル脆弱性**という 2 つのコア問題は解決不可能
3. yansh が reviewer を廃止した後、実行時間は 272 秒から 164 秒に短縮、さらに正しく収束した——**引き算の勝利**

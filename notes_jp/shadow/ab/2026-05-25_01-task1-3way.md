## 主要な差異分析

### 1. cc：直感的探索、最もシンプル

cc subagent のパフォーマンスは「プログラマーがコードを手動で確認」に近い：

```
Grep -l _dispatch_tool_calls    # まずどのファイルに存在するか探す
Grep -C 5 in subagent.py        # 使用方法を探索
Grep -C 3 "def _dispatch_tool_calls" in agent.py   # 定義を特定
Read agent.py:1264-1323         # 関数本体を読む
```

4 つのツール、plan / review / audit ステージなし、直接答えを出力。これは「探索タスク」の形態に最適です。

### 2. yansh：探索タスクが plan agent により「コード修正タスク」に変換

yansh は code mode では、plan agent がこの読み取り専用探索を「agent.py を修正」タスクに無理矢理変換：
- `expected_edits=1, files_modified=["agent.py"]`
- coder は search_in_files を実行後すぐに task_complete を送信（最初の完了 ← 実際の答えはここ）
- しかし plan はまだファイル修正を要求するため、coder は再度 read_file → replace_in_file ×2 で未使用 import 2 行を削除
- pytest 12 passed を実行、再度 task_complete を送信

副作用：**このテストタスク下で yansh は agent.py ファイルを修正**（`get_model_price` と `dispatch_subagent` import を削除）——これら 2 つは確かに未使用ですが、**タスクの範囲外**です。

履歴 task #1 では yansh は audit mode を使用して 2 つのツール（24.5s）のみを実行し、ファイルは変更されていません。**audit vs code は重要な差異**です。

### 3. yscode：bug 修正後「迂回路」に変更、ただし答えはサーフェスされていない

**修正前（PlanFailed bug、既修正）**：architect は循環し、input token を 248K に達し、plan が出ず → exit_code=1、出力なし。

**修正後**：architect は search_in_files + read_file を確認後、「これは探索タスク」と認識し、**空の plan を送信**：
```json
{
  "requirement": "ユーザーが submit_plan を繰り返しリクエストしましたが、実行可能な要件が提供されていません。",
  "files": [],
  "notes": "前のタスクは _dispatch_tool_calls の読み取り専用分析であり、直接回答されました。具体的な機能、バグ修正、またはリファクタリングを説明してください。"
}
```

plan→code→test フローを完了する際、3 つのフェーズすべてが空の操作（code フェーズでファイル変更なし、test フェーズで test コマンドなしでスキップ）、最終的に `success: true`、summary は「all tests pass」。

**問題**：
- 答えは実際に architect のストリーム出力に含まれています（stderr で「dispatch_subagent は ThreadPoolExecutor で並行実行」を確認可能）
- ただし tasklog のトップレベル summary フィールドにはこの答えがなく、stdout JSON にもない
- ユーザーが stdout JSON を見ると答えが見えず、stderr を翻す必要があります

**アーキテクチャの示唆**：yscode 修正後は探索タスクを「ソフトランディング」でき、**「explorer モード」**または**「exploration 直接応答」チャネル**が不足しています——architect が探索タスクを認識したら、答えを summary に明示的に書くことができ、stderr には書かないようにします。

## 注意事項（必読）

1. **mode の不一致による偏差**：今回の三方ともcode mode を使用（yscode に合わせるため）。yansh の履歴 task #1 では audit mode を使用（24.5s / 2 ツール / 副作用なし）、code mode では yansh が plan→coder→test フロー をトリガーし、無関係な作業が増えます。**yansh に不利**。

2. **gateway の差異**：cc は Anthropic API gateway 経由、yansh/yscode は ICA gateway 経由。同名の sonnet 4.6 は両側のバックエンドで動作が若干異なる可能性があります。

3. **ツール集合の差異**：cc subagent のツール集合は Grep/Read/Edit/Write/Bash/Glob/WebFetch のみ；yansh/yscode は search_in_files / get_symbol_definition / dispatch_subagent / replace_symbol などの専門ツールも備えています。ただし今回三方ともAST 関連ツールを使用していないため、影響は軽微です。

4. **yscode .env 互換性問題**：初回実行は直接 404 失敗 —— yscode は `CLAUDE_BASE_URL` が `/v1` で終わることを要求し、yansh リポの .env は `/v1` を含まない（yansh コード内で自動補完）。yscode リポ自身の .env を使用後に実行成功。これは設定エラーではなく、実装の差異です。

5. **PowerShell stdout は UTF-16 LE**：yscode の `task1_stdout.json` は UTF-16 エンコード（PowerShell のデフォルトリダイレクト動作）、後続の解析に影響、ただしデータ自体には影響なし。

6. **task #1 の種類は yscode に不利**：純粋な読み取り専用探索は yscode の multi-agent アーキテクチャの盲点です。後続の task #2-#5 はすべてコード作成タスクで、yscode のパフォーマンスが大幅に改善されることが予想されます。

## 主要な発見

- **アーキテクチャ vs タスク適合度**：cc の「単一 agent + 汎用ツール」は探索タスクに最も適切；yansh 単一フローは code mode で過度に実行；yscode multi-agent は修正後にソフトランディング可能ですが、答えが summary にない。
- **トークンコストは価値を直接反映しない**：yscode 修正後の 65K は三方中等価値 / 最低答え可視性の組み合わせ。yansh 167K は主要タスク正解 + 無害な副作用。cc 50K は直接命中は性能価格比の王。
- **mode 選択は結果に大きな影響**：yansh の audit mode（本テストに含まれず）は历來探索タスクの最適パス——yscode に合わせるため code mode を使用し、この利点を隠した。
- **yscode はまだ explorer 出口が不足**：PlanFailed 修正後、探索タスクは「空の plan 迂回」を使用していますが、アーキテクチャ上、答えを summary に明示的に書く パス が不足しています。後続の task #2-#5 はすべてコード作成タスクで、この辺角をトリガーしません。

# AB Test #5：クロスファイルリファクタリング — yansh code mode vs CC サブエージェント

**題目**：`tools.py:_err(kind, msg, **extra)` に必須の位置パラメータ `tool: str` を追加し、シグネチャを `_err(kind, msg, tool, **extra)` に変更。戻り値 dict に `"tool"` フィールドを追加（エラートレーサビリティ）。全 repo 約64個の呼び出し地点（tools.py 56 / agent.py 4 / subagent.py 1 / test_tools.py 3）を新シグネチャに適応。新しいユニットテストを1つ追加して `result["tool"]` フィールドを検証。

**予想**（task #3 のノートに記載）：yansh の plan→code→fix パイプラインは複数ファイルの統合変更シナリオで反発するはずで、CC の「読む+変更+検証」ループと対比すべき。

**実際**：**予想は完全に逆転**——yansh はハードリミットの分断化により大きく失敗し、CC が完全に勝利。

**CC は全側面で勝利：実行時間 1.7×、tokens 10×、コスト 7.3×、yansh はテスト未完了で失敗**。

## yansh クラッシュの原因特定

stderr 重要イベントシーケンス：

1. **plan フェーズ** ✓：4 ファイル + test_command を列挙（合理的）
2. **Coder フェーズ**：3 ファイル全て「5 ラウンドツール呼び出し上限に達した」——LLM は各ファイルの 5 ラウンド内で 56 / 4 / 3 個の呼び出し地点を全て一括変更できなかった
3. **dispatch_subagent は 7 個を派遣**：しかし stderr に「サブエージェント未宣言 task_complete により切断」が複数表示——サブエージェントも半分故障
4. **fix loop**：attempt 1 でテスト実行 21+ TypeError 失敗 → fix attempt 2 → 「fix は 12 ラウンド上限に達し強制終了」
5. **attempt 3 max 消費 → 終了**

**`_err` シグネチャは正しく変更されたが、56 個の呼び出し地点中 4 個しか適応されなかった**（行 202/204/207/215）。残りの 52 個は `_err("kind", "msg")` のままで位置パラメータが不足し、実行時に全て TypeError。

ツール分布：read_file 64 + get_symbol_definition 16 + search_in_files 14 + execute_command 13 + replace_in_file **7** + dispatch_subagent 7 + task_complete 5 + list_symbols 4 = 130。

**わずか 7 回の replace_in_file** で 4 ファイル変更——ファイルあたり平均未満 2 回の edit、しかし各ファイルに必要な edit 数は 56/4/1/3 = 64+。**LLM は複数箇所の edit をマージせず replace_all も使用せず**、1 回の edit で 1-3 箇所は非常に非効率。

## CC パス：54 ツール一度で完走

CC レポート：Read 5 + Edit 32 + Bash 2 + Grep 2 = ~41（その他ツール使用）。

CC **主動的に深化を設計**：`_err` に tool パラメータを追加する以外に、`_validate_path` / `_check_dangerous` / `_load_ts_parser` / `_parse_symbols_cached` が複数のツール間で再利用される内部補助関数であることを発見。これらに `tool: str = "..."` デフォルトパラメータを追加してパススルー——エラートレーサビリティは補助関数ではなく呼び出し元ツールまで正確に追跡可能。これは yansh が考えなかった設計。

CC は 5 ラウンド上限に制限されず、シングルスレッド直列で 32 回 Edit してすべての呼び出し地点をスキャン完了。

## クラッシュ根本原因（yansh フレームワーク構造的）

| 問題 | トリガーシーン | task #4 が露出しなかった理由 | task #5 で露出 |
|---|---|---|---|
| **ファイルあたり 5 ラウンドツール上限** (`agent.py:1800`) | 単一ファイルで密集修正が必要（>5 回 edit） | task #4 単一ファイルは 1 回 edit で十分 | tools.py 56 回 edit / 5 ラウンド = 不可能 |
| **fix loop 12 ラウンド上限** | テスト駆動検証 + 複数回反復修正 | task #4 1 attempt で通過 | 21+ TypeError → fix 反復全実行 → 12 ラウンド消費 |
| **3 attempts max** | 3 個の完全な plan→code→fix サイクル内で完了できない任務 | task #4 1 attempt | 大規模変更 + fix 失制御 → attempts 消費 |
| **dispatch_subagent は大任務下でサブエージェントも半故障** | サブエージェント max_steps=8 / 16 ハードキャップで大ファイル変更にも不足 | task #4 サブエージェント探索実行（小規模）で十分 | サブエージェント派遣先は 56 箇所変更、max_steps 切断 |

**yansh のハードリミット設計は「小～中規模修正」を仮定**——ファイルあたり 5 ラウンド、fix 12 ラウンド、3 attempts。この制限は task #4 では問題露出なし（小規模変更）が、task #5 は直面撃沈。

## 共通盲点：なし

CC 今回盲点なし、むしろ yansh が考えなかった補助関数パススルーを実装（より細密な設計）。

yansh の盲点は**フレームワークレベル**で LLM レベルではない——LLM 振る舞いは正常（初回 edit は全て正）、上限が努力を分断化したのみ。

## 設計反省（yansh 側）

`agent.py:1800` の 5 ラウンド上限：
```python
if attempts_left <= 0 and response_message.tool_calls:
    warn = f"[警告] {filename} 已用尽 5 轮工具调用上限"
```

これはコード記述シーン向け設計——単一ファイル修正完了は 5 ラウンド内に終了すべき、LLM 無限ループ回避。しかし**密集多地点修正**は合理的要件（リファクタリング、一括適応）、切断は最適化逆効果。

可能な改善方案（**未実装**、backlog 記録）：
- (a) 5 ラウンド上限を token 上限に変更（ファイルサイズで動的調整）
- (b) 上限消費時に直接 break ではなく「残作業」を再フィード 5 ラウンド付与
- (c) plan フェーズで LLM 出力「予想 edit 数」→ スケジューリング数量決定上限
- (d) `replace_all` 類ツール活用で複数箇所一括変更（schema 対応済み、LLM 主動活用せず）

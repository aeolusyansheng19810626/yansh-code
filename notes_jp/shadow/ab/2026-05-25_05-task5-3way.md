## 3 方の動作詳細解説

### cc：64 個ツール呼び出しでの堅牢な完成（132K tokens）

cc の修正パス：
- `tools.py` の `_err` 関数シグネチャ + 56 個の呼び出し箇所を変更
- `subagent.py` の 1 個の呼び出し箇所を変更
- 新しい単体テスト `test_err_helper_includes_tool_field` を追加
- **agent.py は変更しない**——cc は baseline の `agent.py:1236/1244/1248/1310` が既に 3 つの位置パラメータで `_err("internal", "msg", name)` を呼び出していることを正確に識別した（baseline の agent.py は「先制的に」書かれている）。tool パラメータを追加後、呼び出しはマッチする

cc が自己報告した callsites_updated=48（実際は tools.py 56 + subagent.py 1 = 57、自己報告は再度信頼できない）。しかし git diff の客観的結果：tools.py 115 行の変更、タスク要求と一致。

最終的に pytest test_tools.py：**41 passed, 5 failed**（5 個は既知の baseline 失敗、`test_build_diff_lines_exactly_50_no_truncation` など、このタスクと無関係）。新しく追加した単体テストは通過 → タスクは正しく完了。

### yansh：🔴 ほぼすべてを変更したが自身の潜在的バグで失敗

yansh git diff は cc の変更と極めて類似（tools.py 120 行 / subagent.py 2 行 / test_tools.py 12 行）。yansh も同じアプローチで変更したことを示している。しかし **yansh CLI プロセスが fix ループ実行中にクラッシュした**：

```
File "agent.py", line 1236, in _dispatch_tool_call_inner
    result = _tools_mod._err("internal", f"工具调用异常: {e}", name)
TypeError: _err() takes 2 positional arguments but 3 were given
```

クラッシュのチェーン：
1. coder LLM が `search_in_files` に不正な regex（`missing )`）を渡した
2. tools.py `search_in_files` が `re.error` をスロー
3. `agent.py:1236` の except ブロックで `_err("internal", f"...", name)` を呼び出し（3 つの位置パラメータ）
4. **しかし yansh-code メインリポジトリの tools.py `_err(kind, msg, **extra)` は 2 つの位置パラメータのみ受け入れ** → TypeError
5. yansh CLI クラッシュ、exit=1、stdout は空

**これは yansh メインリポジトリの潜在的バグ**：agent.py は既に「将来のタスク #5 リファクタリング後」の方法で _err を呼び出しているが、tools.py はまだ対応していない。通常はエラー分岐を実行しないため暴露されない。タスク #5 LLM が読み取り専用ツールに不正なパラメータを渡すとトリガーされた。

→ **yansh 技術負債 P1 #7 に記録済み（赤旗、30 分で修正可能）**：[[project-yansh-tech-debt]]

皮肉なことに：**このバグは正にタスク #5 が修正しようとしている内容そのもの**。yansh はこのバグを修正する過程でこのバグにより失敗した。

token 消費 692K も高いが、歴史上のタスク #5 の 1.86M と比べ 63% 削減（baseline に付属の「Anti-pattern」コメント line 1361 は LLM に `replace_all` / `write_file` による一括変更を示唆し、yansh のツール round 数を削減したと思われる）。

### yscode：PlanFailed × 2（タスク #1 以来再び出現）

yscode は 24 個ツール呼び出し、789K token / $2.58 を消費し、**0 ファイル変更**。失敗理由：

```
ERROR: <PlanFailed: architect did not submit a valid plan within budget>
```

stderr は architect が複数行 `python -c "..."` コマンドのループを試し、cp932 エンコーディングエラー（Windows コンソール）をトリガーし、LLM が記述方法の切り替えに反復的に再試行（`io.TextIOWrapper(sys.stdout.buffer)` など）し、plan budget を使い果たしたことを示している。

タスク #1 の PlanFailed とは異なる根因：
- タスク #1：architect は「探索タスク」を plan に変換する方法を知らなかった（既修正）
- タスク #5：architect は自分で cmd を実行して探索しようとした（`python -c` で すべての _err 呼び出し箇所をリストアップ）、しかし Windows cp932 エンコーディング反復エラーが発生し、budget を使い果たすまで回転

## 結論：3 つのツール「プロフィール」

### cc (Claude Code subagent + 汎用)
- **強み**：単一 agent + 汎用ツールセット、シンプルで直接的、結果が安定、token が少ない
- **弱み**：自己報告フィールド信頼性なし（`files_modified` がしばしば誤報告）、AST クラス専門ツール欠落、grep + read の組み合わせに頼る必要
- **向き**：5 つのタスク類型すべてに安定して対応可能、baseline 中で最高の「プログラマー代替品」

### yansh (単一 agent CLI + plan→code→fix 分離)
- **強み**：plan agent が scope を正確に切り分けた時は超高速（タスク #3 44K token）；専門ツール（`get_symbol_definition` / `search_in_files` / `dispatch_subagent`）；replay システム完全に可観測
- **弱み**：
  - plan/coder プロトコルが辺端タスクで「手放さない」（タスク #2 91 万 token 消費）
  - baseline 失敗識別メカニズムがユーザーリクエストを飲み込む（タスク #4 サイレント失敗）
  - メインリポジトリ潜在的バグ：_err シグネチャ不一致 → ツール例外時 CLI クラッシュ（タスク #5）
  - ドキュメント生成時に 0 探索（タスク #3 ドキュメント精度 1 エラー 2 偏差）
- **現在の状態**：タスク #2 / #4 / #5 3 つの P1 レベルのメカニズム問題がすべて技術負債リストに記録済み [[project-yansh-tech-debt]]、一括修正が必要

### yscode (マルチエージェント CLI: plan + coder + review + audit)
- **強み**：コード書き込みタスク（タスク #2、#4 正しく修正）の表現が良好；plan→code→test の明確なフェーズ分割
- **弱み**：
  - 探索 / 論証クラスのタスク劣化が深刻（タスク #1 答え stderr に、タスク #3 426K 網羅的 read、タスク #5 PlanFailed）
  - architect が plan フェーズで回転してしまい budget を使い果たしやすい（タスク #1 既修正、タスク #5 cp932 エンコーディングエラーで再現）
  - 「エンジニアリング潔癖癖」で過度に構造を補完（タスク #4 4 つの無関な shim ファイルを作成）
  - cp932 / Windows コンソール エンコーディング互換性が悪い
- **現在の状態**：タスク #1 修正後回復が良好、タスク #5 が暴露した PlanFailed トリガーパスは yscode 側で再度確認が必要

## Caveats

1. **gateway 差異**：cc は Anthropic gateway、yansh/yscode は ICA gateway を経由。同名の sonnet 4.6 は両側バックエンドで動作が若干異なる可能性あり
2. **mode 不一致コスト（タスク #1）**：yansh は歴史的にタスク #1 で audit mode を使用が最適路、今回 yscode に合わせて code mode を使用し優位性を喪失
3. **yansh メインリポジトリが AB-test で潜在的バグを露出（タスク #5）**：AB-test フロー無関、yansh 自身コードの問題
4. **yscode が Windows で cp932 エンコーディング互換性の問題あり**：その architect が自身で `python -c` 探索を実行する能力に影響

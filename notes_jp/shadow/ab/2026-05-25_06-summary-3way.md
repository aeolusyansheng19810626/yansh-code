## 重要な発見

### 1. self-report は信頼できない → git diffのみを信頼

cc の `files_modified` フィールドは誤報が頻繁（task #2 tools.pyをマークしたが diff は空；task #5 callsites_updated=48 だが実際57）。yansh の task_complete summary も空の場合がありますが git diff に変更が表示。**評価時は実際に git diff + pytest を実行、LLMの自己報告に依存できない**。

### 2. mode選択が yansh に巨大な影響

yansh 過去 task #1 audit mode 使用は最適パス（24.5s / 2ツール）。今回 yscode 合わせで code mode 使用、yansh は task #1 / #3 で天然の優位性を喪失。**code mode は強制的に plan→coder→fix フローを走行、探索/論証型task に過度実行**。

### 3. plan agent 正確性は yansh 性能の決定因子

| Task | yansh tokens | plan 正確性 |
|---|---|---|
| #3（plan「1つのドキュメントファイル」と画定） | 44K | ✓ 正確 |
| #1 / #4 | 167K-205K | 標準的 |
| #5（plan 4ファイル画定、baseline 半実装識別未了） | 692K | 逸脱 |
| #2（plan「4ファイル変更必要」と誤画定、実際baseline既実装） | 915K | ✗ 完全に誤り |

**plan/coder分離のコスト**：plan が誤った場合、coder が plan に従って進行するとtoken爆発；plan が正確な場合は極めて省エネ。plan agent 最適化は yansh の最高ROI方向。

### 4. yscode マルチエージェント アーキテクチャの安定性問題

| タイプ | 表現 |
|---|---|
| コード記述task | ✓ 強（task #2完璧 / task #4修正成功） |
| 論証/探索 | ⚠️ 低下（全数探索/答え summary格納/cp932失敗） |
| windows互換 | ⚠️ cp932エンコード問題が architect 死ループ（task #1 / task #5） |

yscode の architect は一部エッジtask で「幅が過負荷」、token消費多くアウトプット低い。「早期終了」パスが必要。

### 5. cc は本当に安定した「プログラマー代替品」

cc 5task全完了、token消費最も安定。これは Claude Code の単一agent + 汎用ツール組み合わせがほとんどのシーン十分という反映。**マルチagentアーキテクチャ（yansh / yscode）の追加複雑性が常に収益をもたらすわけではない**。注意点：
- cc修正の深さが浅い
- self-report は信頼できない
- dispatch_subagent / クロスファイル一括編集など高度なツール欠如、困難なリファクタ（task #5）は LLM 一度の正確な記述に依存

## 3方の行動詳細

### cc：教科書的なバグ修正（51K tokens / 6ツール）

```
1. TaskCreate（自分でtodoを作成）
2. Bash: pytest -v で失敗を確認
3. Grep: find_memory の定義を検索
4. Read: memory.py 100-139
5. Edit: name → _slugify(name) 単一の変更
6. Bash: pytest で 35 passed を検証
```

修正方法は正確：`save_memory` は `_slugify` を使用しているが、`find_memory` は使用していないことを識別 → `_slugify` 呼び出しを追加。**1行のコア修正、14行の削除（commit `d95c87d` のdocstringと重複検証をクリーンアップ）**。

ただし注意：**cc の修正の深さはbaselineより浅い**——baseline `d95c87d` は slugify + resolve 二重チェックの2層防御を追加、ccは slugify のみを追加（テスト合格には十分ですが、resolve の予備層が不足）。この修正方法は過去のtask #4 cc の修正方法と完全に一致（"⚠ slugifyのみ追加、resolve二重チェックが不足"）。

### yansh：🔴 静かな失敗 — baseline failure識別機構がユーザーリクエストを誤認

**最も深刻な発見**。yanshが実行したもの：
- 5回のread_file（memory.py の各セクション確認）
- 3回のget_symbol_definition（_slugify、find_memory、save_memory を確認）
- 1回のlist_symbols / 1回のlist_files
- 4回のexecute_command（pytest で検証）
- 1回のtask_complete

**結果**：files_modified = `<空>`、task_complete summary = `<空>`、**0 回の修正試行**。

stderrは決定的な1行を表示：
```
現在の1件の失敗がすべてbaseline内にある（1件のpre-existing）→ 合格と見なす
```

これはcommit `1e3ce5f`（task #5 v4 で修正されたbaseline failure識別機構）が逆に悪さをしている：
- 本意：fix loop がテスト実行時に「plan files 範囲外の失敗」に遭遇 → スキップして無関係な問題を追修しない
- 誤用：「ユーザープロンプトが明確に要求する失敗」もpre-existing と判定 → スキップ

タスクプロンプトに「tests/unit/test_memory.py にテストの失敗があります。定位 bug を特定して修正してください」と明確に書かれているのに、yansh は完全に無視して直接 task_complete で終了。**これは機構のバグであり、LLMの判断エラーではありません**。

➡ **yansh技術負債リストに記録（P1 #6、赤マーク）**：[[project-yansh-tech-debt]]

### yscode：修正は正しいが極度に浪費（592K tokens / $1.85 / 36ツール呼び出し / 5ファイル変更）

yscode 36ツール：11 execute_command + 10 read_file + 4 write_file + 3 replace_in_file + 3 task_complete + その他。

最終結果は正しい：**35/35 passed**。しかし経路は非常に迂回：
- **4つのshimファイルを作成**：`test_memory.py`（root）、`tests/test_memory.py`、`tests/__init__.py`、`tests/unit/__init__.py`
- rootと tests/ 下のshimファイルの内容はすべて：
  ```python
  # Shim: re-export all tests from tests/unit/test_memory.py
  from tests.unit.test_memory import *  # noqa: F401, F403
  ```

推測される理由：yscode のcoderが `python -m pytest test_memory.py` でテストを実行しようとしたときに見つからず（パス記述エラー）、このshimを作成して import path が合致するようにしました。正しいパス `python -m pytest tests/unit/test_memory.py` を直接使用する代わりに。

**深刻な副作用**：
- 修正 + 4つの無関係ファイルのコミット、ワークスペース汚染
- 592K token / $1.85 消費（task #2 は trick task で56K消費、task #4 は実作業なのに10× のyscode task #2 コスト）
- task #3 yscode は既に426K で文書作成、task #4 でさらに592K、**yscode の資金消費の分散は非常に大きい**

## 主要発見

1. **🔴 yansh のbaseline failure識別機構は時限爆弾**：task #3 では無限ループを防ぐのに役立ち、task #4 ではユーザーが明確に要求したバグの修正を見落とします。この機構は直ちに修正が必要。
2. **cc subagent はバグ修正タスクにおいてコストパフォーマンスの王**：51K token で1行を正しく修正、他の2つの方法よりもクリーン
3. **yscode は「見えないエンジニアリングプラクティス」を補完**：`tests/__init__.py` を作成するのはいくつかのPythonプロジェクトのベストプラクティスですが、このリポジトリには必要ありません——**yscode は過剰に「標準構造」を補足する傾向**
4. **yscode はテスト実行で反復試行と誤り**：11回のexecute_command、パス記述方法は何度か変わってようやく通りました。ysocde が「ワークスペース内でのコマンド実行」の環境推論が弱いことを示しています

## 注意事項

1. **バグ注入は手動**：`git show d95c87d -- memory.py | git apply -R` でreverse-apply、過去のtask #4 と一致
2. **修正の深さはすべて浅い**：cc と yscode は両方ともslugify のみを補足、resolve二重チェックを追加していません（baselineは二層防御）。機能的にはテスト合格に十分ですが、セキュリティは元の修正ほどではありません
3. **yansh のbaseline failure識別はそもそも好意的**：fix loop がbaseline 付属の失敗で立ち往生するのを避けます。問題は過滤戦略が粗い——「ユーザーが言及する失敗」と「無関係な失敗」を区別しない
4. **gateway の差異**が残存

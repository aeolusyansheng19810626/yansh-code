## 三、シナリオ推奨

### cc を使うシナリオ

- **日常のコーディング助手**：5種類のタスク全て安定完了、token 消費最小かつ安定（50K–132K）
- **バグ修正（テスト失敗含む）**：テストが信号アンカーの時、cc は単一スレッド順序実行で 1回完了、plan overhead なし
- **迅速な探索 / 情報検索**：パス最短、専用ツールなしでもカバー可能
- **確実な結果が必要な場合**：cc は唯一 5/5 完了したツール、真の意味での「プログラマー代替品」

### yansh を使うシナリオ

- **中規模機能完全実装**（schema、ドキュメント、クリーンアップ含む）：plan agent が scope 正確な時、yansh は「語義的完成」——tools_schema.py を順手に修正、デッドコード削除など cc しない処理
- **AST レベル探索が必要なシナリオ**：`get_symbol_definition` で一撃に docstring 返却、「なぜこう設計」を示す単なる「コード何する」のみ
- **audit モード下の読み取り専用分析**：強制読み取り専用 + dispatch_subagent 自動子タスク分割、不慣れなコードベースに適す
- **P1 技術負債修正後**：P1 全て修完後（現状 2026-05-26 完了済み）、ファイル間リファクタリング シナリオで顕著改善予想

### yscode を使うシナリオ

- **ゼロからの新機能 / マルチステージ開発**：plan→code→test ステージ分割明確、architect が「修正不要」正確識別で空 plan 終了、yansh より抑制的
- **コード作成タスク + テスト検証**：task #2 / #4 修正法完全、yscode の強項
- **ドキュメント作成や探索不要の純実装タスク**：yscode の弱区（探索 / 論証 / Windows エンコード）を回避

- **P1 #5 plan がコード詳細ドキュメント作成前に探索ゼロ**（task #3）：plan agent が脳で技術ドキュメント生成、1つ誤り 2つ偏差；修正法：コード詳細ドキュメント前に強制 explorer 子 agent 配置

## 六、主要教訓（最重要 2条）

**1. plan/coder 疎結合は両刃剣**

plan 正確時（task #3、44K tokens）が yansh 最省走法；plan 誤時（task #2、915K tokens）は「修正不要」識別 coder を空ラン 20ラウンド fix loop に推進。yansh の token 消費は plan 正確性でほぼ全決定——plan agent 最適化が yansh 最高 ROI 方向。

**2. self-report フィールド不信頼、git diff + pytest のみ信頼**

cc の `files_modified`、yansh の `task_complete summary`、yscode の `success: true` 全て実結果と不一致事例発生。AB 評価必ず現地で `git diff --stat` + `pytest` 実行で客観結果検証、LLM 自己報告依存不可。

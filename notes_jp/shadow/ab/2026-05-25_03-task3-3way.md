## 主な相違分析

### yansh：plan agentが「コンテキスト知識」からドキュメントを直接出力（44Kトークン、4つのツール呼び出し）

yanshの4つのツール呼び出し：
```
1. write_file → notes/shadow/2026-05-24_01-task-complete-signal-migration.md
2. task_complete (主声明：レポート完成、4つのポイントをカバー)
3. task_complete (fix循環でlint 216件は基準失敗と認識 → スキップ)
4. task_complete (最終、テスト実行時「不明エラー」発生 → タスク範囲に属さないと判定)
```

**plan agentはcoderに何もコード探索させることなく、直接「ドキュメント作成」段階に進んだ。** これは以下を意味する：
- ✓ 非常に高速（44Kトークン、全5方task #1-3中最小の一つ）
- ⚠️ ドキュメント内容はLLMのsystem promptに注入済みのrepo情報 + 学習知識から「記憶」または「推論」されたもので、**baseline実際のコードの100%を反映していない可能性がある。** ドキュメント精度の個別レビューが必要。

歴史的task #3のyanshはaudit modeで50個のツール呼び出し + 73万トークンでコードを深掘り探索してからドキュメント作成；今回code modeは「ショートカットパス」を取った。

### yscode：徹底探索 + ドキュメント全体をtask_complete summaryに詰め込み（426Kトークン、$1.35）

yscodeの31個のツール呼び出しの中で**24個はread_file**で、codebase全体を一読している。その後、5,226文字のmarkdownドキュメント**全体をtask_completeのsummaryフィールドに直接詰め込んでいる。**

**問題点**：
- summaryは文字列フィールド、5K文字のmarkdownを詰め込むのは設計意図ではない
- summary内容は後続の各ラウンドのmessagesに再生され、トークン消費が倍増
- ユーザーはstdout JSONを見てsummaryからドキュメントを取得、**独立したファイル出力がない**

これはyscodeが「タスク要件はドキュメント出力だが、plan段階でfile_pathを識別していない」場合の退化動作。task #1探索タスクの「答えをstderrに詰め込み」より若干マシ（少なくともsummaryから見つけられる）だが、まだ理想的ではない。

### cc：均等探索、最も実用的

ccの26個のツール呼び出しの中で：14回のRead（agent.pyの複数段落を細読）+ 3回のGrep + 2回のGlob。agent.pyのplan/code/fix/audit 4つのコア循環段落を読み、subagent.py、tools_schema.pyなどを読んだ。

7,215文字のドキュメントを`AB-test/cc/task3_doc.md`に出力 —— **workspaceを汚さない。** これはccの良い習慣：subagentはデフォルトでworkspace内にファイルを書き込まず、出力はresult.jsonを経由。

### yansh「plan files文書のみ」が発動させた退化パス

stderrに出現：
```
[セキュリティブロック] 危険なコマンド検出：python -c (インライン実行)
テスト失敗 (試行 2/3)
[Agent: Tester]
コード修正開始...
1個の修正操作を実行...
修復完了（task_complete: 成功）：Plan files文書のみを含む...
```

yanshのfix循環が発動：
1. planが`test_command: python -c "import os; assert os.path.exists('notes/shadow/...')"` ドキュメント存在確認を書き込み
2. yanshはセキュリティが`python -c`をブロック → テスト「失敗」
3. fix loopに入り、Testerエージェントが主動的に「plan filesが文書のみを含む、テスト失敗はタスク範囲に属さない」と宣言 → 抜ける

**これはtask #5 v4で修正されたbaseline failure認識メカニズムが作動している**（commit `1e3ce5f`）。このメカニズムがなければ、task #3 yanshはfix無限ループにはまっていた。

## タスク間トレンド

| Task | yanshトークン | yscodeトークン | ccトークン | タスク性質 |
|---|---|---|---|---|
| #1 探索 | 167K | 65K（修正後） | 50K | 読み取り専用 |
| #2 コード記述 trick | **915K** | 56K | 70K | 既実装の識別 |
| #3 論証 | **44K** | **426K** | 128K | ドキュメント作成 |

観察：
- **yansh成本は非常に不安定**（44K～915K、21倍の差）：plan段階でscopeを正確に定義できるかに依存。task #2 planが4ファイルのサブタスクを定義 → 爆発；task #3 planが1つのドキュメント → 極省
- **yscode成本は相対的に安定だが高め**（56K～426K、8倍の差）：multi-agentフロー「幅優先探索 + plan+code+review 3段階」の基本オーバーヘッド
- **cc成本が最安定**（50K～128K、2.5倍の差）：単一agent、オーバーヘッドはタスク複雑度に直結

**yanshへの示唆**：plan agentのexpected_edits精度は後続のトークンオーバーヘッドを直接左右する。task #2 planが「既実装タスク」を「4ファイル修正が必要」と誤分類 → 悪夢；task #3 plan「ドキュメント作成」を正確に「1ファイル」と定義 → 最適パス到達。**これがplan agent最適化の高ROI方向。**

# P2 #12 セッション間の永続的記憶

[_21](./2026-05-22_21-hooks.md) に続く：Hooks 完成後に #12 を実施——この波で**ROADMAP 全体を締めくくる**。
Claude Code 内蔵 memory システムと同じアーキテクチャを採用（今私が記事を書くために使用しているそのシステムと同じもの）。

## 目標

yansh がセッション間で事実を蓄積する——ユーザー設定 / プロジェクト背景 / フィードバック / 外部リソース——
次回起動時にも取得可能で、毎回最初から説明する必要がない。

## 変更内容

### 1) memory.py 新規モジュール

#### データモデル

```python
@dataclass
class Memory:
    name: str               # kebab-case スラッグ、一意識別子
    description: str        # 1行インデックス（次回取得の関連性を決定）
    type: str               # user | feedback | project | reference
    body: str               # markdown 本文
    scope: str              # project | global
    source_path: Optional[str]
```

#### デュアルパス保存（mcp / hooks に合わせる）

```
<workspace>/.yansh/memory/<slug>.md      プロジェクトレベル（コードベースに従う、コミット可能）
<workspace>/.yansh/memory/MEMORY.md      プロジェクトレベルインデックス
~/.yansh/memory/<slug>.md                グローバル（プロジェクト間、ユーザー設定）
~/.yansh/memory/MEMORY.md                グローバルインデックス
```

同じ slug の場合は**プロジェクトレベルがグローバルをオーバーライド**——skills / mcp と一致。

#### 4 種類の type が Claude Code に対応

- `user` ：ユーザーは誰か、ユーザー設定（"vim を使う"、"フロントエンド React"）
- `feedback` ：ユーザーフィードバックがどのように機能するか（"指示がない限りテストを書かない"）。慣例として本文末尾に `Why:` / `How to apply:` が付く
- `project` ：プロジェクト背景 / 主要決定（"pytest を使用、unittest は使用しない"）
- `reference` ：外部リソース（API ドキュメント URL、内部 Confluence リンク）

#### API

```python
parse_memory_file(path, scope) -> Optional[Memory]   # ネストされた metadata.type frontmatter パース含む
discover_memories(workspace_dir) -> list             # デュアルパススキャン、プロジェクトがグローバルをオーバーライド
find_memory(name, workspace_dir) -> Optional[Memory] # name で1件検索
save_memory(name, type, description, body, scope, workspace_dir) -> dict
delete_memory(name, scope, workspace_dir) -> dict
load_memory_index(workspace_dir) -> str              # 2つの MEMORY.md を結合 → system prompt に注入
list_all(workspace_dir) -> list                       # /memory list 用
```

#### MEMORY.md インデックス自動メンテナンス

save / delete の度に `_update_index(target_dir, scope, ws)` を呼び出して対応ディレクトリの
MEMORY.md を再構築：各行は `- [type] name — description`。
load_memory_index は2つのディレクトリの MEMORY.md を結合 + 呼び出しヒントを追加し、
system prompt に注入される。

### 2) tools.py / tools_schema.py に2つのツールを追加

- **save_memory(name, type, description, body, scope='project')** ：LLM が主体的に呼び出し
- **recall_memory(name)** ：name で完全なコンテンツを読み込み

`READONLY_TOOL_NAMES` に追加——save は `.yansh/memory/` に書き込み（ワークスペースコードではない）、
audit / explorer サブエージェント両方が書き込み可能（例えば audit が "プロジェクトは pytest を使用" を実行したら自然に蓄積される）。

schema の description は主要なガイダンス：
- save_memory：**いつ主体的に呼び出すか** + **書き込みしないべき** クリアリスト（毎回の書き込みを避けるため）
- recall_memory："system prompt にはインデックスのみを提供、関連インデックスを見つけたらこれを呼び出す"

### 3) agent.py 統合

- モジュールレベルの `_ACTIVE_MEMORY_INDEX: str = ""` が `_ACTIVE_SKILLS_PROMPT` と並行
- `_run()` エントリが MEMORY インデックスを読み込み
- 5つの system prompt 注入ポイントすべてに `_ACTIVE_MEMORY_INDEX` を追加：plan / code（既存 / 新規パス両方） / audit / fix（review_rejection / test_failure 両方）
- plan_chat() が独立してスキャン（skills と同じ処理）
- `_build_subagent_system_prompt` もインデックスを追加——サブエージェントが表示可能 + READONLY ホワイトリストを通じて save/recall も可能

### 4) main.py コマンド

```
/memory list                  scope で分類してすべてのメモリを一覧表示
/memory show <name>           完全なコンテンツを表示（プロジェクトレベルが優先）
/memory delete <name>         削除（まずプロジェクトレベル、次にグローバル）
```

### 統合検証（エンドツーエンドセッション間）

**セッション 1**（Python プロセス A）：
```python
agent._run_subagent('save_memory: project-uses-pytest, type=project, ...',
                    role='general')
```
→ サブエージェントが save_memory ツールを実際に呼び出す
→ ファイルを `workspace/.yansh/memory/project-uses-pytest.md` に書き込み：
```
---
name: project-uses-pytest
description: 本プロジェクトは pytest を使用し、unittest は使用しない。すべてのテストは tests/unit/ 内
metadata:
  type: project
---

本プロジェクトはテストフレームワークとして pytest を使用し、unittest は使用しない。...

Why: ユーザーが明示的に指定したプロジェクト慣例。
How to apply: テストを書くときは pytest スタイル（def test_xxx, assert ステートメント）を使用、...
```
→ MEMORY.md インデックスも更新される

**セッション 2（真新しい Python プロセス B）**——すべてのメモリがクリアされる：
1. `memory.load_memory_index('workspace')` がディスクからインデックスを読み込む ✅
2. インデックステキストがサブエージェント system prompt に注入される ✅
3. LLM がインデックスを見て recall_memory("project-uses-pytest") を呼び出す ✅
4. Why / How to apply を含む完全な body を取得 ✅

**重要な証拠**：プロセス A が書いたメモリをプロセス B が完全に読むことができる——これが「セッション間」の堅い証拠。

### 学んだこと

- **"LLM が主体的に呼び出す" vs "ユーザーが明示的に保存"**：LLM が自分で何が memory の価値があるかを判定させることが鍵——schema description で What/When/When-not を明確に書くことで LLM に安定した判定パターンを形成させる。**最も重要な一行：description に「何時に書き込みしないか」を記述する**——何を書くかだけを言い、何を書かないかを言わないと、LLM はたくさんの無用な内容を書く。
- **インデックス/詳細の2層構造**：「インデックス」（短い説明）と「詳細」（完全な body）を分離することは古典的な token 予算最適化——インデックスは毎回注入される（各項目 ~50 token）が詳細はオンデマンド read（各項目 ~500 token）。100個のメモリインデックスは ~5k token だが、すべてを注入する場合は ~50k——10 倍の節約。
- **type システムの価値**：異なる type は LLM にとって異なる意味——`user` は上書きされない、`feedback` は「why」を強調、`project` はコードベースに従う、`reference` は外部リンク。この分類は LLM の使用方法を直接決定する。
- **「セッション間」の重要なテスト**：**新しい Python プロセス**を使用してテストする必要がある——同じプロセスで2回実行することは「メモリに保存できる」ことのみを証明でき、「再起動して失われない」ことは証明できない。

## 実装しない（今後用）

- `[[memory-name]]` クロス参照解析
- LLM 知的取得（インデックステキストに依存せず直接 fuzzy select memory、P2 #8 LLM skill 選択の考えを再利用）
- memory 逆インデックス（どのタスクがこのメモリを読んだか、memory の価値評価用）
- memory 自動期限切れ（90日呼び出されなかったらユーザーにクリーンアップを促す）
- memory マージ（重複テーマを自動マージ）
- セキュリティ標記（"この memory を MCP server に見せないでください" 反 prompt injection）

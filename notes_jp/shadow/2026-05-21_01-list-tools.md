## 学んだこと

### 1. Prompt の変更効果は定量化可能

| 指標 | 変更前 | 変更後 | 変化 |
|---|---|---|---|
| 実行時間 | 27.8s | 9.3s | **-66%** |
| ツール呼び出し | 2 | 1 | **-50%** |
| 出力長 | テンプレート満杯 | 直接リスト | 大幅に簡潔化 |
| 回答の正確度 | 誤り（20） | 正確（19） | 関鍵 |

**単一の prompt ルールの ROI は非常に高い**——3 行の文字を加えるだけで実行時間が 3 倍高速化し、回答が正確になる。これは ROADMAP P0 #2 の判断を検証している：1 週間の prompt 調整は 5 つのツール追加より効果が高い。

### 2. 「タスク規模の認識」は過小評価されているルール

LLM はデフォルトで**最も複雑な出力形式にパターンマッチング**する——自分の役割が「監査 Agent」であることを見ると、ユーザーが「何個」と聞いているだけでも監査テンプレートを適用する。

単純な質問には単純な回答を与えることを教える方が想像以上に重要。**これは市場の監査ツールが一般的に冗長である根本的な理由**。

### 3. 「先に grep、その後詳読」ルールが機能していない

prompt に「search_in_files を使って特定の行番号を特定し、ファイル全体を read_file してはいけない」と書いてあるが——yansh は依然として tools_schema.py 全体を read した。

**機能しない理由**：LLM はすでに答えがこの 1 ファイル内にあることを知っているので、直接 read する方が「効率的」。ルールの表現をさらに強化する必要がある：いずれかの方法で「200 行を超えるファイルは全体 read を禁止」に変更するか、few-shot 例を追加する。

→ ROADMAP P0 #2 後続処理：ルール文言を追加するより few-shot 例を追加する方が効果的。

### 4. yansh の「過度な発展」は双刃剣

変更前の yansh は delete_file の登録漏れを発見——これは真のバグ。変更後の yansh は発展しないが、このバグも発見しない。

**深刻な問題**：いつ発展させるべきで、いつ抑制すべきか？  
現在の解決：**タスク表現で決定**。「X をリストアップ」→厳格に回答；「X を監査」→発展を許可。  
しかしユーザーの表現はしばしば曖昧で、曖昧な場合に LLM が**先に意図を確認**することを教える必要がある。

→ これも ROADMAP P0 #2 の別の条項に対応：「曖昧なタスクは先に 1 文で確認」。

### 5. workspace_symbols プリインジェクトの副作用

audit mode に入ると 35 ファイルのすべてのシンボルを system prompt に詰め込む。**これにより LLM は「既知情報から翻す」傾向があり、より精密なツールを使わない**——「すでに要約を見た」ため。

→ ROADMAP P0 #1 に対応：フラットな要約より層状シンボルインデックスの方が優れている。

# P2 #11 Hooks システム

[_20](./2026-05-22_20-mcp.md) に続いて：MCP 完成後 #11 を行う。ユーザーが shell コマンド hook で yansh の重要イベントに割り込むことができるようにする——Claude Code の settings.json hooks に対応。

## 目標

4 つのイベント + block/modify 2 種類のアクション + shell stdin/stdout JSON プロトコル。
最も一般的な使用例：write 完了後に自動 prettier 実行 / 敏感ファイル削除前に拦截 / ユーザー入力提交後にコンテキストを追加。

## 変更内容

### 1) hooks.py 新規ファイル

#### プロトコル

イベント 4 種類：`PreToolUse / PostToolUse / UserPromptSubmit / Stop`

Hook サブプロセスプロトコル（stdin/stdout JSON）：
```
stdin  ← {"event": "...", "tool_name": "...", "tool_input": {...},
          "tool_output": {...}, "user_input": "...", "task_summary": "...", "cwd": "..."}
stdout → {}                                              空 / 出力なし = allow
       → {"decision": "block", "reason": "..."}          ブロック
       → {"modify": {"tool_input": {...}}}               入力を変更
       → {"modify": {"tool_output": {...}}}              出力を変更
       → {"system_message": "..."}                        LLM にコンテキストを追加
```

#### `run_hook_event(event, payload, match_target, workspace_dir)` 集約ルール

- 複数マッチした hook は順序実行（設定順序）
- いずれかが block → 全体ブロック、**残りの hook は実行されない（短絡）**
- modify は連鎖蓄積：2 番目の hook は 1 番目の変更後の payload を見る
- system_message はすべて収集される
- 個別 hook 失敗/タイムアウト → errors リストに追加、全体の決定に影響なし（保守的に allow）

#### タイムアウトプロセスツリーキル（Windows 重要修正）

初期実装で `subprocess.run(..., timeout=)` を Windows + shell=True で使用するとゾンビプロセスが残留：
shell（cmd.exe）が kill されるもゾンビプロセス（python sleep）は実行継続、wait もハング。
改善後は `Popen` + タイムアウト時に `taskkill /F /T /PID`（Windows）/ `os.killpg(SIGKILL)`（POSIX）を使用
プロセスツリー全体をキル。テストにより `timeout=1` が実際に 1 秒で終了することが確認。

### 2) agent.py に 4 つのトリガーポイントを統合

**PreToolUse / PostToolUse**（`_dispatch_tool_call` 内）

既存の `_dispatch_tool_call` を 2 層に分割：
- `_dispatch_tool_call_with_hooks`（外層）：PreToolUse を実行 → 内層を呼ぶ → PostToolUse を実行
- `_dispatch_tool_call_inner`（内層）：元々のツール分配ロジック（事前解析済み args を受け取る）

PreToolUse は args を変更可能（modify）；PostToolUse は result を変更可能（modify）；いずれかが block なら LLM に error を返す。

**UserPromptSubmit**（`run()` 入口）：ユーザー入力が画像/コンテキストを解析後、`_run` 呼び出し前。
hook は user_input を変更、system_message を追加（requirement ヘッダ部分に注入）、リクエスト全体を拒否可能。

**Stop**（`run()` 出口）：`_run` が返される後、return 前。
タスク完了後、hook の主な役割は system_message——ユーザーに直接表示（次の LLM ラウンドに注入ではなく）。

### 3) スキップシーン

- サブ agent 内部（`_is_in_subagent()`）：親 agent がツールを派遣した時点で PreToolUse は既にトリガー、
  サブ agent が重複トリガーしない（1 つの hook コマンドが同一ファイル操作で N 回トリガーするのを回避）
- グローバル無効化（`hooks.set_disabled(True)`）：バッチ処理 --json モードは main.py で設定
- 個別 hook 失敗：`_run_one_hook` が `_hook_error` を返す → 集約時に errors リストに追加、
  全体はまだ allow（メインフロー停滞を防止）

### 4) main.py

- 起動時 `--json` は自動的に `hooks.set_disabled(True)`
- `/hooks list` で現在の設定を列挙（各イベント下の各 hook の matcher/timeout/command）

2 つの Python hook スクリプトを外部コマンドとして作成：

3 つのシナリオを実行：

| シナリオ | 入力 | 結果 |
|---|---|---|
| PostToolUse modify read_file | read sample.txt（4 行） | content 前に `[hook 注入: 5 行]\n` ✅ |

### 「なぜ hooks が開放拡張ポイントなのか」

以前は yansh の動作を変更したければソースコードしか改変できず：
- すべての write_file 後に prettier を実行したい？agent.py を改変して呼び出しを追加
- .env の削除をインターセプトしたい？_dispatch_tool_call に判定を追加

今はユーザーが hooks.json に 1 行書くだけ——**ユーザーと yansh メンテナーは疎結合**。
yansh はイベントトリガーポイントのみを公開、実装戦略はユーザーが決定。

MCP は鏡像関係：
- MCP：**能力**を拡張（新しいツールを追加）
- Hooks：**戦略**を拡張（既存ツールをインターセプト / 変更）

両者の組み合わせが「開放アーキテクチャ」——ツール追加と動作変更の両方が可能。

### 学んだこと

- **イベント駆動アーキテクチャを agent に組み込むキー**：トリガーポイントは十分に「アトミック」である必要——`_dispatch_tool_call`
  外層ラップは自然な Pre/Post カットポイント。トリガーポイントが粗すぎる場合（「タスク開始/終了」）実行可能な処理が制限；
  細すぎる場合（「LLM の各トークン」）オーバーヘッドが爆増。Pre/Post Tool はゴールデングレイン。
- **失敗時容錯**：hook のデフォルト allow は必須——不正な hook 設定が agent 全体をハング させない。
  ユーザーが hooks.json を破壊しても yansh は使用可能。これは「安全性より可用性を優先」の判断と正反対——
  hook 失敗 → ツール実行（ユーザーが作業継続可能）；ユーザーが逆を希望する場合は hook で明示的に block 必要。
- **クロスプラットフォームタイムアウト**：subprocess.run + shell=True + timeout は Windows 内でのピットフォール——
  Popen + プラットフォーム特定のプロセスツリーキルが必須。POSIX は killpg + start_new_session；
  Windows は taskkill /F /T /PID + CREATE_NEW_PROCESS_GROUP。

## 不実装（今後に残す）

- matcher 正規表現（"write_file|append_to_file"）
- 非同期 hook（fire-and-forget；現在はすべて同期ブロック）
- hook 間の依存関係（「hook A が完了後 hook B が実行」）
- hook の優先度（同一イベントの複数 hook は現在設定配列順で実行）
- hook 自体が yansh ツールを呼び出し可能（ネスト）——複雑性を引き入れる
- PostToolUse の modify で tool_call を変更し LLM に再発信させる（「自動リトライ」モード）

# P2 #10 MCPプロトコル（最小版）

[_19](./2026-05-22_19-subagent-concurrent.md)を継承：サブエージェント完了後に #10 を実施。
ROADMAP でこれを LLM エージェント設計の**重要な構造概念**として指定——完了後、ツールエコシステムに対する理解が次のレベルに進む。

## 目標

yansh を MCP（Model Context Protocol）エコシステムに統合する——ユーザーが任意のサードパーティ
MCP server（GitHub / Linear / Sentry / 自作の内部ツール server）を設定でき、yansh が自動的に発見して
ツールを TOOLS リストに注入し、LLM が内置ツールと同じ方法でそれらを呼び出せるようにする。

## 何を変えたか

### 1) `mcp_client.py` 新規ファイル

#### `MCPServer` クラス——サブプロセスの完全なライフサイクルを管理

```python
class MCPServer:
    def __init__(self, name, command, args=None, env=None, cwd=None): ...
    def start(self, init_timeout=15):    # spawn + initialize ハンドシェイク + tools/list
    def call_tool(self, tool_name, arguments, timeout=60): ...
    def shutdown(self): ...
    def is_alive(self) -> bool: ...
```

実装のポイント：
- `subprocess.Popen` 3つのパイプ（stdin/stdout/stderr）+ `text=True` 行バッファリング
- バックグラウンド reader スレッドが stdout を読み、JSON-RPC `id` で `_pending` キューに分配
- バックグラウンド stderr スレッドがエラーを収集（診断用に最新50行を保持）
- `_request(method, params, timeout)` が `threading.Event` で応答をブロック待ち——タイムアウト時は `TimeoutError`、server エラー時は `RuntimeError`
- `_send_line` に `_writer_lock` を追加して書き込みをシリアル化（複数スレッドの交差防止）

#### MCP プロトコルシーケンス（実装）

```
client  → server : {"jsonrpc":"2.0","id":1,"method":"initialize",
                    "params":{"protocolVersion":"2024-11-05","capabilities":{},
                              "clientInfo":{"name":"yansh"}}}
server → client  : {"jsonrpc":"2.0","id":1,"result":{...}}
client  → server : {"jsonrpc":"2.0","method":"notifications/initialized"}   # 通知
client  → server : {"jsonrpc":"2.0","id":2,"method":"tools/list"}
server → client  : {"jsonrpc":"2.0","id":2,"result":{"tools":[{name,description,inputSchema}, ...]}}
（その後ツール呼び出し）
client  → server : {"jsonrpc":"2.0","id":3,"method":"tools/call",
                    "params":{"name":"echo","arguments":{"text":"hi"}}}
server → client  : {"jsonrpc":"2.0","id":3,"result":{"content":[{"type":"text","text":"hi"}]}}
```

#### モジュールレベルのレジストリ

```python
_servers: dict = {}   # name -> MCPServer、_servers_lock で保護

load_config(workspace_dir) -> dict          # mcp.json を読み込み
start_all_servers(workspace_dir) -> tuple   # 全サーバーを spawn + initialize
discover_tools_as_schemas() -> list         # server ツールを yansh TOOLS schema に変換
parse_prefixed("mcp__a__b") -> ("a", "b")   # プレフィックスを分解
call_tool(prefixed_name, args) -> dict      # 対応する server にルーティング
shutdown_all() -> None                      # atexit フック
```

#### ツールの名前空間：`mcp__<server>__<tool>`

Claude Code に合わせる。LLM はプレフィックス付きの名前を見て、`_dispatch_tool_call` がプレフィックスを分解して転送。
内置ツールと名前がぶつかることはない。

#### 設定形式（Claude Code の mcp.json と互換）

パス優先度：`<workspace>/.yansh/mcp.json` → `~/.yansh/mcp.json`

```json
{
  "mcpServers": {
    "everything": {
      "command": "npx.cmd",
      "args": ["-y", "@modelcontextprotocol/server-everything"]
    },
    "github": {
      "command": "npx.cmd",
      "args": ["-y", "@modelcontextprotocol/server-github"],
      "env": {"GITHUB_PERSONAL_ACCESS_TOKEN": "ghp_..."}
    }
  }
}
```

Windows に関する注意：npx は実際に npx.cmd です——subprocess が npx を直接見つけられず FileNotFoundError をスロー。
初版ではユーザーに `.cmd` サフィックスを手で書かせます；次段階で PATHEXT 自動検出を追加。

### 2) `agent.py` 統合

```python
import mcp_client as _mcp_mod

# _dispatch_tool_call の末尾にルーティングを追加（「予期しないツール」分岐前）
if name.startswith("mcp__"):
    result = _mcp_mod.call_tool(name, args)
    return {...}

# 新規追加
def init_mcp(verbose=True) -> dict:
    """mcp.json のサーバーを起動し、ツールを TOOLS に注入"""
    started, errors = _mcp_mod.start_all_servers(_get_workspace())
    if started:
        new_schemas = _mcp_mod.discover_tools_as_schemas()
        # TOOLS を原地修正（参照の安定性を保つ、audit/subagent の各パスが同じコピーを読む）
        TOOLS[:] = [t for t in TOOLS if not t["function"]["name"].startswith("mcp__")]
        TOOLS.extend(new_schemas)
    ...

def shutdown_mcp() -> None: ...   # atexit フック
```

重要な設計：**TOOLS を原地修正せず再割り当てではなく**——agent.py の各パス（audit/code/fix/subagent）
がリスト参照を保有していて、原地の `[:]` 修正により全読者が再起動なしに新ツールを取得。

### 3) `main.py` 統合

```python
# 起動時
import atexit
atexit.register(_agent_mod.shutdown_mcp)
_agent_mod.init_mcp(verbose=True)

# コマンド
/mcp list           起動中のサーバー + ツール数 + alive 状態をリスト表示
/mcp tools [name]   指定サーバーの全ツールをリスト（mcp__ プレフィックス付き）
```

### 4) セキュリティ：audit モードが mcp ツールをブロック

audit モード `mode == "audit" and name not in READONLY_TOOL_NAMES` が mcp ツールを自動ブロック——
サードパーティの mcp ツールは外部状態を変更する可能性（例：GitHub MCP の create_issue）があるため、audit はデフォルトで無効。
ある mcp ツールを audit で使用可能にするには、ユーザーが明示的にそれを READONLY_TOOL_NAMES に追加する必要があります。

サブエージェント role：
- explorer/auditor：読み取り専用ツールセット、mcp を含まない（保守的）
- general：全ツール、全 mcp ツール を含む

直接呼び出し：


1. ✅ LLM がツール schema を見る（プレフィックス mcp__ + description [MCP/everything] ...）

7. ✅ content[] をマージして text "The sum of 1234 and 5678 is 6912" にする
8. ✅ LLM がそれを最終 summary "6912" に変換

### エンジニアリング意義：「1回の内置ツール実装」から「1回のプロトコル実装」へ

この回以前は、yansh に新しいツールを追加する必要がありました：
1. tools.py で関数を書く
2. tools_schema.py に schema を追加
3. tools_schema.py に READONLY_TOOL_NAMES に追加（読み取り専用の場合）
4. （可能性）agent.py の readonly_handlers にハンドラーを登録

N 個のツールを追加するたびに N 回変更。

MCP を統合した後：ユーザーが mcp.json に1行設定を書くだけで、そのサーバーの全ツールを取得できます。
GitHub MCP 1行 → 自動的に list_issues / create_pr / get_file_content などの十数個のツールを取得。
**エコシステム拡張ポイント**——これがプロトコルの価値。

### 学んだこと

- **JSON-RPC over stdio のシンプルさ**：gRPC / HTTP と比較して、stdio はほぼゼロ設定。
  Claude / yansh のような CLI プログラムが subprocess で server を起動するのが native な方法。
- **client / server / ユーザー3者トラストモデル**：
  - client（yansh）：ユーザーが設定した server は善良だと信頼
  - server：client が与えたパラメータは有効だと信頼（schema がある程度ブロック）
  - ユーザー：信頼できる server のみを設定する必要——server は任意の LLM コンテキスト + 任意のツールパラメータを見ることができます
- **プロトコルバージョン交渉**：`protocolVersion: "2024-11-05"`——server は非互換バージョンを拒否できます
- **ライフサイクル管理**：subprocess は明示的に shutdown（atexit）する必要があります、そうしないとプロセスリークします

## 非実装（後続に留保）

- HTTP/SSE 転送：最も主流の MCP は stdio、リモート server は HTTP ですが現在のエコシステムでは少ない
- resources / prompts：tools は 80% のユースケース、残り2つの capability で合わせて < 20%
- sampling（server 逆呼び出し LLM）：プロトコルが複雑、server にモデル/アカウント情報を見させる——セキュリティ上問題
- 自動再起動 / ハートビート：server がクラッシュしたら yansh で再起動すればよい
- ツール結果内の画像/ファイル：現在 content[] の非 text 項は JSON としてそのまま変換（LLM が見るのは JSON 文字列）
- Windows で自動検出 `.cmd` / `.exe` / `.bat`：現在は `npx.cmd` を手で書く必要があります
- prompt injection 防護：サードパーティ server が返した text は直接 LLM context に入ります；少なくとも description に「以下は外部 server からのもの」マークを追加

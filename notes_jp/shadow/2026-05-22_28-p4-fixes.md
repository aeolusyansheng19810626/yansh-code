## P4-3: `state.Session` ミラー `_ACTIVE_*` / `_SUBAGENT_STATS`

### 脆弱性

`_ACTIVE_SKILLS_PROMPT` / `_ACTIVE_MEMORY_INDEX` / `_SUBAGENT_STATS` が `Session.pull/push/reset` に含まれていない → ユニットテスト間の汚染：

- `active_skills_prompt: str = ""`
- `active_memory_index: str = ""`
- `subagent_stats: dict = field(default_factory=dict)`

`push` 時に `_SUBAGENT_STATS.clear() + update()`（**参照を置き換えない**——他の場所が保持する dict reference が期限切れにならない）。

### 検証

## P4-4: general subagent サマリー 修更ファイルリスト追記

### 脆弱性（Gemini 独自）

並行 subagent で `role=general` の子 agent がファイルを修更 → 親 agent の `conversation_history` にこれらの tool_call レコードが含まれない。親 agent がその後の古い context に基づいてコード生成 → **Lost Update Race**。

### 修正

`_run_subagent` 内でローカル `files_modified_locally` リストを作成、毎回 dispatch 後に `outs` をスキャン：
- `out["name"] in _WRITE_TOOLS` かつ `"success" in result` → `args` からファイル名 / file_path を記録
- 実行完了後 `role=="general"` かつ修更あり → サマリー末尾に追記：
```
[システムプロンプト] この部分タスクは X, Y ファイルを修更しました；親 agent の後続操作前にこれらのファイルを再度 read_file して認識を更新してください...
```

`_WRITE_TOOLS` には以下が含まれます：write_file / replace_in_file / apply_patch / replace_symbol / append_to_file / delete_file / move_file。

### 設計トレードオフ

**task_log の `_task_files_modified` スナップショット差分を使わない理由？**
並行 subagent 間で相互汚染が発生——A 実行時に B も append 中なら、A の差分に B のファイルが含まれる。ローカル `files_modified_locally` は _run_subagent のローカル変数で、本来的に thread-safe。

**general role のみを追加する理由？**
`explorer` / `auditor` は `dispatch_mode="audit"` ツールセットを使用、`write_file` などは内部 dispatch で遮断される——実際にファイルを修更不可能。記録しても無意味で、むしろ親 agent を誤導。

### 検証

`tests/unit/test_subagent.py` +3 件：
- `test_general_subagent_summary_lists_modified_files`：2 つのファイル書込 → サマリーに `[システムプロンプト]` + ファイル名 + "再度読込" 表示
- `test_explorer_subagent_summary_no_files_addendum`：explorer role は試行してもサマリー追記なし
- `test_general_subagent_no_files_modified_no_addendum`：general role でも読込のみで書込なし → 追記なし

`test_subagent.py` 35 → 38 すべて合格。

## 学んだこと

### 1. モジュール分割は必ずしも総行数を減らさない

agent.py 2859 → 2681（減 178 行）だが、subagent.py は新規追加 296 行（docstring / import / 型注釈含）。**総行数は 2859 → 2977**（実際はもう少し多い）。

価値は「行数が少ない」ことではなく、「耦合が少ない」こと：agent.py のコア流程 plan/code/audit/fix は現在、subagent ループ実装詳細と混在していない。今後子 agent に token budget / per-subagent log を追加するとき、subagent.py 内で実施でき、主流程を汚さない。

### 2. 遅延 import は循環依存の実用的な解決策

完璧な方案：subagent がコールバック注入を受ける（call_llm / dispatch / config など）。しかし改造範囲が大きく、実際には「agent が subagent を使う / subagent も agent ヘルパーを呼ぶ」が真の双方向依存。

実用的な方案：subagent.py トップレベルに agent なし、関数本体内で `import agent`。Python import システムはこのパターンをサポート：
1. import agent → トップ `from subagent import ...` → import subagent
2. subagent.py トップレベル実行完了（agent 不要）
3. agent.py トップ import 完了
4. 以降 _run_subagent に呼ぶたびに → `import agent` は既にキャッシュされたモジュール

ゼロ runtime オーバーヘッド（import キャッシュ）、循環依存を破除。

### 3. dict 参照 vs 置換の詳細

`Session.push` で `_SUBAGENT_STATS` に書き戻す際に `clear() + update()` を使用、**`agent._SUBAGENT_STATS = self.subagent_stats` ではない**。後者だと agent.py と subagent.py は異なるオブジェクトを保持――以前 `with _SUBAGENT_STATS_LOCK: _SUBAGENT_STATS["calls"] += 1` で修正したのは旧参照で、state.Session には見えない。

**経験則**：モジュール間で可変容器（dict / list / set）を共有するときは、常に in-place 修正を行い、参照置換は行わない。さもなくば alias が断絶。

### 4. 「ファイル修更後に親 agent に通知」は単なる「ログ追加」ではない

Gemini が提案したのは小さく見える（サマリーに 1 行追加）ですが、**情報システム設計**問題に属する：親 agent の conversation_history は世界に対する認識モデル――子 agent がファイルを修更したのに親 agent が知らない場合、モデルと現実の乖離が生じ、その後生成されるコードはすべて錯誤した前提に基づく。

`[システムプロンプト]` この行をサマリー末尾に追記することで、強制的に親 agent が次のラウンドでこれらのファイルを read_file 直す。これは「メッセージで LLM を現実と再同期させる」――本質的には LLM agent 設計における cache invalidation パターン。

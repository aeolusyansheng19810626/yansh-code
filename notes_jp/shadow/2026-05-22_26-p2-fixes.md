## P2-1: `procutil.py` を hooks/mcp 共有用に抽出

### 動機

P1-1 で mcp_client に `_kill_tree` 静的メソッドを追加し孫プロセスを処理；hooks.py は既に**ほぼ同じ** taskkill / killpg + Popen プロセスグループ作成ロジックを持つ。両側で別々に書くとドリフトが発生する（実際、hooks は psutil を使わず、mcp は使っている；mcp の実装が変わった場合、hooks は追従しない）。

### 修正

新しいモジュール `procutil.py` が以下を提供：
- `spawn_with_pgroup(cmd, **popen_kwargs) -> Popen`：プラットフォーム毎に自動で `creationflags / start_new_session` を追加、呼び出し側は重複した if win32 が不要
- `kill_tree(proc, timeout=2.0) -> None`：psutil 優先（最も信頼性がある）、フォールバック プラットフォーム固有（taskkill /F /T / killpg SIGKILL）

mcp_client と hooks の両方が procutil を使用；`MCPServer._kill_tree` はパススルー wrapper として保持（後方互換性）。

## P2-2: hooks.py stdout/stderr サイズ上限

### 脆弱性

`hooks.py:proc.communicate(input=stdin_text, timeout=timeout)` は stdout/stderr を全てメモリに読み込む、**サイズ制限がない**。制御不能 / 悪意のある hook が 10s timeout 内で数百 MB の stdout に書き込み可能——パイプが満杯になった後書き込みはブロック、しかし communicate は読み続ける、OOM。

### 修正

`communicate` を 3 つのバックグラウンド スレッド + メインスレッド調整に切り替え：
- 書き込みスレッド：stdin への ブロック 書き込み（stdout 満杯 + stdin 書き込みブロックによるデッドロックを避ける）
- stdout 読み取りスレッド：ループ read(4096)、累計 > `_HOOK_STDOUT_CAP=1MB` 直ちに `cap_exceeded` をセット
- stderr 読み取りスレッド：同様、cap=256KB
- メインスレッド：50ms 毎に `cap_exceeded.is_set()` / `t.is_alive()` / タイムアウト deadline をチェック

いずれかがトリガー → `kill_tree` + `_hook_error` を返す。

`_HOOK_STDOUT_CAP=1MB`：通常の hook 利用量（典型的に < 1KB）より遥かに大きいが、制御不能な数百 MB 出力を阻止できる。

### 検証

`tests/unit/test_hooks.py` +2：
- `test_run_one_hook_stdout_size_cap_kills_runaway_hook`：5MB 出力 hook → cap トリガー → エラー メッセージに「上限」を含む、elapsed < 10s（30s timeout を待たない）
- `test_run_one_hook_normal_output_under_cap_works`：通常の小出力 hook が完全に受信される（過度なスロットリング防止）

`test_hooks.py` 28 → 30 全て通過。

## P2-3: `task_log` グローバル list にロックを追加

### 脆弱性

`task_log.py:18-20` モジュール級 `_task_tool_calls` / `_task_files_modified` は list、agent が複数箇所で直接 `.append()` する。CPython GIL 下で list.append は単一アトミック、しかし：
1. `finish_task_log` の `dict.fromkeys(_task_files_modified)` の反復中に並行 append がある場合 → 結果は未定（CPython ドキュメントは「動作未定義」）
2. Python 3.13+ free-threaded モード GIL を削除後 list.append も原子ではない

子 agent が並行実行時、複数スレッドが同時にログに書き込む、記録順序が混乱、欠落の可能。

### 修正

`task_log.py` に `_log_lock = threading.Lock()` を追加、全ての読み書きはロック経由：
- `init_task_log` / `finish_task_log` clear + update 全体にロック
- `record_file_modified` / `record_tool_call` append にロック
- 新規 `snapshot_files_modified()` / `snapshot_tool_calls()` helper を読み取り側に提供

`agent.py` を 7 箇所の直接 append → `record_file_modified` / `record_tool_call` に変更；2 箇所の読み取り専用スライス → `snapshot_*`。

`finish_task_log` は盤 IO をロック解放後に実施（最初にロック内で dict のスナップショット、IO 外で JSON dump）、ロック保持時間を短縮。

### 検証

`tests/unit/test_task_log_concurrency.py` 4 条：
- `test_record_file_modified_concurrent_appends_complete`：50 スレッド × 100 回 → 合計長 == 5000（欠落なし）
- `test_record_tool_call_concurrent_appends_complete`：同様
- `test_snapshot_during_concurrent_writes_no_crash`：5 書き + 3 読み並行 → 例外なし
- `test_finish_task_log_under_concurrent_writes_consistent`：200 件記録後 finish 書き込み正確

## P2-5: `stderr_buffer` を `deque(maxlen=50)` に変更

### 脆弱性

`mcp_client._stderr_loop` の `self.stderr_buffer.append(line); if len > 50: self.stderr_buffer.pop(0)` が `call_tool` エラー診断の `srv.stderr_buffer[-3:]` と同時実行——`pop(0)` はアトミック操作ではない（O(n) 要素移動 + 長さ変更）、並行読み `[-3:]` 中に中間状態に踏む、IndexError、脱獄読み。

### 修正

`list` → `collections.deque(maxlen=50)`——append は自動的に ringbuffer で旧エントリを削除、**手動 pop 不要**、根本から race を排除。

副作用：deque はスライス（`[-3:]`）をサポートしない。両方の読み取りを `list(self.stderr_buffer)[-3:]`（最初に list に変換してからスライス）に変更。

`_stderr_loop` 簡素化：

```python
# 変更前
self.stderr_buffer.append(line)
if len(self.stderr_buffer) > 50:
    self.stderr_buffer.pop(0)

# 変更後
self.stderr_buffer.append(line.rstrip("\n"))
```

### 検証

新規単体テストなし——1 行修正 + 既存 mcp テスト 27/27 全て通過で十分。

## 学んだこと

### 「無害に見える実装の詳細」は並行処理 race の一般的なソース

P2-3 / P2-4 / P2-5 は全て同じクラスの脆弱性：**単一操作 CPython 下ではアトミック、複合操作はアトミックではない**。
- list.append はアトミック、しかし `for x in list` 反復中の append は動作未定
- list.pop(0) は単一ステップに見える、実際 O(n)、読み取り側は中間状態に踏む
- TOOLS[:]= は単一ステップに見える、実際「クリア + 再構築」2 ステップ

**経験則**：「読み-修正-書き」または「反復-修正」の任意の組み合わせはロックが必要。CPython GIL は特効薬ではなく、単一バイトコード のみアトミック——セマンティクス境界がバイトコード 境界に必ずしも合致しない。

### 「maxlen のある deque」は list+pop(0) の無料代替

`deque(maxlen=N)` は手動 pop の race を排除するだけでなく、パフォーマンス上 popleft は O(1) で list.pop(0) は O(n)。これは**構造的**改善——正しいデータ構造を選ぶことはロックより重要。

「最新 N ログ」、「LRU キャッシュ」など、小さなデータ構造でロックが必要に見えるもの、実際には `collections.deque` / `functools.lru_cache` に切り替えれば ロックなしでスレッドセーフになる。

### Hook リソース制限は「読み取り側で実施」、「書き込み側を信頼しない」

Hook はユーザーが自身で書いたスクリプト——小さい出力、stdin に応答、終了を仮定できない。全スロットリングは**読み取り側で実施**：
- size cap：読み取り側が byte 数を累計、到達で kill
- timeout：deadline は親プロセスが計時
- pipe デッドロック防止：stdin 書き込み / stdout 読み取り / stderr 読み取りは必ず各 1 スレッド、communicate(input=...) 不可

これは web server が untrusted client を扱うのと同じ思想——全ての外部入力は悪意的と仮定。

### 共有コード抽出のタイミング

procutil 抽出はちょうどいい時机——以前 hooks と mcp_client は各々 `taskkill /T /F` / `killpg` を書き、差は小さく見えるがドリフト已に発生（mcp は psutil を使い、hooks は使わない）。**≥2 呼び出し側が共有する時に抽出**——早すぎると過度設計。

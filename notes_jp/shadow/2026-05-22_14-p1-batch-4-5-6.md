P0 の3項目完結（[_13](./2026-05-22_13-task-complete-signal-persistence.md)）に続き、

## 何を変更したか

### P1 #4: JSON 解析の堅牢性

**1) llm_client.py: response_format 検出**

以前は「Claude が response_format をスキップする」がハードコードされていた——粗い。改善した：

- `_should_skip_rf(model)`: ハード規則（既知の低パフォーマンスモデル）+ 動的ブラックリスト（実行時 400 後に追加）
- `_RF_UNSUPPORTED: set` プロセスレベルキャッシュ
- `_call_single_model` / `call_llm` が `_looks_like_rf_rejection(exc)` をキャッチし、ヒット時にモデルをブラックリストに追加、自動的に response_format を削除して1回再試行

**重要な発見（実測）**: ICA バックエンド**400 を返さないが品質が低下**——
`response_format={"type": "json_object"}` を Sonnet 4.6 に渡すと出力が `{}` に低下し、
400 拒否よりも隠蔽性が高い。そのため Claude は「ハードスキップ」経路を取るのであって「検出降級」経路ではない。

後人への注記: 動的検出は将来の未知バックエンドに有用。現在のバックエンドの既知の落とし穴はハード規則に入れれば毎回踏むことがない。

**2) agent.py: `_call_with_json_retry` ラッパー**

```python
def _call_with_json_retry(stage, messages, parser_fn,
                          response_format=None, stream=None, ...):
    response = call_llm(...)
    ok, data, err = parser_fn(content)
    if ok: return data
    # 1回再試行: 元の内容 + エラーを LLM に持ち帰る
    retry_messages = messages + [
        {"role": "assistant", "content": content},
        {"role": "user", "content": f"前回のあなたの出力は有効な JSON として解析できませんでした...エラー: {err}\n前回の出力: {raw}"},
    ]
    response2 = call_llm(retry_messages, ...)
    ok2, data2, _ = parser_fn(content2)
    if ok2: return data2
    # 両方失敗 → raw をログ + 降級値を返す
    return data2
```

`_parse_plan_response` / `_parse_review_response` を2層に分割:
- `*_with_status` が `(ok, data, err)` 3要素組を返す——再試行ラッパー用
- `*_response` は古いエントリーポイント、委譲してログ、単体テストは後方互換

`plan()` / `review()`（`REVIEW_MODEL` が未設定の場合のみ）を再試行ラッパーを使用に変更。

### P1 #5: グローバル状態リファクタリング（段階的）

モジュールレベル変数（agent._BATCH_MODE / _PROJECT_TYPE / _CURRENT_SNAPSHOT、
tools._BATCH_MODE / _BATCH_STRICT / _AST_CACHE）は変更せず、新しい `state.py` を作成:

- `Session` dataclass: すべての可変状態をミラーするフィールド
- `Session.pull()`: モジュールからスナップショットをプルする
- `Session.push()`: Session をモジュールに書き戻す
- `Session.reset(workspace_dir=None)`: 1行でゼロにクリア（AST キャッシュ含）
- `scoped_session(workspace_dir)` context manager: 入場時にスナップショット取得→reset; 退場時にスナップショット復元 push

テストは現在 `with scoped_session(tmp_path): ...` でユースケースを隔離できる。
将来、状態を完全に移出したい場合は、ファイルごとに `current()` への読み書きに変更すればよい——今回は行わない。

**なぜ完全な Session クラスでモジュールグローバルを置き換えないのか**:
- agent.py / tools.py で2つの _BATCH_MODE が、import チェーンの統合が複雑
- 1回限りの大規模な爆発的な書き直しは ~15 箇所の読み書き + テスト fixture を変更する必要
- 段階的: 最初に「テストを隔離できる」という最も苦しい点を解決し、将来さらに移行

### P1 #6: サンドボックスモード opt-in

新しい `sandbox.py`（専用モジュール、tools.py 汚染を回避）を作成:

- `SandboxConfig(enabled, backend, image, extra_args)` dataclass
- `parse_cli_arg(value)` が `--sandbox docker[:image]` / `none` を解析
- `wrap_command(cmd, ws)`: 無効時は元々のまま返す; 有効時は出力
  ```
  docker run --rm -i -v <abs(ws)>:/ws -w /ws <image> sh -c '<cmd>'
  ```
  インジェクション防止に `shlex.quote` を使用

接続ポイント:
- `tools.execute_command`: Popen の前に1回 `sandbox.wrap_command()` を呼び出し、無効時はゼロコスト
- `main.py`: `--sandbox` パラメータを追加; 起動バナーに `サンドボックス: off | docker:python:3.11-slim` を表示

**execute_command だけを含める**: read_file / write_file などはすべて制御された IO; execute_command は
「任意のコードを実行する」唯一のツール。

**rw ではなく ro マウントにしない理由**: テストはしばしば中間ファイルを書き込む必要があり; 隔離の中核的な利益は「ファイルシステム/プロセス/ネットワークはすべてネームスペース隔離」、ro マウントは反対に「テスト実行」経路をカットしてしまう。将来、サブオプション `--sandbox docker:img:ro` を追加可能。

## 評価

P0 の3項目は「機能正確性」を固め、P1 の3項目は「工学的健全性」を固める:

- **P1 #4** は隠蔽性の高いバグを修正: 以前は Claude が response_format をスキップすることは「防御的フォールバック」と思っていたが、
  実測では「必須」である——ICA はパラメータを受け入れるが出力品質が低下。再試行ラッパーは現在、
  極端なケース（スキーマ検証失敗）で plan/review が1回自救できるようにする。
- **P1 #5** は大規模リファクタリングではなく、「テスト隔離可能」の最小限の工学化——`scoped_session` により単体テストが
  `reload(tools)` といった hack から卒業できる。完全な Session クラスは将来に残す。
- **P1 #6** は opt-in セキュリティ: デフォルトはゼロ動作変更、ゼロ docker 依存; 有効化は1行 CLI で隔離可能。
  現在、開発マシンに docker がインストールされていないため実際の docker テストはない、必要な場合はホスト変更して後で補充。

次の波（このスコープ外）:

- P1 #6 続行: `--sandbox docker:img:ro` サブオプション; ネットワーク隔離 `--network=none`; 別の backend（podman / firejail）
